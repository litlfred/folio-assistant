Paper document generation

Pipeline: content objects → PDF 

content/<paper>/<paper>.ts          paper manifest (metadata, sections)
     ↓
pipeline/build.ts           validates + renders sections → output
     ↓
preamble template + manifest        generate-main.ts → main document
     ↓
PDF engine                          main → PDF
     ↓
pandoc                              → .md → paper-raw.html
     ↓
generate-html.py                    → paper.html (enhanced)
     ↓
generate-index.py                   → per-paper index.html (viewer)

Running locally 

# Build sections + generate the main document from the manifest
cd content && bun run pipeline/build.ts \
  <paper>/<paper>.ts \
  --out-dir ../sections/ \
  --generate-main \
  --main-out ../main.tex \
  --preamble ../latex/preamble.tex

# Compile PDF (requires the PDF engine). No engine in the sandbox? Run
# scripts/install-tex.sh first, or fall back to the Docker image.
cd .. && <pdf-engine> main.tex

Formal-layer documentation

When a paper carries a formal layer (e.g. a proof assistant), its API documentation is generated by the formal-layer CI workflow after the formal build succeeds. If the primary doc generator fails, the workflow falls back to a static HTML source browser.

A gap/axiom report lists unproved-gap declarations and dependency transparency; it is produced by the same workflow.

Folio landing page

The root index.html on the docs site is a folio page listing all papers with viewer links. Generated from content/folio.ts.

This is the paper pipeline’s own page. In a checkout that instantiates several harnesses, which instance owns <base>/index.html is site.landing in the root index.config.json — an instance name, or "hub". That is index-config’s rule. For where every other page is published, canonical and alias, see schema-management §”Where a viewer publishes”.

Adding a new paper to the folio

  1. Create content/<paper-dir>/<paper-dir>.ts (paper manifest with title, authors, abstract, macros, sections)
  2. Create section directories with content objects
  3. Add paperRef({ dir: "<paper-dir>", title: "...", ... }) to content/folio.ts
  4. The pipeline discovers it automatically via extract-folio.py

Unified Docker image

All CI/CD workflows use the same paper-assistant Docker image (adapters/mcp-server/Dockerfile), which is also the folio MCP server. This eliminates per-workflow tool installation and ensures consistent build environments. The image bundles the PDF engine, the content pipeline runtime (Bun), pandoc, graph tooling, and CI scripts.

Using locally (Docker fallback)

When the PDF engine isn’t installed locally, the render hooks automatically fall back to the Docker image. The scripts/lib/docker-tex.sh helper automates this fallback for the render hooks.

In brief

WHO is building SMART Guidelines content (guidance turned into structured, computable, testable form) with AI agents doing part of the authoring. To keep those agents accurate, every piece of work runs through a process diagram (BPMN): each step belongs to a role, and an agent taking that role is given only that step, with only the knowledge it needs. The software that enforces this is the harness.

This proposal does four things:

  1. One work plan, any storage. The list of work items (each one a work item) is kept by a store that offers a fixed set of operations (read, update, note, history, “where is this item in its process?”). Today the store is a git branch; tomorrow it can be a server or an MCP service. Nothing that uses the work plan needs to change when the storage does.
  2. The process starts the agent. When a step is ready and its role is an AI agent, the harness starts an agent of a chosen model (Claude, Gemini through Antigravity, others) and hands it a work order: the item, the step, the role’s skills. The work order is the same for every model.
  3. Everything is recorded. Every change to an item, and every step it passes through, is kept as history. That history is also the trace a benchmark is scored on.
  4. Fair testing in the ITB. The ITB test bed stands up a private copy of all of this per test run, starts several agents (possibly of different models), and checks what they did. A test can hand the agent its task as a tracked work item, or hide that entirely: the agent gets an ordinary prompt written from the item and works as it would in the real world, while the harness tracks the item behind the scenes (§4.9). Every run is set up from a saved run profile (which model, which knowledge sources, MCP or command line, which tools are on), so runs are comparable (§4.12).

1. Why: the WHO Assured AI concept note

The concept note Gemini Integration and Benchmarking Methodology for WHO Assured AI (2026-11-02) sets the purpose of this work.

Its background. WHO Assured AI is establishing how complex health guidance becomes computable, structured and verifiable (L2, L3, L5), and how large language models are to be benchmarked for high-stakes health work. To keep the infrastructure model-agnostic, Gemini must be integrated deeply enough to reach usability parity with the models already in use, and the methods must be validated against Gemini’s own reasoning and tool-calling.

Its architecture, which this proposal implements:

  • BPMN swimlanes as a guardrail. Work is split into swimlanes; each task belongs to a role (human or AI) and is supported by skills with tooling or prompts behind them. An agent gets one specific, checkable task with bounded context, which structurally limits hallucination.
  • MCP servers give agents their tools and precise data.
  • Layered knowledge graphs: L1 foundations, L2 importing L1 for digital adaptation, L3 importing both for executable logic; L4 and L5 to follow once the guardrails are proven.
  • Central instructions, model-specific prompting. Behaviour is defined once, but each model may need its own wording to stay on track. Claude already has such prompts in its workflow; replicating them for Gemini (GEMINI.md) needs dedicated testing.

Its method. Models are tested against WHO baselines and new projects through three routes (Route 0 bare, Route A with skills, Route B with skills and the knowledge graph), driven by executable Gherkin test specifications through the BPMN harness, so that reasoning traces are captured and models can be compared on a WHO-approved benchmark.

Its asks of Google: Cloud credits to run Antigravity at enterprise scale for the benchmark pipelines; Gemini Ultra access for three engineers; and a consultation with the Antigravity developer-experience team on replicating guardrail prompts, on Gemini’s use of the MCP servers and skills, and on shaping outputs for the ITB.

Its expected outcomes: a native Gemini path through the harness, a validated benchmarking method, and progress toward a WHO-approved standard for testing LLM output in digital health.

What that requires of the harness, and where this proposal provides it:

The concept note needsWhat the harness must doSection
Agents confined to one step with bounded contextThe engine, not the agent, decides the step and hands over only that step’s context§4.4, §4.5
Agents reach tools and data over MCPThe work plan reachable over MCP, not only through git commands an agent may not have§4.2, §4.10
Usability parity; guardrails that do not depend on one vendor’s prompt fileA model-neutral work order; model-specific wording kept in the launch Tool, where a test can check it§4.5
Routes 0, A, B through Gherkin and the BPMN harness, with tracesOne dispatcher that runs the same case under each route and records everything in one shape§4.6, §4.7
Outputs shaped for the ITBThe ITB drives each run through a small set of harness services and receives the trace§4.8
Behaviour comparable with real-world useRuns where the agent is not told it is working a tracked item, or that it is being tested§4.8, §4.9
Models switched and compared on equal terms, with the same sources and toolsA standing test configuration: named run profiles for models, knowledge sources, MCP or command line, and which tools are on§4.12

Two facts matter from the start. Each repository’s GEMINI.md is a short pointer to AGENTS.md, so today every model gets the same written guidance, and anything Claude-specific lives outside the process. And the harness’s benchmark requirement already says a benchmark never writes to the real work plan, so a run needs a store of its own (§4.7).

3. Where things stood (2026-11-02)

  • The store was already modelled as a role with Tools, and its contract was written, but it was phrased in terms of git, and nothing tested it.
  • The process diagrams were already storage-neutral. The skills were not: about 57 lines in 7 skills told agents to run git commands to change a work item.
  • The engine wrote work items one way only: by running the beans command or editing the file directly. A server-backed store could not be used without changing the engine.
  • Agents got work item ids, not work items. A step’s context named its work items but did not carry their content, and nothing on a work item said which process or step it was at; the only way to place a work item was to read every instance.
  • Nothing in the harness started an agent. beans-serve (a separate work items server) can already start a Claude agent per work item. Gemini through Antigravity, GitHub Copilot and local agents were all started by hand, with a prompt written for each model.
  • History lived only in git, with no way to ask for it, and recording through processes had stopped in early October.

The detailed findings, with file names, are in Appendix A.

4. Design

4.1 The work plan is a set of operations

Every Tool that keeps the work plan provides the same operations, each with a guarantee a test can check:

OperationWhat a caller can rely on
get(id)the work item as last written, or “none”
list(filter)work items by status, type, tag or parent
create(bean)the id is unique
update(id, change, ifMatch)refused if someone else changed the work item since you read it (ifMatch is the version you read); a retry on the fresh version lands, so no concurrent change is ever lost
note(id, text, by)added to the work item’s notes, never rewriting earlier ones
history(id)every change, oldest first: when, by whom, what, and from which process step
positions(id), beansAt(process, step)where a work item is in its processes, and which work items are at a step (§4.4)

Archiving is a field set through update, not a separate operation (ruled, Q7): it is refused unless the work item is completed or scrapped, and an archived work item can still be read.

One conformance test suite checks every Tool against these guarantees. Built: the contract (cat-harness#993), the tests (cat-harness-tools#1418).

4.2 Tools behind the work plan

ToolKept whereStatus
git state brancha git branch per work plan, read and written with the beans command or by editing filestoday’s storage; has its own page
work items serverbeans-serve, which already offers versioned updatesproposed
MCP servicean MCP server offering the operations as tools to any agentproposed (§4.10)
run-scoped storea private store for one test run (§4.7)proposed

The git commands now in the skills move to the git Tool’s page; each skill says the operation (“note the bean”, “claim it”). A check refuses git terms in work-plan skills outside a Tool page.

4.3 The engine uses the operations

The engine reads and writes work items only through the operations, so the Tool can change without touching it. Which Tool is named in the deployment description (ruled, Q2), for example "stores": { "work-plan": "beans-git-branch" }; a checkout says which description is its own with the CAT_DEPLOYMENT environment variable, and without it uses the git branch as today. A description naming a Tool the toolset does not have is refused, never silently replaced by the real work plan. Built (cat-harness-tools#1420, #1424; cat-harness#1005 names the store in every deployment).

4.4 Where a bean is, and what the agent is given

A work item’s position lives only in the process instances that name it (ruled, Q1): there is one source of truth and nothing to keep in step. positions(id) and beansAt(process, step) read the instances, including the sub-processes an instance calls. Built (cat-harness-tools#1421).

When the engine reports what step is ready, each step’s context now carries its work items themselves (title, status, description, links, position), not only their ids. Built (cat-harness-tools#1423).

4.5 The process starts the agent

A shared step, Dispatch agent, is added to the diagrams. When a ready step’s lane belongs to an AI role, the engine hands a work order to a launch Tool:

Work order fieldFrom
the work itemget and positions
the instance and stepthe token
role, skills, conventionsthe step’s context
the storewhich Tool to use and how to reach it
how to report“when done, complete this step of this instance”

The work order is the same for every model: plain data and the skill texts. How a particular model is best told to stay on the step is the launch Tool’s job, written on that Tool’s page and tested, so parity between models is checked by a test instead of depending on someone copying a prompt into GEMINI.md.

Launch ToolModelToday
launch-beans-serveClaude, through the work items serverexists; first (ruled, Q3)
launch-claude-sessionClaude, cloud session or routineAPI exists, no Tool yet
launch-antigravityGemini through Antigravity, on the project the concept note requestsprompts written by hand today
launch-copilotGitHub CopilotAPI exists, no Tool yet
launch-localany command-line agentno

The agent reports by completing its step; that moves the token, writes the instance history and notes the work item, so the position and history stay current without anyone remembering to update them.

4.6 History: one event log

Every change is an event: created, status changed, claimed, noted, changed, archived, step reached, each with when, who and what, and for a process step the instance and step. history(id) returns them in order. For the git Tool the events are derived from the git history of the work item plus the instances’ own histories, so nothing is migrated (ruled, Q4); a server Tool would keep them as rows. Built (cat-harness-tools#1425).

Each work item’s page shows this history with a stepper (buttons and keyboard), drawing the process the work item was in at each moment. In review (cat-harness-tools#1426).

4.7 Benchmark runs: route, private store, trace

A benchmark run is the same dispatch with a few settings, not a new runner:

SettingValues
system under testmodel + launch Tool + its configuration
route0 the task text only: no skills, no knowledge graph · A skills, knowledge-graph tools withheld · B skills and the knowledge graph
context modebean-aware or bean-blind (§4.9)
sources and toolsthe run profile (§4.12): knowledge sources, MCP or command line, which Tools are on
storea run-scoped store: private to the run, seeded from the test case, thrown away after (ruled, Q5)
  • A test case becomes seeded work items and started instances in the run’s store: Given seeds, When dispatches, Then checks the store and the instances afterwards.
  • The trace is the run’s history, its instance histories and every step the engine refused, in the same shape whatever the model. That is the reasoning trace the concept note wants handed to the ITB, and the count of refused steps becomes a metric of every run.
  • Results are written to the benchmark output area, never into the authored content.

4.8 The ITB runs the test

The ITB drives each run (ruled, Q6), using Gherkin test plans as already agreed in the ITB proposal. The harness offers it a few services, so a test step is a call, not a script:

ServiceDoes
harness-upcreates one private harness: a state machine, a run-scoped store and the run’s context (below)
seedwrites work items and started instances into it
start-agentsstarts each agent through its launch Tool, with its model, route, context mode and work items
observestreams events while the run goes on
statethe store and instances at a moment, for Then to check
harness-downexports the trace and removes the private store

A test plan reads like a description of work:

Feature: two agents share a merge window
  Background:
    Given a harness with processes "code-change-review" and "merge-train"
    And the context "folio-assistant@<hash>"
  Scenario: A opens changes, B lands them
    Given agent A (gemini, route B, bean-aware) holds beans S_A = {a1, a2}
    And agent B (claude, route B, bean-aware) holds beans S_B = {b1}
    When the agents are started
    Then within 2 hours every bean in S_A is completed
    And bean b1 is at "merge-train" step "End_Landed"
    And no instance recorded a refused step

The ITB keeps its role of running the plan and judging the result; the result comes back in the ITB’s own report format.

Agents should not know they are in a test. What an agent sees is what it would see in real work: the same work order, operations and skills; work items written as real work, never labelled as tests; the run’s identity (plan, route, model) kept in the harness, never shown to the agent. What cannot be hidden (a fresh store, a short repository history) is listed on the test plan so a result can be read with it in mind.

One consistent context. Each run gets one repository built in layers, the same for every model in the run:

LayerFrom
knowledge graphthe L1, L2, L3 content and harness definitions the processes need, at pinned versions
skillsthe skills the plan’s processes use
memorya MEMORY.md per role, generated for the plan’s processes, so every model starts with the same memories
instruction filesAGENTS.md, with CLAUDE.md and GEMINI.md pointing to it, so no model gets guidance the others lack

The repository is identified by its commit hash, named in the plan’s Background: two runs with the same hash gave their agents the same world. Route 0 gets an empty context; Route A skills and memory without the knowledge graph; Route B all of it.

4.9 Bean-aware and bean-blind runs

Owner, 2026-11-03: “the bean is the test context.”

A run hands an agent its task in one of two ways. Both are measured against the same work item.

Bean-awareBean-blind
What the agent receivesthe work order (§4.5): the work item, its step, the store, how to reportone fixed prompt, written from the work item
What the agent knowsthat it is working a tracked item in a processonly the task, as a person would phrase it in real work
Who records progressthe agent, by completing its stepthe harness, observing what the agent produced
What it measureshow well a model works inside the harnesshow a model behaves on the same task without the harness telling it anything: the real-world case

The fixed prompt. For a bean-blind run, the work item under test is turned into a prompt by a fixed, reviewed template: the task (from the title and description), the acceptance criteria, the material to work on. It contains no work item id, no store, no process or step names and no harness vocabulary; a check refuses a prompt that leaks any of them. The prompt is generated once, stored with the test case and identified by its hash, so every model gets exactly the same words, and a re-run is reproducible.

The work item is the test context. The work item still exists, in the run’s private store, and is what the test is scored against: its acceptance criteria are the Then. The harness plays the agent’s part in the process: it watches what the agent produces (files, answers, a change), moves the instance and notes the work item on the agent’s behalf, so the run leaves the same trace as a bean-aware run. The agent’s own transcript is kept as its reasoning trace.

With the routes, this gives a small grid to compare models in:

Bean-awareBean-blind
Route 0 (bare model)— (no work order without skills)the bare model on the task: the baseline
Route A (skills)skills and the work orderskills available, task in plain words
Route B (skills + knowledge graph)the full harnessthe full knowledge, no harness framing

The gap between a bean-aware and a bean-blind run of the same model and route measures what the process harness itself contributes, which is the guardrail claim the concept note makes.

In a test plan:

Scenario: the same task, told and untold
  Given bean g7 "Encode the ANC contact schedule as decision logic"
  And agent G1 (gemini, route B, bean-aware) holds bean g7
  And agent G2 (gemini, route B, bean-blind) is given the prompt of bean g7
  When the agents are started
  Then both outputs meet the acceptance criteria of bean g7
  And the trace of G2 shows no harness vocabulary in its prompt

4.10 A live work plan on your own machine

Owner, 2026-11-03: “5 sec refresh is local mcp bean store. on ghpages, refresh makes no sense.”

The published site (GitHub Pages) shows the work plan as it was when the site was built; it cannot reach a store server. A store server can only be reached on the machine that runs it (localhost). A hosted server (for example on Hetzner) would change that, but there is none, so it is out of scope.

The local setup:

  1. Run the harness server in the checkout: CAT_DEPLOYMENT=developer bun run cat-harness-tools/src/server.ts.
  2. Open the beans-by-process page from the same machine. It offers “Refresh every 5 s from the local bean store” and shows what the store holds now, through whichever Tool the deployment names. On GitHub Pages the control does not appear.
  3. If no server answers, the page says so and keeps what it was built with; it never shows an empty plan because a request failed.

The route it reads (GET /api/work-plan/beans-processed) answers only on localhost, is read-only, and allows cross-site reads from localhost pages only. The proposed MCP service (§4.2) would sit on the same server, offering the operations to agents. In review (cat-harness-tools#1429).

A run, end to end:

  1. CAT_DEPLOYMENT=itb-benchmark is set where the harness runs.
  2. The ITB calls harness-up: a state machine, a run-scoped store (because stores says so) and the pinned context.
  3. The plan’s Given steps call seed, and for bean-blind agents the fixed prompts are generated and pinned.
  4. When the agents are started calls start-agents: each agent’s launch names its Tool and model; bean-aware agents get the work order, bean-blind agents their prompt.
  5. The agents work; observe streams the events. On localhost the beans-by-process page shows the run live (§4.10).
  6. Then steps check state; harness-down exports the trace and removes the store. The ITB reports the result.

From outside the harness, each model needs what the deployment names and whoever runs it supplies: for Claude, the claude command and its login; for Gemini, the Google Cloud project and identity the concept note requests, reached through Antigravity.

4.13 Work context, and beans out of the content layers

Owner, 2026-11-03: “the beans stay out of the smart base dependency tree … the knowledge graphs for the smart guidelines should not have any reference to beans in it. Otherwise it pollutes the testing run because the agent will then learn about beans and processes”; “when an agent takes up / processes / completes a task it should preserve memory/context. one Tool is a bean”; “so we remove beans from explicit in most diagrams, make sdlc a subgraph and clean up it and dependent harness use of beans”.

Where work items reach a content layer today (review of 2026-11-03):

  • Through the dependency chain: smart-base → fhir-harness → folio-assistant-core → cat-harness. smart-base mounts cat-harness whole, and its instruction file tells the agent to read the cat-harness skills.
  • Through the diagrams. Process_BeanOpen and Process_BeanClose sit in processes/sdlc/, a folder of the one processes graph rather than a sub-graph, and are called by 15 cat-harness diagrams (7 of them outside sdlc/: kg, library, process, global tasks), by 8 fhir-harness diagrams and by 4 smart-base diagrams, including the DAK diagram diig-investment-path.bpmn. cat-harness’s diagrams also carry 115 task-level op="note" steps.
  • Through the MCP server, which offers every Tool in the chain, and the skill scan, which reads every sibling folder.
  • Through prose: about 200 of 265 cat-harness skill files say “bean”, many only as a provenance id (“bean kg83”).

The work item data does not leak: it is on its own branch. The words do.

A work item is tied to a process instance, not to a task. An instance names its work item (bean, carriedBeans), and every sub-process it calls inherits it. Tasks only act on it: the op steps, a data output to the Work items store (Q-BR-8 F), and a call activity naming extra work items.

Work context: what replaces the markup (ruled, Q11: all three):

  1. The engine, at every task boundary and with no markup in the diagram:
    • on take up, it hands the agent what was kept from earlier work on the same item;
    • on complete, it stores the agent’s completion summary, links and what is left open;
    • at the instance’s start and end, it does what Process_BeanOpen and Process_BeanClose did: claim, resolve, archive.
  2. A neutral data store: a diagram may mark a task that must read or write the context explicitly with a standard BPMN data store named Work context. The engine binds it to the chosen Tool.
  3. The agent may record context during a task through a neutral MCP tool, work_context_note.

All three write to one work-context store, a role like the work plan (§4.1), whose Tool the deployment or run profile chooses (§4.12):

stores["work-context"]Used by
work-plan (default): a work item in the work-plan store, with each line’s metadata wrapped by the serverfolio-assistant development and bean-aware runs (the real store); bean-blind test runs (the run-scoped store, Q5): the context is kept and measured, and the agent never learns it is a work item
nonea run that tests a cold start

Owner, 2026-11-03: “the neutral work_context_note is in reality a bean with metadata wrapped in the backend (just not exposed to agent)”. So work_context_note is its own Tool, registered apart from the workflow_* tools and outside the sdlc sub-graph: an agent that is offered it sees a neutral name, description and one input, never the workflow tools it would otherwise reach through the dependency tree. The run’s launcher binds the session to its instance (CAT_WORK_INSTANCE); the agent never sees an instance or item id. Built (cat-harness-tools#1435).

This is separate from agent-memory, which assembles each agent’s long-lived memory file; work context belongs to one item and one run.

Two switches, not one. The harness’s own machinery (store, engine, trace) stays on in a test run, because the work item is the test’s context. What the agent is given (skills, knowledge graph, Tool list, instruction files, prompt) follows the run profile. A sub-graph that is switched off removes the material from the agent’s context; it does not stop the harness using it.

sdlc becomes a named sub-graph of cat-harness (ruled, Q12), on the pattern of openapi/ and archimate/: one folder whose graph.json declares what it holds — the sdlc skills, the sdlc processes, the work-plan and work-context typologies, and the work item and workflow Tool definitions. It is off by default in every layer above cat-harness; folio-assistant switches it on. The MCP registrar and the skill scan honour the switch, and a whole-mount does not override it.

Clean-up (ruled, Q13):

  • No work item markup in diagrams outside the sdlc sub-graph: no calls to Process_BeanOpen/Process_BeanClose, no op steps, no Beans-store data outputs. The engine does that work (above). This covers cat-harness, fhir-harness and smart-base.
  • Provenance ids move out of agent-facing text (into the node’s provenance fields or the changelog).
  • Generic skills say work context and the operation, never “bean”.
  • The instruction files are generated from the run profile.
  • Development checkouts keep work items on; every content layer’s knowledge graph and every agent test context has them off.

The leak check, check:context-leak. The runner is generic, in cat-harness-tools; the vocabulary is a code list the sdlc sub-graph declares. It scans a built context — every file, the live MCP tool list, the generated instruction files and the fixed prompt — and, in each content layer’s CI, that layer’s bean-blind context. It matches work item, the provenance-id pattern, beans/, the work items branch name, work plan, work order, the workflow_* and work-plan tool ids, Process_Bean* and cat-harness.processes:bean. It does not match process, BPMN or business process: DAKs hold business processes as content. “Could not determine” is never clean. It starts in report mode and becomes a gate once the clean-up lands.

4.14 The memory store: drawn only where a process needs it

Owner, 2026-11-03: “We need the memory store in the diagrams, only if a process explicitly requires it. For example, if an agent knows that it is shutting down and wants to write a record of where it’s at. Or if an agent wants to create a shared memory store as part of a swarm that they can collectively access. It may be that it gets implemented as a tool as beans. There may be other tools. We use beans as a tool in SDLC. We also use it as a tool for the same type of agentic memory in collaborative agent-assisted content development.”

So the work context of §4.13 is one use of a more general Role, the memory store:

  • A Role, not a Tool. Like the work plan (§4.1), it is a set of operations — keep an entry, recall entries, checkpoint where the work stands — over a scope: one item, one run, or one shared space a group of agents opens together. Work items are one Tool for it; a run-scoped store, a plain file store or a server are others. The deployment or run profile picks the Tool (stores["memory"]).
  • Drawn only where a process needs it. A diagram draws a standard BPMN data store whose dataStoreRef is memory only where the process itself depends on memory:
    • Checkpoint before stopping: a task such as Record where the work stands writes to it before an agent shuts down or hands over, and the task that resumes reads from it.
    • Shared memory for a swarm: a task such as Open a shared memory space creates a scope that the agents of a parallel or multi-instance step all read and write; writes carry the version they read (ifMatch), so two agents never overwrite each other silently.
    • Hand-over between lanes: a task in one lane writes what the next lane needs to know. No diagram draws it as routine bookkeeping. What every process needs (who took the work, when it finished) the engine keeps without a drawing (§4.13).
  • The agent’s side is neutral. The MCP tools (memory_note, memory_recall, memory_checkpoint) and their skill name no Tool. The backend wraps each entry with its metadata (process, step, instance, agent, time). It is its own Tool group, so a bean-blind agent can be offered it.
  • Two kinds of work use work items for it today, and both keep them: software development (sdlc) and collaborative, agent-assisted content development (folio-assistant). So the work item Tool is not inside sdlc: it is its own sub-graph, beans, which sdlc and folio-assistant both switch on. The memory store Role, its data store, its tools and its skill sit in cat-harness itself, outside both, so a content layer’s diagram (a DAK authoring process, say) can draw a memory store without naming work items.

A work item is a memory record with more structure (owner, 2026-11-03: “bean is a memory note w/ additional structure for process/role/ etc… can we formalize this a bit more in schema to show this and align a bit the services”; ruled Q17, layered):

LayerSchemaStore interfaceWhat it adds
memory recordmemory-record (new base)MemoryStore: keep, recall, checkpoint, list by scopeid, title, scope (item, run, shared), about, tags, timestamps, and structured entries: each with text, when, who, kind (note, step done, checkpoint, taken up, closed) and, when the engine knows them, process, step, instance and role
work itembean-defs extends memory-recordWorkPlanStore extends MemoryStore: create, update with ifMatch, relations, positions, beansAtstatus lifecycle, type, priority, parent and blocking

So the memory service and the work item service are one service: a memory note is a work item note without the work-item fields, and the process and role are entry metadata the backend fills in. The work items Tool implements both layers and keeps entries in the work item body as lines it can parse back (the conformance tests check the round trip, so existing work items stay valid); a file store implements only MemoryStore. The curated agent memory (the memory kind, “never written by a process”) stays separate.

The ITB chooses the memory Tool, and the test scenarios include (owner, 2026-11-03: “the test scenarios should include cases where agent is offered no memory store vs when it is offered beans as a Tool and the SDLC type processes”):

Each is a run profile (§4.12), so the same case runs under all three and the ITB compares them.

6. Keeping the process recorded

A work item’s place in its process is only as good as the habit of recording it, and nothing can force that: anyone can edit the work-plan branch directly. So (owner, 2026-11-03) the recorded path is made the easy one, and drift is reported, never blocked:

  • Claiming or creating a work item starts its process. The claim command starts or advances the work item’s process instance.
  • Agents get the work item with its step (§4.4), and completing the step records the move (§4.5).
  • Drift is reported: an in-progress work item that no running instance names is flagged on the beans-by-process pages, in the repository health report and when a session starts.
  • The skills say so: working a work item means starting or advancing its instance.

7. What this does not do

  • It does not move work items off the git branch; the git Tool stays the default.
  • It does not change what the diagrams mean.
  • It does not decide what an agent works on: dispatch starts an agent only on a step the process has already made ready.
  • It does not replace the ITB proposal’s test-plan and result formats; it adds the services a plan needs to test agents working through processes.

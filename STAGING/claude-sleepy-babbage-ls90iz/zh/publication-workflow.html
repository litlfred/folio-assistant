这里有多少个 BPMN 2.0 文件？本页面已不再给出数字，而这是解决之道，绝非避而不谈。

曾经作为此处开篇的那句话包含一个计数，并且接连错了五次——“六个”，接着是“十九个”，然后是“三十个”，再接着是“三十二个，全部位于 processes/ 下”，随后又是“三十九个”——每一次错误都持续了相当长时间，且每次都是由碰巧运行了 ls 的人发现的。最后一次在最终核对时差了十六个：它声称有三十九个，而实际有五十五个。

正文里的计数只是断言；派生的索引才是证据。因此，具体的数量保存在派生流程索引中，该索引由 bun run docs:auto 根据声明生成，受 CI 门禁把关，绝不会与其统计的图表发生偏差。本页面的任务则是负责无法自动生成的那一半——每个流程的用途是什么、何时会进入该流程，以及你真正需要的是哪一个相邻流程。

这种划分正是 docs-auto 技能的规则，而本页面就是其具体范例：索引说明了存在什么以及每个图表自身声明了什么；下文的一切则阐述了索引在结构上无法表达的内容。

Bootstrap 的图表是有意排除在该索引之外的，它们的不存在是一个客观事实而非遗漏。bootstrap/workflows/ 由 bootstrap/bootstrap.json 声明，而非由根目录声明，因为若在根目录声明，就会将 bootstrap 的流程重新带入根目录发布的图中——#432 特意移除了这一点，并且仍有测试对此予以保护。Bean pve3 记录了这一抉择：bootstrap 的两半要么全要，要么全不要。 因此，派生索引涵盖根目录所声明的内容，而三个 bootstrap 图表则列在下表中。

每个图表都是带有图表交换格式的真实 BPMN 2.0 文档——可在 bpmn.io、Camunda Modeler 或任何 BPMN 工具中打开它。整个文档中的 SVG 均由 bun run render:bpmn 从这些文件生成；切勿手动编辑 SVG。

在其余所有流程之前——一个人最先接触的流程，也是在尚无 folio 时唯一运行的流程。

在 2026-09-20 之前，此表曾列出 bootstrap/workflows/bootstrap.bpmn——一个根本不存在的文件，早在很久以前就已重命名为 initialize-harness.bpmn——而三个真实的图表却全未列出。一个悬空引用隐藏在一个没有任何工具扫描的目录后面，而这正是未索引检查本应捕获却未能捕获的，因为它同样看不到该目录（bean 7u3g）。

现在这些行均已修正。这些图表对工具链而言仍是不可见的，在做出决定之前有意保持如此：bootstrap/workflows/ 由 bootstrap/bootstrap.json 声明，但未由根目录声明，在根目录声明会将 bootstrap 的流程重新带入根目录发布的图中——#432 特意移除了这一点，并且仍有测试予以防护。Bean pve3 记录了这一抉择：bootstrap 的两半要么全要，要么全不要。

图表 解答的问题
bootstrap/workflows/bootstrap.bpmn 智能体被指向一个仓库，此时一无所知。这是否已经是一个实例——加载它——还是并非实例，此时它应该变成什么？唯一的输入是一个实例引用；harness 类型、知识图谱与表达风格均从该实例的声明中读取。参见 bootstrap/README.md 和提案
bootstrap/workflows/initialize-harness.bpmn 智能体被指向一个仓库，此时一无所知。bootstrap 中唯一由参与者启动（STARTS）的流程——阅读了 bootstrap/README.md 的引导智能体处于其启动事件处，没有其他起点。包含三条泳道：引导智能体、请求者和知识图谱数据存储。参见 bootstrap/README.md 和提案
bootstrap/workflows/discussion.bpmn 有两个事实在引导智能体可访问的任何文件中都找不到答案——该仓库应成为哪个 harness，以及从哪些仓库读取和向哪些仓库写入。它们是提出 harness 需求的人所持有的判断，因此任何指令主体都无法生成它们。当需要此类事实时，从 initialize-harness 内部进入，这也是 bootstrap 拥有第二个流程的原因：它是被每项任务所预设的，而非由某项任务明确指示
bootstrap/workflows/log-message.bpmn 一个子流程，绝非入口点——通过调用活动到达，从不由外部启动，这就是为什么 bootstrap 的 README 仍然可以说只有一个流程由你开始。可从任何任务中可选调用（参与者记录自己在做什么无需权限），或者由明确绘制该调用的图表强制要求；无论哪种方式都是同一个子流程，区别在于调用者是否显式绘制了它。它驻留在 bootstrap 而非 harness 中，因为 bootstrap 不能导入 harness，如果在上游定义日志记录器，那么最需要说明自己在做什么的参与者反而无法使用它
getting-started.bpmn 有人提出了“创建一个 folio”。他们指的是五件事中的哪一件，在写入任何内容之前必须满足什么条件？

它的意图网关是经过计算的，而非人工选择的：decisions/folio-intent.dmn 返回分支，而 ask 是它可以返回的结果之一——这使得该提问成为强制性的步骤，而非一种客套。参见新手入门。

与内容无关——这三个流程适用于每个 folio，外层流程通过调用活动引用内层流程，因此每个流程只需描述一次即可复用：

智能体流程——智能体如何工作，而非内容如何创作。这些流程与内容流程并行运行，而非嵌套在其中：

图表 解答的问题
crdm-requirements.bpmn 收到一个功能请求。它如何转化为达成共识的需求，由谁签批？这是外层流程；其六个阶段是下方的调用活动。参见 CRDM 方法论
crdm-issue-linking.bpmn 扫描匹配的 issue，然后关联或询问——未经 BA 许可，绝不创建 issue
crdm-needs.bpmn 阶段 1：识别利益相关者，整合需求陈述，循环往复直至得到确认
crdm-requirements-definition.bpmn 阶段 2–4：绘制当前工作流，定义需求及其影响，循环往复直至获得批准
crdm-data-model.bpmn 介于需求与签批之间：来自 BPA 和需求的实体，双向标明基数，循环往复直至 BA 确认实体且利益相关者已答复每一个基数
crdm-signoff.bpmn 阶段 5：需求转化为 bean，BA 进行签批，在 issue 上通报分支
crdm-deliver.bpmn 阶段 6：实现、审阅增量、共享 MVP、获取利益相关者意见。合并为一个阶段，因为所有三个循环均路由回实现环节
crdm-close.bpmn 利益相关者签批，BA 确认，之后才关闭——智能体绝不假定完成
diig-investment-path.bpmn 作为流程的 WHO《数字实施投资指南》：从组建团队到价值主张的九个章节，将《指南》自身在 4.5 和 8.5 节的进度检查作为网关，而非此处额外添加的门禁。第 3 章建立在 CRDM 之上，因此与上述图表并列。存放在 smart-base 中，因为领域方法属于拥有该领域的仓库

基础流程是严格的

✎ Edit TR

三个与内容无关的图表——编辑、草稿到发布、生命周期——带有 <cat-harness.processes:policy enforcement="strict"/>。workflow_gate 会拒绝它们尚未到达的步骤。三个针对特定内容类型的图表则是建议性的（advisory），因为对 Lean 证明和 FHIR profile 而言，何为充分审阅是不同的问题，应该由了解该领域的软件包来解答。

机械验证与非机械验证

✎ Edit TR

并行网关将流水线一分为二，这种划分正是其核心要旨：

  • 机械验证——机器能够自行解决的任何事项，具有可重复的判定结果：块模式与约束规则、标签前缀、语法、拼写、交叉引用与引证解析、Lean 构建与证明状态、LaTeX 编译、FHIR/SUSHI 验证、QA 维度。无需主观裁决，无需协商；要么通过，要么不通过。
  • 非机械验证——需要主观裁决的一切事项：论断是否准确、正文是否保持了 folio 的表达风格、变更是否真正表达了编辑的本意。审阅智能体处理常规情况；任何取决于临床或科学判断的事项都会升级至人类审阅者或 SME。这两个分支属于流水线的同一阶段——审阅者是人还是智能体，改变的是由谁来回答，而不是答案提交到哪里。

两个分支都必须在汇聚之前进行报告。绿色的机械运行不能成为缺少审阅的借口，干净的审阅也不能成为构建失败的理由。

工作计划——任务即 bean

✎ Edit TR

每个图表都包含一条工作计划泳道，它绝非摆设。编辑工作作为 bean（hmans/beans）在已提交版本控制的 beans/ 目录中进行跟踪，这使得它成为人类与智能体对已完成什么、接下来做什么看到相同答案的唯一场所。

工作流中的位置 工作计划发生的操作
方案达成一致 方案以 bean 的形式提供初始数据
编辑开始 在进行任何起草之前，先认领 bean（--status in-progress）
验证报告出具 将发现项追加到 bean 中
变更被提交 bean 被解决——或者保留未完成事项继续保持打开状态
审阅请求变更 每个请求作为独立的 bean 打开
版本发布交付 已交付的工作被关闭；延期的工作保持打开状态进入下一个周期

为何将其建模为泳道而非注释：

  • 它是共享状态，而非会话状态。 beans/ 已提交至版本控制，因此工作计划在恢复会话后依然存在，并且对在其他分支上工作的同胞智能体可见。智能体内存中短暂的待办清单则做不到这一点。
  • 认领是两个工作者避免领取同一事项的方式。 工作前先认领，绝不解决属于他人的 bean。
  • beans create 不是幂等的。 在创建 bean 之前，先按完全匹配的标题检查是否存在已有 bean——该防护措施及其诱发的事故记录在 todo-manager 中。
  • Beans 不是 sidecar。 机器生成的队列（QA *.qa.json、见证文件、监视器队列）保持为批量 JSON；它们绝不会转变为 bean。

dak-preprocessing

Skill id: dak-preprocessing · Package: authoring-who-smart-guidelines · Layer: smart-base, DAK kind (smart-stack-layering; smart-dak until stage D, #1767), with two steps that are not pre-processing at all — see §”Two of these are authoring, not pre-processing”.

The phase the WHO build calls DAK Preprocessing: everything that runs between checkout and publisher.jar, gated by the do_dak input and by a dak section under contentTypes in the root index.config.json (owner, 2026-10-24, bean cz17: “WHO will adopt harness file”). Every script reads and writes it through input/scripts/dak_index.py. An IG that still carries the old dak.json keeps building: the workflow reads that file into the index for that build only, with a warning (dak_index.py --adopt-legacy), until the IG moves it. Nothing is committed back.

Sourcing. Read from WorldHealthOrganization/smart-base — .github/workflows/ghbuild.yml and the scripts under input/scripts/ — on 2026-09-22, at that repository’s main. Line numbers move; step names and script names are the stable handles. Re-read before relying on a detail: the scripts are fetched at build time from SCRIPTS_BASE_URL pinned to smart-base main, so a downstream IG’s build runs whatever smart-base’s main holds that day, not whatever its own checkout holds.

The steps, and what each one accomplishes

#scriptwhat it actually does
1generate_dak_from_sushi.pywrites contentTypes.dak into index.config.json from sushi-config.yaml plus branch/repo context — only when smart.who.int.base is a dependency and the section is absent
2update_sushi_config.pyregisters pages and menu entries in sushi-config.yaml, and writes placeholder markdown — see below, this is the one that matters
3generate_dak_from_sushi.py, againre-runs step 1 with the resolved branch context, after the branch name has been sanitised
4dmn_questionnaire_generator.pyemits FHIR Questionnaire resources from the DMN decision tables
5transform_dmn.py + dmn2html.xslt + dmn.cssrenders each DMN file to HTML for inclusion in a page
6inject_translations.pysubstitutes translated strings into the diagram sources before they are rendered

Six script invocations across four named workflow steps: the first two share the step “Prepare DAK environment”, and step 3 is a deliberate second run.

What “get it into the IG index” meant — step 2, precisely

This is the step the phase mostly exists for, and it is worth stating exactly, because the vague version (“pre-processing gets things into the index so the pages render”) is what keeps the phase alive after its reason has gone.

update_sushi_config.py does four things:

  1. Scans for resources — fsh-generated/resources/ (SUSHI’s output) and input/resources/ (static JSON), collecting every ValueSet and every logical-model StructureDefinition.
  2. Writes a placeholder markdown page per resource into input/pagecontent/, as ValueSet-<id>.md and the logical-model equivalent, each carrying a <!-- DAK_API_PLACEHOLDER: … --> marker. A file that already exists with real content is left alone; the marker is how the script tells its own placeholder from an author’s page.
  3. Registers dak-api.md in sushi-config.yaml’s pages: map, creating the pages: key if the IG has none.
  4. Registers Indices → DAK API → dak-api.html in the menu: map, creating menu: and the Indices subsection if absent.

So the “index” is sushi-config.yaml’s pages: and menu: maps, and the “pages would not render” is literal: the IG Publisher’s Jekyll renders a page only if the file exists in input/pagecontent/ and the config’s pages: names it. Both halves are what step 2 supplies.

Which is why this step does not survive the transition. Under the just-the-docs pipeline the navigation is derived from sushi-config.yaml directly and the pages are folio pages — we own both maps, so writing them back into somebody else’s config to get them read again is a round trip through a tool we are removing. See ig-render-jekyll for what replaces it, and kn0t for the phasing.

Two of these are authoring, not pre-processing

Steps 4 and 5 — dmn_questionnaire_generator.py and transform_dmn.py — are not hooks around a renderer. They mint artefacts:

  • the questionnaire generator emits FHIR resources, which the Publisher then validates, indexes and publishes like any other resource. Delete the step and the IG is missing Questionnaires, not missing a page.
  • the DMN transform produces the only human-readable rendering of a decision table the IG has.

They run late because the pipeline had nowhere earlier to put them, not because they depend on anything the Publisher does. They are content generation and belong upstream of the Publisher, in the DAK document kind as authoring steps — which is how they survive the transition while step 2 does not.

transform_dmn.py has a second property worth recording: its output is HTML, which the JSON-only render contract does not take. Either it gains a structured output, or its HTML is treated as an embedded asset rather than as a representation. That is an open question, not a settled one — bean kn0t.

Step 6 is conditional on who renders

inject_translations.py rewrites diagram sources before rendering because the Publisher offers no later hook. Once pages render through just-the-docs, the locale layer already in this platform does this, and the step is redundant for pages. It is not redundant for the diagram sources themselves, which are still rasterised outside Jekyll.

Do not remove it on the strength of the page argument alone.

Steps 1 and 3 — one fact, computed twice

generate_dak_from_sushi.py runs twice, the second time “with current branch context”. That is a workaround for ordering: the branch name is sanitised by a later step than the one that first needs it.

The DAK section is ours (bean cz17), not a file we merely read, so this is a derivation we own and can compute once, in the right order. Do not reproduce the double run when lifting this step.

What a QA report already exists for

Every one of these scripts instantiates a QAReporter and writes a phase report — successes, warnings, errors, files_processed, files_expected, files_missing, plus a summary with counts and a completion timestamp. The data for the QA-report graph typology already exists and is thrown away, because nothing downstream read it.

It has somewhere to go now. The owner ruled for the evidence-led option on 2026-09-22 and qa-report/v1 is registered — schemas/qa-report.ts, graph typology qa-report, holds: "state". The shape is whatever these scripts already emit, down to upstream’s snake_case field names, because renaming them would insert a translation step between a producer we do not control and a consumer we do.

In the AST lifecycle: the overlay on fhir-harness’s refresh

Owner, 2026-10-14: “that should be in fhir-harness then smart- all use that”, and *“i want AST to be used. it should be in cache branch”. smart-base’s IG is published from the AST on its cache branch (cat/fhir-harness/fhir-ast/<package id>), like every smart-* IG. The one writer of that branch is fhir-harness’s reusable ig-ast-refresh.yml (skill ig-build-pipeline, §”The AST cache lifecycle”). The plain AST exporter does not run this phase, so smart-base supplies it as an overlay. fhir-harness never names it.

  • The command is smart-base/scripts/dak-pre-export.sh (bun run cat smart-base:dak-pre-export). It runs steps 1, 2, 4, 5 and 6 of the table above, in that order. It uses this checkout’s own input/scripts/, never a download from another repository’s main. It does not repeat step 3, as §”Steps 1 and 3” says. Steps 4–6 run only when the IG declares contentTypes.dak, as in ghbuild.yml. Any failure fails the run.
  • The caller is smart-base’s .github/workflows/ig-ast-refresh.yml: fhir-harness’s template plus pre-export: bash smart-base/scripts/dak-pre-export.sh. It runs by hand, and on every push to main that changes sushi-config.yaml, ig.ini or input/** (owner, 2026-10-14: refresh automatically when the IG source changes).
  • What the cache records. This phase rewrites the IG’s inputs: sushi-config.yaml’s pages:/menu: and placeholder pages under input/pagecontent/. fhir-harness takes the clean commit’s input digest before the command runs, puts the inputs back after the export, and records the AST against the clean commit. The prepared tree’s digest is kept under the manifest’s preExport. So the cache verifies on any clean checkout, and a merge that changes no input does not make it stale.
  • The counterpart after the export is not the Publisher’s output/ any more. It is fhir-harness’s ig-api-gen.ts, the generic port of the post-processing schema and vocabulary generators, run over the AST by ig-site:sidecars (dak-postprocessing).

ghbuild.yml is WHO’s inherited build and keeps its own copy of these steps for downstream repositories. It is not how smart-base’s cache is written.

Source of truth versus generated artefacts in a DAK repository

Owner, 2026-10-30 (litlfred/folio-assistant#222, bean l1nl): state which artefact is authoritative and which is compiled, cached or rendered output in a DAK repository, extending the base IG rule in ig-build-pipeline §”Source of truth versus compiled, cached and rendered output”.

Two authority rules govern a DAK repository:

  1. Across knowledge layers, authority flows L1 → L2 → L3 → compiled AST / rendered site (smart-guideline-end-to-end §”The order is a rule: L1, then L2, then L3”). L1 narrative guidelines and referenced tables (library/<bib>/l1-extraction/) ground L2 DAK components (business processes, decision-support logic, core data dictionary, L2 form wireframes, personas, scenarios, indicators, functional/non-functional requirements); L2 DAK components ground L3 FHIR artefacts (input/fsh/, input/cql/). Never patch an L3 artefact or a rendered page to contradict its L2 source, or an L2 table to contradict L1 without an L1 citation.
  2. Within the repository tree, hand-edit only the authored inputs — never the files written by DAK pre-processing, row generators, SUSHI, the AST refresh or DAK post-processing. Both the pre-export hook (dak-pre-export.sh) and the QA suite (qa-checkers-dak.ts isGeneratedArtefact) distinguish authored inputs from generated artefacts:

Version numbering: DAK SEMVER and how an IG’s version relates to its DAK’s

Owner, 2026-10-30 (litlfred/folio-assistant#222, bean l1nl): define the SEMVER rule for DAK and IG versions — what bumps major, minor and patch, and how an IG’s version relates to its DAK’s.

Both index.config.json contentTypes.dak.version (schemas/dak.ts DakDeclarationSchema, mirroring input/fsh/models/DAK.fsh) and sushi-config.yaml version use exact MAJOR.MINOR.PATCH semantic versioning:

IncrementWhat triggers the bump on a DAK (contentTypes.dak.version)What triggers the bump on the L3 IG (sushi-config.yaml version)
major (X+1.0.0)Breaking L2 change across the nine DAK component types (DAK.fsh): removing or incompatibly redefining a core data element (dataElement), business process (businessProcess), decision-support table (decisionSupportLogic) or clinical rule, indicator (indicator) numerator/denominator definition, persona (healthInterventions), scenario (userScenario), L2 form wireframe (form), or functional/non-functional requirement (requirement); or rebasing onto a new L1 WHO guideline edition that invalidates prior L2 logic or data elementsBreaking L3 conformance change per ig-build-pipeline §”Version numbering: SEMVER for a FHIR IG” (removing/renaming a canonical resource, tightening cardinality or bindings, incompatible CQL/operation signature change, fhirVersion change, or breaking dependency major bump), or any major bump in the DAK it encodes
minor (X.Y+1.0)Backward-compatible L2 addition: adding a new persona, scenario, BPMN workflow, DMN decision table or rule row, optional data dictionary element, L2 form wireframe, indicator or requirement; or extending an L2 value set without invalidating existing rowsBackward-compatible L3 addition (new profile, logical model, extension, ValueSet, CodeSystem, Library, PlanDefinition, Measure, Questionnaire, optional element/slice, or new narrative page), or any minor bump in the DAK it encodes
patch (X.Y.Z+1)Backward-compatible L2 editorial or bug fix: fixing typos, descriptions, labels, translations or diagram layout; correcting a DMN cell or data dictionary description to match the existing L1 source without changing data-element semantics or workflow structureBackward-compatible L3 fix (narrative prose in input/pagecontent/**, translations, example fixes, CQL/FML bug fixes preserving declared inputs/outputs and clinical intent, or rendering fixes), or any patch bump in the DAK it encodes

How an IG’s version relates to its DAK’s:

  1. Co-hosted DAK and L3 IG in one repository (contentTypes.dak + contentTypes.ig) — lockstep MAJOR.MINOR.PATCH. When a repository publishes a DAK and its L3 FHIR IG together (the standard WHO SMART Guideline repository shape), index.config.json contentTypes.dak.version and sushi-config.yaml version (plus publication-request.json version on a release) carry the same MAJOR.MINOR.PATCH version and matching status (draft | active | retired). If L2 changes by minor and L3 changes by patch, both move to the higher increment (minor); if L3 makes a breaking conformance change (major) while L2 is unchanged, both move to major so the published DAK package and its FHIR IG artifact never diverge.
    • Why both files must be updated together when bumping: step 1 (generate_dak_from_sushi.py) seeds contentTypes.dak from sushi-config.yaml only when contentTypes.dak is absent (if read_dak_section(repo_root) is not None: return). Once contentTypes.dak exists in index.config.json, editing version or status in sushi-config.yaml alone leaves contentTypes.dak.version stale. Always update sushi-config.yaml version/status and index.config.json contentTypes.dak.version/status in the same commit.
  2. Standalone L2 DAK vs downstream L3 IG (l3-fhir-authoring). When an L2 DAK (contentTypes: { dak } only) and an L3 IG (contentTypes: { ig }) live in separate repositories, each tracks its own MAJOR.MINOR.PATCH lifecycle, and a major or minor bump in the upstream L2 DAK requires at least a matching major or minor bump in the L3 IG release that adopts it.
  3. Adapted / country DAKs and IGs (l2-dependency-choice, l3-dependency-choice). A downstream or country adaptation pins the upstream WHO DAK and IG in sushi-config.yaml dependencies: (and index.config.json dependencies) at an exact released MAJOR.MINOR.PATCH version (bun run cat check:published-refs), while the adaptation’s own contentTypes.dak.version and sushi-config.yaml version track the adaptation’s own MAJOR.MINOR.PATCH release series.

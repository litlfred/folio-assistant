descriptionReport a check's verdict on one tracking issue: close the issue when the check found nothing, open or edit it when the check found something, and leave it untouched when the check could not tell. Every watch that keeps one tracking issue runs this, with its own label: ci-health-watch (`ci-health`), repository-health-watch (`repo-health`) and pr-checks-present (`pr-no-checks`). Before 2026-11-01 each of them drew these seven steps itself (shared block G2 of the BPMN guidance review, owner Q-BR-2 C). THE THIRD STATE IS THE WHOLE POINT, AND IT IS THE ONLY ONE THAT FAILS THE JOB. `unknown` runs `exit 1`; a finding does NOT. A repository in trouble leaves the watch GREEN and speaks through the tracking issue, while a sweep that could not look turns the job red. That inversion is deliberate and is invisible from the run list, which is the argument for drawing it. ONE TRACKING ISSUE, EDITED IN PLACE, never a comment and never a second issue: a feed nobody reads is the failure mode a watchdog invites. On `unknown` the issue is left UNTOUCHED: not closed, not opened, not edited. Closing it would assert the thing the sweep just failed to establish. `Ensure the tracking label exists` sits AFTER `Could we tell?` and before the split, because both issue paths need the label: the clean path filters on it too, and on a repository where nothing has ever gone wrong it would not otherwise exist. It is skipped on `unknown`, where neither path runs and a label hiccup must not be what fails the job. The verdict is the calling watch's: its check writes a report file before any exit path, exit 0 is clean, 1 is a finding, 2 is could-not-check, and an exit 1 with no report file is a crash, read as could-not-check. Each watch's own gateway documentation in its workflow says which step writes it.

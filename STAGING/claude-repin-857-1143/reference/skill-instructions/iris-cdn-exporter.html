The IRIS CDN Exporter

The exporter is an agent role plus a set of deterministic scripts. The scripts (scripts/iris-cdn/) move bytes. The agent plans, reviews and reports. It never holds the signing key and never pushes to a WHO repository.

Processes, all in processes/:

ProcessWhenWhat
iris-cdn-initial-load.bpmnonce, on the owner’s approvalevery record and every bitstream, in resumable batches
iris-cdn-nightly.bpmnevery night, 02:00 UTConly the items IRIS reports as changed
iris-cdn-reconcile.bpmnweeklycatches withdrawals, which REST does not report, and checks for drift
iris-cdn-sign-publish.bpmncalled by the three aboveBagIt bag, detached JWS (ES256), did:web key, verify

Owner’s choices (2026-10-30)

  • The initial load carries metadata and the PDFs.
  • Changes are read from the DSpace REST API only (skill iris-rest-feed).
  • Exports live on Cloudflare: a git repository on Cloudflare Artifacts (not GitHub) and R2 object storage behind the Cloudflare CDN. Cloudflare is an actor in every process.
  • GitHub Pages is a preview, never the store. litlfred/who-iris and WHO/who-iris preview the full exported site; they keep materialized only the three items held today, for testing.
  • The graph is rebuilt in full every night; sorted output keeps unchanged partitions byte-identical.
  • Keys are published as verificationMethods of a did:web DID document, whose publicKeyJwk.x5c chains to WHO’s signing DID. The key is taken as already published, and its private half is in the GitHub environment secret. No GDHCN trust list is assumed (skill iris-cdn-signing).
  • Metadata can change while the PDF does not. Records and files are diffed separately, and see iris-rest-feed for how edits are caught.

The no-churn rule

The owner’s requirement: minimise churn of content that has not changed. It holds at every step, and each step says how:

  1. Canonical records. A record is written as JSON with sorted keys, LF line endings and no fetch timestamp inside it. If the canonical bytes equal the held ones, the file is not rewritten.
  2. Content-addressed bitstreams. A bitstream is stored under its SHA-256. An object that already exists is never downloaded, uploaded or overwritten again.
  3. Sorted graph output. The graph is rebuilt in full, and N-Quads partitions are written sorted, so a partition with no changed item comes out byte-identical and is not re-uploaded.
  4. Date-free manifests. bag-info.txt has no Bagging-Date, so the tag manifest of an unchanged payload is byte-identical.
  5. An empty diff ends the run. No commit, no new signature.

A step that cannot meet its rule reports it. It never hides it.

What the agent does

  • Plan the initial load as one batch per collection, with the checkpoint in state/initial-load.json in the Cloudflare git repository.
  • Review each run report and open a bean for each anomaly: a change count far from the recent median, a quarantined bitstream, a verification whose verdict is unknown, or a partition over its size ceiling.
  • Never widen scope. Only the owner changes what is exported, its budget or where it is stored.

What the agent must not do

  • Push to any WHO/* repository.
  • Treat a short listing as a mass withdrawal (see iris-rest-feed).
  • Delete a published object. A withdrawn item is marked withdrawn, and its bytes stay addressable because a citation to them may exist.
  • Put an upstream count into prose. Counts come from the catalogue and the run reports.

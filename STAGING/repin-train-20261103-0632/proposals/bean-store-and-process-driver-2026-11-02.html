0. Context: WHO Assured AI, Gemini parity and benchmarking

This proposal is written for the concept note Gemini Integration and Benchmarking Methodology for WHO Assured AI (owner, 2026-11-02). That note asks for three things this harness must deliver, and each depends on the work below:

The concept note saysWhat it needs from the harnessWhere in this proposal
Agents are confined to BPMN swimlanes, each task backed by skills and Tools, with bounded context, to keep them on trackThe state machine, not the agent, decides the step and hands over only that step’s context§4.4, §4.5
Agents use MCP servers for tools and dataThe work plan reachable over MCP, not only through git commands a given agent may not have§4.2 (beans-mcp)
Usability parity across frontier models; guardrails replicated in GEMINI.mdA model-neutral work order an agent of any model receives, so guardrails live in the process and the work order, not in one vendor’s prompt file§4.5
Routes 0, A and B, run through Gherkin test specifications and the BPMN harness, with reasoning traces captured for the ITBOne dispatcher that can start the same case under each route and record every step, refusal and bean change as a trace§4.6, §4.7
The ITB is the testing tool (owner, 2026-11-02 19:07Z)A test harness the ITB drives: a state machine, a Beans store and a materialised knowledge graph per run, agents A, B, C… started with bean sets S_A, S_B, S_C…, end state and behaviour observed§4.8

Two facts about today matter here. GEMINI.md in each repository is five lines that point to AGENTS.md, so the guardrails an agent gets are the same text for every model, and anything Claude-specific lives in Claude’s own session configuration rather than in the process. And req:model-benchmark (cat-harness#686) already says a benchmark never writes to beans/, which a store that can only be the git branch cannot honour without care: a benchmark run needs a store of its own (§4.7).

1. The ask

Owner, 2026-11-02:

we have a bean data store as part of our processes/skills/tools. i want to make sure documentation is complete. currently we are using github repo branch as one Tool. another Tool could be using the server (there is an mcp service for example) to manage bean state. can we make sure that process documentation is independent of Tool.

we also have a bpmn state machine. i think that can use beans already as part of context for agents (if not it should be). the state machine should be able to start a agent (e.g. via API) and give a bean (which is tagged hopefully with process + task + etc.) that the agent is supposed to work on and also track process with (as they go through processes and tasks). we should be able to track the evolution of the bean over time.

look at what we have and what needs to be done

also in proposal doc, i want to integrate ITB as the testing tool for this. so it needs to spin up a bpmn state machine, a bean data store as part of test harness. then a testplan would be to start “agents A, B, C,… each with their bean sets S_A, S_B, …” and see what end state is/monitor behaviour.

we want agents to know as minimal as possible they are in a test environment. we use skills and memory.md to help set up consistent memory (based on needs for processes in test plan) across models. we layer all of them into a more singular KG (e.g. materialized within a git repo) as part of consistent context.

Four goals follow from this:

  • G1. Process and skill text says what happens to the work plan, never how one Tool does it.
  • G2. The state machine gives an agent its bean as context. Partly true today.
  • G3. The state machine can start an agent on a step, with a bean tagged by process and step. Not true today.
  • G4. A bean’s history over time can be read from the store, whatever Tool backs it. Only true for the git Tool, and only by reading git.
  • G5. (from the concept note) The same process can be run by an agent of any model, under Route 0, A or B, and the run leaves a trace that can be scored and compared.
  • G6. The ITB runs these tests: it stands up a state machine, a Beans store and one consistent context per run, starts several agents each with its own beans, and checks the end state and the behaviour on the way. The agents should not be able to tell a test run from real work.

2.3 The engine writes beans through one Tool

workflow_complete (cat-harness-tools src/tools/workflow.ts) calls applyWorkPlanOp (src/workflow/bean-link.ts), which runs the beans CLI and falls back to editing the Markdown file. That code path is the git Tool. A server-backed store could not be used without changing the engine.

2.4 Beans as agent context (G2): half there

  • TaskContext (src/workflow/instance.ts) carries carriedBeans, together with role, role stack, skills and conventions. workflow_next returns it.
  • An instance names its bean (bean, carriedBeans), but a bean does not name its instance, process or step. Nothing in the bean’s front matter says “I am at Task_RunCI of Process_CodeChangeReview”. The only way to place a bean is to scan every instance file. The beans-by-process pages do exactly that.
  • The bean’s body (what to do) is not in TaskContext: the agent gets the id and must fetch the bean through a Tool.

2.5 Starting agents (G3): exists outside the harness only

  • The harness has no step that starts an agent. arm-forced.ts (bean 502c) walks a diagram and hands one agent the enabled step, but inside one process run, as an experiment arm.
  • beans-serve already starts agents per bean. Its GraphQL API (litlfred/beans, internal/graph/schema.graphqls) has sendAgentMessage(beanId, message) (“Starts a session if none exists”), stopAgent, agentSession(beanId), agentSessionChanged and activeAgentStatuses subscriptions, and a worktree per bean. It runs the claude CLI (internal/agent/claude.go). The beans repository also has a draft bean beans-kp3h, “Wrap beans in an MCP server”, with one beans_graphql tool.
  • Other ways to start an agent: a Claude Code session or routine through its API, Gemini through Antigravity (agy; the project already hands it prompts, for example bean-drain-2026-10-31/agy-prompt-1142.md), GitHub Copilot’s assign-to-issue, a local claude -p. Each is started by hand today, with a prompt written for that model.
  • The closest thing to a benchmark driver is bean 502c’s two arms in cat-harness-tools: arm-forced.ts (the token machine hands one step at a time and refuses out-of-order steps) and arm-self-managed.ts (the agent gets the whole diagram and manages itself). They measure exactly the guardrail the concept note describes, but run one bank case in-process, not a dispatched agent of a chosen model.

2.6 History (G4): only in git, and recording stopped

  • The bean: git log on cat/cat-harness/beans. Notes in beans/notes/. No API: beans-serve has no history query.
  • The process position: each instance’s history (node, at, actor, note).
  • Recording stopped in early October. The 12 instances on the branch last moved 28 to 42 days ago (#988).

4. Proposal

4.1 The contract speaks operations, not git (N1, N9)

Rewrite work-plan-store.md as a list of operations every Tool must provide, each with its guarantee:

OperationGuarantee
get(id)the bean as last written, or “none”
list(filter)by status, type, tag, parent, process, step
create(bean)id is unique
update(id, change, ifMatch)refused when ifMatch is stale; never loses a concurrent write
note(id, text, by)appended, never rewritten
history(id)every change, oldest first: when, by whom, what, and from which process step
positions(id), beansAt(process, node)where a bean is, read from the instances (§4.4)

Archiving is a field, not an operation (ruled 2026-11-02, Q-BSD-7 B). update(id, { archived: true }, ifMatch) archives a bean. It is refused unless the bean is completed or scrapped (check:bean-archive’s invariant); get still finds an archived bean, and list leaves it out unless asked. Each Tool decides where an archived bean lives: the git Tool keeps today’s defs/archive/.

Keep the six responsibilities and phrase each against the operations. “Lose nothing to a race” becomes “update with a stale ifMatch is refused, and a retry on the fresh version lands”. How the git Tool does that (fetch, rebuild on the tip, push, never force) moves to the git Tool’s own page.

Then one conformance test suite runs against each Tool (N9). kg-audit stops reporting mechanical-role-untested once the git Tool passes it.

4.2 Tools, each with its own page (N2)

ToolBacked byStatus
beans-git-branchthe cat/<harness>/beans branch, branch-store.ts, beans CLI or manual edittoday’s behaviour, renamed and documented as one Tool
beans-serverbeans-serve GraphQL (ifMatch already exists on mutations)proposed
beans-mcpan MCP server, for example beans-kp3h’s single beans_graphql tool, or harness MCP tools over the same operationsproposed

The git commands in the 7 skills move into beans-git-branch’s page. Each skill line becomes the operation (“note the bean”, “claim it”), with a link to the Tool pages. A check, check:store-tool-neutral, refuses git or branch terms in a skill whose Role is work-plan unless the line sits in a Tool page. The skill already has a precedent in selection.when.

4.3 The engine calls the store, not the CLI (N3)

Put a WorkPlanStore interface in cat-harness-tools with the operations of §4.1, and make applyWorkPlanOp call it. The git Tool is its first adapter (today’s code, moved). The adapter in use comes from the deployment (deployment-descriptions.md), the same way other Tools are chosen (ruled 2026-11-02, Q-BSD-2 A). This fits the platform-boundary rule: different code, so an adapter.

4.4 Where a bean is: read from the instances (N5, N6)

Ruled 2026-11-02, Q-BSD-1 B: instances only. A bean’s position lives only in the workflow instances that name it; the bean file gets no position field, so there is one source of truth and nothing to keep in sync.

The work-plan store already holds workflow-state beside bean-defs, so the lookup is a store operation, not a scan each caller writes:

OperationReturns
positions(beanId)every instance naming the bean: process, node(s), status, last move
beansAt(process, node?)the beans with a token at that step

The git Tool answers both by reading beans/workflows/ (what the beans-by-process pages already do, cat-harness-tools#1414); a server Tool can index them. Process and step tags on the bean (process:code-change-review) stay optional labels for people, never the position.

TaskContext gains the bean itself (title, status, body, links, position), read through get, not just its id.

4.5 The state machine can start an agent (N7, N8)

Add a global task Task_DispatchAgent to processes/global-tasks.bpmn. When an enabled step’s lane binds an agent Role, the engine (or a watcher) hands a work order to an agent-launch Tool:

FieldFrom
beanget(bean), with positions(bean)
instance, nodethe token
role, skills, conventionsTaskContext
storewhich work-plan Tool to use, and how to reach it
report“call workflow_complete on this instance and node when done”

The work order is model-neutral: plain data plus the skill texts, the same for every model. Model-specific wording (how Claude or Gemini is best told to stay on the step) is the launch Tool’s job, kept on that Tool’s page and tested, so parity is something a test can check rather than a prompt someone remembers to copy into GEMINI.md.

Candidate agent-launch Tools, each a Tool page with selection, like the store Tools:

launch-claude-sessionClaude, cloud session or routine through its APIthe API exists; no harness Tool

The agent moves the token with workflow_complete, which writes the instance history (so positions moves with it) and notes the bean (§4.6). The diagram draws dispatch as a step, so whoever reads the process sees where agents start. #988’s rule (“an agent working a bean through a process starts or advances an instance”) becomes a property of the engine, not a habit.

4.6 One event log, readable from any store (N4)

Every store change is an event: created, status-changed, claimed, noted, step-reached, dispatched, completed, each with at, by, and, when it came from the engine, instance and node. history(id) returns them in order.

  • The git Tool builds history from git log on the bean file plus the instance histories, so nothing is migrated (ruled 2026-11-02, Q-BSD-4 A).
  • A server Tool keeps the events as rows.

The beans-by-process pages then gain a timeline per bean (bean-processed/<bean>/ from cat-harness-tools#1414), from history(id).

4.7 Benchmark runs: routes, isolated stores, traces (N10, N11, N12)

With §4.1 to §4.6 in place, a benchmark run is the same dispatch with three settings, and no new runner:

SettingValues
system under testmodel + launch Tool + configuration (the req:model-benchmark notion)
route0 the case text only, no work order, no skills, no graph · A work order with skills, graph Tools withheld · B work order with skills and the knowledge-graph Tools
storea run-scoped store Tool (in memory, or a scratch branch per run), seeded from the case, never the real work plan (ruled 2026-11-02, Q-BSD-5 A)
  • Cases. A Gherkin scenario from the test plan becomes a seeded bean and a started instance in the run’s store. The Given seeds the store, the When is the dispatched step, the Then is checked against the store and the instance after the agent finishes.
  • Trace. history(id) on the run’s store, the instance history and its refusals (each refused out-of-order step or hand-asserted gateway) are the run’s trace, in one shape whatever the model. That is the reasoning trace the concept note wants handed to the ITB, and bean 502c’s refusal counts become a metric of every run, not of one experiment.
  • Isolation. The run-scoped store is what lets a benchmark honour “never writes to beans/” while still exercising every bean step.
  • Results land where benchmarking-mode says (build/benchmarks/, reports/), never in a declared graph.

4.8 The ITB as the test harness (N13, N14)

The ITB drives the run (ruled 2026-11-02, Q-BSD-6 A). It uses GITB, through OpenTestBed Gherkin as already ruled (D4 = I1 in the ITB proposal), and orchestrates the test. The harness gives it a small set of services, each a Tool, so a test step is a call and not a script:

ServiceDoes
harness-upstands up one test harness: a BPMN state machine, a run-scoped Beans store (§4.7) and the run’s materialised context (below), and returns its handle
seedwrites beans, notes and started instances into that store
start-agentsdispatches agents through the launch Tools (§4.5), each with its model, route and bean set
observestreams the run’s events (history, instance moves, refusals, dispatches) while it runs
statethe store and the instances at a moment: the end state a Then is checked against
harness-downexports the trace and removes the run’s store

A test plan in these terms. A Gherkin feature reads like a scenario of work, not of tests:

Feature: two agents share a merge window
  Background:
    Given a harness with processes "code-change-review" and "merge-train"
    And the context "folio-assistant@<hash>"
  Scenario: A opens changes, B lands them
    Given agent A (gemini, route B) holds beans S_A = {a1, a2}
    And agent B (claude, route B) holds beans S_B = {b1}
    When the agents are started
    Then within 2 hours every bean in S_A is completed
    And bean b1 is at "merge-train" step "End_Landed"
    And no instance recorded a refused step

Given seeds the store and the agents’ bean sets, When dispatches, and Then is checked against state and observe. The ITB keeps its own role of running the plan and judging the result; the TAR comes back as a folio-test-run/v1, as the ITB proposal already describes.

Agents should not know they are in a test. What an agent sees is the same as in real work:

  • the same work order (§4.5), the same store operations, the same skills;
  • beans written as real work items, never titled or tagged as tests;
  • the run’s identity (run id, plan, route, model) kept in the harness, never in the work order, the bean or the context;
  • the store reached through the same Tool interface as production; only the deployment description behind it differs (Q-BSD-2 A).

What cannot be hidden (an empty repository history, a fresh store) is listed on the test plan as a known difference, so a result can be read with it in mind.

One consistent context, materialised. Each run gets one git repository built from layers, the same for every model in the run:

LayerFrom
the knowledge graphL1, L2, L3 content and the harness layers the processes need, as a composed checkout pins them today (index.lock.json)
skillsthe skills the test plan’s processes name, closed over their roles
memorya MEMORY.md per role, generated from the memory graph (agent-memory) and filtered to the plan’s processes, so each model starts with the same memories
entry filesAGENTS.md, with CLAUDE.md and GEMINI.md pointing to it as they do today, so no model gets guidance the others lack

The repository is pinned by its commit hash, and the hash is the context named in the plan’s Background. Two runs with the same hash gave their agents the same world, which is what makes a comparison across models fair. Route 0 runs get an empty context; Route A gets skills and memory without the knowledge-graph layer; Route B gets all of it.

4.9 A live store on localhost

Owner, 2026-11-03: “for mcp server, this will only work i think on localhost (or hosted like hetzner which we dont have) deployments. do localhost setup.”

The constraint. The published site is static (GitHub Pages). It can show what the store held when the site was built, and nothing newer: a page there cannot reach a beans server or an MCP service, because none runs where Pages runs. A store server is reachable only from a machine that runs one, which today is the developer’s own (localhost). A hosted server (Hetzner or similar) would make it reachable from anywhere, but there is none, so it is out of scope here and noted under “Later”.

The setup. Every piece below already exists except the one route:

PieceWhatWhere
The harness serverbun run cat-harness-tools/src/server.ts (or the MCP server image); MCP at http://localhost:8080/mcp, viewer at http://localhost:3200/cat-harness-tools, exists
The deploymentCAT_DEPLOYMENT=developer names scenarios/deployments/developer.json, whose stores names the work-plan Tool (§4.3). Unset means the git branch on its mountcat-harness + tools#1424
The read routeGET /api/work-plan/beans-processed returns the same rows the all-beans page embeds, read through the store’s operations, so it answers from whichever Tool the deployment namescat-harness-tools#1429
The pagebeans-processed/ keeps its embedded rows and, every 5 s, asks the route for fresh ones; it re-renders only when the answer changed. Only on a page opened from localhost: on GitHub Pages there is nothing to refresh from, so there is no control (owner, 2026-11-03)cat-harness-tools#1429

How a reader turns it on:

  1. Start the harness server in the checkout: CAT_DEPLOYMENT=developer bun run cat-harness-tools/src/server.ts.
  2. Open the all-beans page from this machine (a local preview of the site, or the harness server). The page polls its own origin, then the MCP server’s default port (8080).
  3. The page shows Live with the store Tool and the time of the last answer. With no server it shows Live updates off: no local store server answered, and keeps the built rows. It never shows an empty plan because a request failed.

Security, because the route is a door into the work plan:

  • The server binds to 127.0.0.1 only. A deployment that wants it on a network must say so in its description, and that is the hosted case under “Later”.
  • The route is read-only: no store operation that writes is reachable from it.
  • CORS allows a localhost origin only, not *. The server allows * today for its other routes; this route does not inherit that. The published site never calls it.
  • No credential travels to the page: the server reads the store with the checkout’s own access, and the page receives rows only.

The MCP service Tool (beans-mcp, §4.2, proposed) would sit on the same server: MCP tools that are the store operations (proposed names work_plan_get, work_plan_list, work_plan_positions, work_plan_history), for agents. None of them exists yet. The page uses the plain HTTP route rather than MCP, because a browser polling every 5 s needs one cheap GET, not an MCP session.

Later (not now): the same server hosted (for example on Hetzner), with authentication in front of the route and its address in the deployment description. Nothing on the page changes except the address it polls.

The one proposed field: launch on a placement. A placement says where an actor runs; for an agent actor it must also say which model and which launch Tool (§4.5) starts it. Proposed shape, following Q-BSD-2 A (the deployment chooses Tools):

{
  "actor": "agent-gemini",
  "host": "vendor-cloud",
  "compute": "vendor-cloud",
  "toolSurface": "mcp",
  "modelProvenance": "hosted",
  "launch": { "tool": "launch-antigravity", "model": "gemini-<version>" },

}

launch.tool names a launch Tool by id, as stores names a store Tool, and an id this toolset lacks is refused, never replaced. launch.model is passed to the Tool as given. The test plan names agents by actor id, so a plan never names a model: changing the model is a one-line change to the deployment, and the same plan then compares models fairly.

The run, end to end:

  1. CAT_DEPLOYMENT=itb-benchmark is set where the harness runs.
  2. The ITB calls harness-up (§4.8): a state machine, a run-scoped store (because stores says so), and the materialised context the plan pins.
  3. The plan’s Given steps call seed: beans and started instances in the run’s store, never the real work plan.
  4. When the agents are started calls start-agents: for each agent in the plan, its placement’s launch names the Tool and model; the work order is the same for both (§4.5).
  5. The agents move through the processes with workflow_complete; observe streams history, instance moves and refusals; on localhost the all-beans page shows the run live (§4.9).
  6. Then steps check state; harness-down exports the trace and removes the run’s store. The TAR comes back as folio-test-run/v1.

What each model needs from outside the harness, named in the deployment and supplied by whoever runs it: Claude, a claude CLI and its login on the machine launch-beans-serve runs on; Gemini, the GCP project and Workload Identity named by the concept note, reached by launch-antigravity.

6. What this does not do

  • It does not move beans off the git branch. The git Tool stays the default.
  • It does not change the diagrams’ meaning. The diagrams are already Tool-neutral; #972’s Beans store links stay.
  • It does not decide what an agent works on. Dispatch starts an agent on a step that the process has already enabled.
  • It does not replace the ITB proposal’s model (test-plan/v1, folio-test-run/v1, system/v1); §4.8 adds the services a plan needs to test agents working through processes.

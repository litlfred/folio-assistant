terminology-coding — declared by smart-base — source held

Applies when. Classifying and coding L1 narrative content (guideline recommendations, implementation practices, remarks) and L2 Digital Adaptation Kit (DAK) artefacts (personas, user scenarios, business processes, data-dictionary elements, decision-table concepts and indicators) against authoritative vocabularies and local code lists. Reach for it whenever a slot requires a code or SKOS concept (condition, intervention, persona/role, medicine, guideline domain, business process, or GRADE rating), or when deciding whether to reuse an existing term, fall back to a generic base concept, or propose a local glossary candidate. It does NOT grade evidence (that is grade), does NOT model BPMN/DMN control flow (crdm), and does NOT plan programme investment (diig).

Origin. World Health Organization, SMART Guidelines: Digital Adaptation Kits (DAKs) (Mehl et al., BMJ Global Health 2021;6:e004908, ingested at smart-base/library/mehl-2021-who-smart-guidelines/); Classification of digital health interventions, services and applications in health (CDISAH) v2.0 (WHO, 2023, ISBN 978-92-4-008194-9, ingested at who-iris/library/9789240081949-eng/, superseding CDHI v1.0 at who-iris/library/who-rhr-1806-eng/); Digital transformation handbook for health supply chain architecture (WHO, 2024, ISBN 978-92-4-010119-7, ingested at who-iris/library/9789240101197-eng/); and Digital transformation handbook for health product catalogue (WHO, 2025, ISBN 978-92-4-011619-1, ingested at who-iris/library/9789240116191-eng/).

Node file: terminology-coding.md

WHO SMART Guidelines Terminology Classification and Reuse-First Coding

Adopted into smart-base (bean folio-assistant-4nfs) as the methodological foundation for classify-and-code-content, recommendation-extraction, and recommendation-scenarios. It bridges the platform’s generic ontology and glossary rules — ontologist, glossary-terms, vocabulary-authority, and code-lists — with the WHO Family of International Classifications (WHO-FIC) and SMART Guidelines DAK component conventions.

1. The scheme for each slot

Every classifiable slot in an L1 extraction or L2 DAK component has an authoritative primary scheme and a local fallback or code list. Coding a slot means resolving a concept in the scheme designated for that slot, never picking an arbitrary string or borrowing a code from an unrelated axis.

2. The reuse-first precedence (kvd2 decision D4)

When classifying and coding any slot, an agent or terminologist walks the four-rung reuse-first ladder and stops at the first rung that yields an exact or well-scoped match:

  1. Rung 1 — Target guide’s own declared vocabulary (exactMatch in guide). Check the target guide’s own personas (personas.md), business processes (business-processes.md), data dictionary (C5), and local code lists first. If the target guide already defines the persona, process, or code and its scope covers the statement, reuse its identifier verbatim.
  2. Rung 2 — Layer base vocabulary (smart-base generic personas, FSH CodeSystems, and shared code lists). When the target guide does not declare the concept (or its description is narrower than the statement’s need — e.g. an immunization guide’s health worker cannot be stretched to cover inpatient clinical management), consult smart-base’s shared vocabularies:
    • smart-base generic personas (DAK.Persona.* in input/fsh/actors/, extracted in smart-base-generic-personas.json);
    • smart-base FSH CodeSystems (ISCO08, CDHIv2, CDHIv1, CDSCv2, CDSCv1, KGTerminologySystem and KG*);
    • shared folio-code-list/v1 lists (smart-base/code-lists/*.json, folio-assistant-core/code-lists/*.json) and SKOS glossaries (folio-assistant-core/glossary/guideline-domain.glossary.json).
  3. Rung 3 — External authoritative standard (WHO-FIC / ILO / HL7 / W3C). When the concept is a standard clinical, occupational, or ontological term not yet materialised in Rungs 1–2, resolve it against the external authority in vocabulary-authority and §1 above (ICD-11, ICHI, CDHI, ISCO-08, ATC, SNOMED CT, LOINC), recording the mapping predicate (skos:exactMatch or skos:closeMatch) per ontologist.
  4. Rung 4 — Local candidate or explicit third state (citing glossary-terms). When Rungs 1–3 hold no match:
    • For a persona or domain concept: mint a local glossary entry in <instance>/glossary/<scheme>.glossary.json following glossary-terms with status: "candidate", source: "extracted" (citing the doc_id and section / quote), and emit a WARNING persona-glossary-candidate (or term candidate warning). An agent may only write status: "candidate"; promoting to status: "authored" requires human review in the terminologist/ontologist lane.
    • For a business process: never invent a process. Record could-not-determine with WARNING process-not-determined and the basis quoting the statement. That warning is the work list for the guide or domain process catalogue (bean 2ipj).

3. Provenance and review status on every coding

Every classification or coding link records two orthogonal facts:

  1. How the coding was obtained (source):
    • declared — a person acting in an authorised role explicitly stated the code or link (must carry by);
    • context — the printed section heading, table header, or structural container in the source document settles the classification without inference;
    • inferred — an agent or author read the statement text and matched it against the scheme’s definitions.
  2. Where it sits in review (status):
    • candidate — proposed by the authoring-agent (using terminology-lookup and classify-and-code-content);
    • reviewed / authored — checked and signed off by a person acting in the terminologist (or l1-extraction-reviewer) role in classify-and-code-content.bpmn.

4. Adjudicating L1 coverage exclusions (l1-extraction-reviewer)

When l1-recommendation-candidates scans an L1 source, every sentence carrying a normative marker (should, shall, must, recommend*, may be …) must either become an L1 node (recommendation, implementation-practice, remark, or part-of) or be excluded with one of the five closed reasons (background-fact, manufacturer-statement, editorial, research-question, duplicate-of:<id>).

Per owner ruling 3b (2026-10-12), an agent may propose an exclusion in exclusions.proposed.json ("signerRole": {"role": "l1-extraction-reviewer"}), and never signs it. A person acting as l1-extraction-reviewer reviews each proposed exclusion in classify-and-code-content.bpmn by reading the candidate sentence in place on the printed page (sections/page-NNN.md), verifying that the sentence is genuinely non-normative under the stated reason, and either signing it (signedOffBy) or rejecting it back to the extraction curation so no guidance is silently dropped.

5. Refusals

  • Never invent a business process to make coverage look complete. When no process in the target guide or a published domain catalogue realises a scenario, the only valid value is could-not-determine with a warning.
  • Never stretch a narrower code as exactMatch. If a guide’s persona or a code list entry covers only part of the concept, use skos:closeMatch (or skos:broadMatch / skos:narrowMatch per ontologist) or fall through to the next rung.
  • Never self-approve a candidate term or an L1 exclusion. An agent writes status: "candidate" on glossary terms and leaves signedOffBy absent on exclusions; only a person in the reviewer lane records sign-off.

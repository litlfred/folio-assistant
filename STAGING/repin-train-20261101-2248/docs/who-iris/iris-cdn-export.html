IRIS CDN Exporter: processes

How WHO IRIS gets from its DSpace server to a signed, versioned copy on Cloudflare: one initial load, then a nightly change ingest, a weekly reconciliation, and one signed release per run. Issue litlfred/who-iris#100.

The diagrams below are rendered from the BPMN files in processes/. The BPMN files are the source of truth, and each step names the skill that carries it out. Where the infrastructure runs and where the keys live is covered in deployment.

1. Initial load

processes/iris-cdn-initial-load.bpmn. The load runs in batches of one collection each. After every batch it commits a checkpoint, so a stopped load resumes where it left off. Bytes that fail the IRIS checksum are quarantined, not published.

2. Nightly change ingest

processes/iris-cdn-nightly.bpmn. The pipeline lists the items IRIS changed since the cursor, fetches only those, and rebuilds the graph. If nothing changed, it publishes nothing and makes no commit. The cursor moves forward only after the release verifies.

3. Weekly reconciliation

processes/iris-cdn-reconcile.bpmn. REST does not report deletions, so once a week every item ID is compared with what the library holds. If more than 1% of held items are missing, the listing is treated as faulty and nothing is marked. Withdrawn items are marked as withdrawn and their bytes stay addressable.

4. Sign and publish (called by all three)

processes/iris-cdn-sign-publish.bpmn. Each changed library item gets a detached JWS (RFC 7515 Appendix F, ES256) over its own manifest. The release is a BagIt bag (RFC 8493) whose tag manifest pins every item manifest and signature, and the tag manifest is signed once. Payload objects go to R2 first. The tag files and the signature are committed to Cloudflare git last, in one commit. A release that does not verify is reverted, and the previous release stays served.

The signing key

Given, not modelled here. The subordinate signing key is already published in a DID document, with publicKeyJwk.x5c chaining to WHO's signing DID, and its private JWK is already in the GitHub environment secret IRIS_CDN_SIGNING_JWK. How that key was created and certified happens offline and outside these processes (owner, 2026-10-30). The exporter only uses the key.

When metadata changes and the PDF does not

A record and its files are stored and diffed separately. A Dublin Core edit produces a new record, and therefore a new digest, while the PDF keeps its digest and is not fetched again. Renamed communities and collections are caught by re-reading them nightly. Edits that do not move lastModified are caught by the weekly metadata hash check. See the skill iris-rest-feed.

How churn is kept to a minimum

  1. Records are canonical JSON: sorted keys, LF line endings, no fetch time inside. An unchanged record is not rewritten.
  2. Bitstreams are named by SHA-256. A byte that is already stored is never fetched, uploaded or overwritten again.
  3. The graph is rebuilt in full, but its N-Quads are written sorted. A partition with no changed item comes out byte-identical and is not re-uploaded.
  4. bag-info.txt carries no date, so an unchanged payload has an identical tag manifest and needs no new signature.
  5. An empty diff ends the run: no commit and no signature.

The platform processes these call are in cat-harness: processes/kg/nquads-distribution.bpmn (graph partitions), processes/kg/named-query-execution.bpmn (prepared SPARQL) and processes/kg/kg-to-portal.bpmn (the general select, package, sign, distribute and verify pattern).

Still open

  • CDN and DID domain. The proposal is a stable domain the owner adds to Cloudflare.
  • Live endpoint shapes (confirmed 2026-10-31, #104). Probed against live https://iris.who.int/server/api: sort=lastModified,DESC returns HTTP 422 because IRIS's default Discovery configuration exposes only score, dc.title, dc.date.issued, dc.date.accessioned and dc.date.available. rest-feed.ts therefore queries query=lastModified:[<UTC-ISO-Z> TO *]&sort=dc.date.accessioned,DESC (with +00:00 normalised to Z), scope=<collectionUuid> for initial-load batches, and embed=bundles/bitstreams&embed=owningCollection for items.

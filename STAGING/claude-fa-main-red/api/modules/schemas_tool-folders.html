    Module schemas/tool-folders

    One Tool per folder: <tools dir>/<id>/<id>.ts, and the loader that reads them.

    Bean tdir. The owner, 2026-10-15, asked why the tools were not each in their own folder, as a content layer's DAK-extraction tool already is — and, on how: "make sure the Tool schema is used and conventions of dirname and declaration like <tool>/<tool>.ts are followed. dont externalize the json on main, only when rendered in gh-pages."

    The convention, held here rather than in prose

    rulerefused with
    every folder in the tools directory is one Toola folder with no <folder>/<folder>.ts
    the folder, the file stem and the Tool's id are one stringa Tool whose id differs from its folder
    the file default-exports a ToolFactorya module with no default export, or one that is not a function
    what it returns is a Tool nodedefineTool's own parse, which the factory calls

    The source stays TypeScript, so a malformed Tool still fails at tsc and in the editor (the carrier decision, tool.ts). The JSON-LD of each Tool and the JSON Schema of each of its types are RENDERINGS, written when the site is published, never committed beside the source.

    Why a factory, not a constant

    A Tool's I/O type IRIs are minted against the publication base at load (toolTypeIri), so relocating the base edits no Tool. A constant would have to know the base when its module is first evaluated; a factory is handed it.

    Why require, synchronously

    tools() is synchronous and every consumer calls it that way (cat-harness-tools/tools/discover.ts). The module path is a variable read from the directory, so it adds no import edge (repo-partition counts only a literal specifier), which is the same reason discovery itself is safe.

指南中的推荐意见如何获取其证据——由谁检索、去何处检索，以及是什么让一个来源具有权威性（authoritative）而不仅仅是被引用。

草案原型（STRAWPERSON）。 下方的流程形态是真实的，能够正常渲染并通过工作流策略关卡。此处特意未予确定的事项包括：哪些注册库（registries）算作受信任的、folio 声明哪种分级系统，以及观察台（observatory）API 如何绑定。具体需求由一个单独的流程进行细化；设立本草案是为了提供可供细化的具体载体。

为什么这是编辑的一个子流程

✎ Edit TR

它在编辑循环内部运行，位于认领 bean 与起草变更之间——参见编辑与 HCI 验证关卡。处于这一位置正是其核心要义所在：证据是在撰写语句之前收集的，而不是在事后拼凑以支持该语句。

先起草推荐意见、后寻找证据的做法，不过是为了寻求证实的文献检索。而正是步骤的先后顺序使其避免沦为这种做法。

它是一个调用活动（call activity），因此拥有自己的文件、自己的泳道以及自己的流程图，从而使编辑流程图保持清晰易读。对于不包含任何推荐意见的内容（例如数学 folio 中没有任何推荐意见），它也无需执行任何操作，在此类情况下直接跳过，而非流于形式地空泛满足。

子流程

✎ Edit

划分为四个泳道，是因为涉及四种不同类型的参与者，而将它们混为一谈正是问责机制失效的根源：

泳道参与者职责归属
作者 / 指南制定者人工PICO、评价、分级
证据智能体系统跨三类来源的检索
受信任的注册库与观察台外部引用能否解析
工作计划 — beans共享每一个缺口与每一条未验证的引用

第三个泳道特意设为外部。权威性不是 folio 自身能够声称的属性；它是在发布机构处解析确立的事实。如果将该泳道画在系统边界之内，就会使“权威性”沦为一种自我评估。

第一步是向内审视

✎ Edit TR

第一步是向内审视，而非向外寻找。

在进行任何检索之前，作者应先阅读文档、DAK 或 IG 对该问题已有的表述。同一制品中与同级推荐意见相冲突的新推荐意见是一种缺陷，任何外部证据都无法揭示这一点——即使来源无懈可击，指南本身依然可能自相矛盾、条理不清。

这无疑也是成本最低的一步，却最常被跳过。

将问题构建为 PICO

✎ Edit TR

研究人群（Population）、干预措施（Intervention）、对照（Comparator）、结局（Outcome）。

在开展任何检索之前，WHO 指南制定都以这种方式表述问题，其原因在于可审计性而非走过场：没有 PICO，“我们寻找了证据”就不是任何人都能够核验的声明。而有了 PICO，检索便具有可重现性——另一位读者也可以运行相同的检索，并确认是否能获得相同的证据体。

PICO 会保留在推荐意见上，而不是在检索结束后就被丢弃。后来的读者正是据此判断新的证据是与本条推荐意见相关，还是针对另一条不同的推荐意见。

三类证据，而非单一类别

✎ Edit TR

检索扇出至三个不可互换的类别，而将它们区分开来正是并行网关的用意所在：

受信任的来源 — L1。 library/ 下已摄入的原始文献：sections/*.md 目录树，以及扫描文档对应的 ocr/page-NNN.txt。

已知盲点。 经过 OCR 处理但从未通过 pdf-structure.py 重新运行的文档在 sections/ 中只有一个存根（stub），因此仅针对 sections 的检索会完全漏掉它。实测数据：26 个 library/*/ocr/ 树，而记录 "text_source": "ocr" 的 structure.json 仅有 11 个。参见文档摄入。

受信任的内容 — L2 DAK、L3 IG。 已经过裁定的指南：L2 的 WHO SMART 数字化适应包（DAK），以及 L3 的 FHIR 实施指南（IG）。在已发布的 DAK 中采用的推荐意见属于另一种不同类型的证据，不同于一手原始研究——它是一项先验决定（prior decision），拥有其自身的溯源与分级——且必须作为此类决定予以引用。将其洗白包装为一手证据，正是这一区分旨在防止的失效模式。

数据存储库与统计数据集。 指标序列和微观数据。这一点同样截然不同，因为证据的单元是附加了人群、时期和方法的测量值（measurement）——而非散文形式的陈述声明。

验证权威性，而非自称权威

✎ Edit TR

每个候选证据都会对照发布它的机构的标准 API 进行解析，使得“权威性”成为一项解析确立的事实，而非引用中的主观断言。具体检查四项内容：

  1. 标识符在发布机构处能够成功解析；
  2. 检索到的记录与引用所声明的内容相符；
  3. 版本和日期与所引用的相一致；
  4. 发布机构已被当前 folio 声明为受信任。

检查项 2 能够捕获真正的错误。一个引用可能完全可以成功解析，但其内容却根本不支持引用它的那句话。

无法解析的引用既不会被丢弃，也不会被默不作声地保留。它会转化为一个 bean，以便在工作计划中显式暴露这一缺口，而不是作为无人重新核对的脚注苟存下来。

此处特意未予确定的事项：注册库列表、端点以及存储的权威记录的数据结构（shape）。由于此容器没有出站网络，因此在“发布机构自身 API”层级之下的具体端点均未经验证，列举具体端点无异于胡乱猜测。这是一个需求问题，会有单独的流程来处理它。

对证据体进行分级并记录缺口

✎ Edit TR

等级附着于针对单个 PICO 问题的证据体（body of evidence）之上——这正是评价环节位于汇聚之后而非扇出内部的原因。单个引用不承载确定性评级；回答某个问题的整个证据体才承载评级。

随后是一个网关：这是否足以形成一条推荐意见？

证据不足本身就是一项成果。它被记录为指南可以诚实陈述的缺口——“现有证据在此不支持形成推荐意见”——而不是通过不断削弱推荐意见的措辞，直到现有证据刚好能够支持它为止来敷衍闭环。这种妥协手段随时可用，但永远是错误的，这也是为什么“否”分支有明确去向的原因。

在“是”分支上，PICO、完成分级的证据体，以及每条带有已解析权威记录的已验证引用，都会写入推荐意见块。读者随后便可沿着这条链条，从最终语句一路回溯至原始来源。

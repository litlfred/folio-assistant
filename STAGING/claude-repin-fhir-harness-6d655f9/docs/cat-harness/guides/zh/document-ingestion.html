uploads/ 与 library/ 是同一流水线的两个阶段

✎ Edit TR

它们并不是同一个目录冠以两个名称，两者的区分具有关键的承重作用（load-bearing）：

uploads/library/<bib-slug>/
所存内容放入时的原始文件已摄取、已结构化、已描述
阶段传入队列L1 来源内容
是否可通过语料库检查清单 grep否是

最后一行正是消耗会话成本的地方。语料库 grep 检查清单仅搜索 library/ —— 因此，仍然留在 uploads/ 中的论文不仅没有被阅读，而且在源文件明明静躺在磁盘上时，还会使没有任何匹配的 grep 结果被误读为“没有任何人做过这项工作”。未摄取的来源比不存在的来源更糟糕，因为它产生的是盲目自信，而不是暴露出缺口。

library/ 即 L1

✎ Edit TR

library/ 下的任何内容都是 L1 来源内容。对来源的任何知识图谱引用 —— 无论来自论文、L2 DAK、L3 IG 还是任何其他制品 —— 都通过 library/ 进行解析，绝不会解析至游离路径或裸 URL。

书目条目可以指向远程资产，而非本地二进制文件。该条目存放在同级的 assets[] 字段中，包含 kind / role / url-or-path / checksum / retrieved —— 而不是在 library: 内部，因为每次同步时 LibraryRef 都会根据目录树重新生成，放置在其中的手动编写的 URL 会被静默丢弃。

流水线

✎ Edit TR

打开 BPMN 源文件

该图中有四点值得仔细阅读。

摄取引擎是一个参与者，而非脚本。 它以无人值守方式运行。在编辑会话期间放入文件会在后台触发摄取 —— 贡献者无需等待它，编辑流中的任何部分都不会被其阻塞。

失败分支是一个 bean，而非一行日志。 当完整性关卡发现缺少衍生制品时，引擎会打开一个 bean，且该文档保留在 uploads/ 中。它不会半摄取地落入 library/ 并显得像是已经完成了一样。

每个子流程都是独立的文件，使用 bpmn:callActivity 进行调用，并使用 bpmn:import 进行声明。在 bpmn.io 中单独打开其中的任何一个；父流程因未内联它们而保持良好的可读性。

终点即是创作的起点。 “可作为 L1 来源进行引用”是向发布工作流的交接点 —— 也就是作者进行编辑和审阅者进行审阅的同一个语料库。

提取结构

✎ Edit TR

打开 BPMN 源文件

需要特别了解的是 OCR 分支。以这种方式摄取的文档将其文本保留在 ocr/page-*.txt 中，而在 sections/ 中只有一个存根（stub） —— 因此已文档化的 sections/ grep 根本无法看到其中的数学内容。这种不对称性正是语料库 grep 检查清单设立第四层的原因，也是为什么干净的 sections/ grep 结果并不是表明库中缺少某个主题的证据。

每个章节文件的前置元数据中都带有文档简介。这就是上下文检索：孤立的代码块/文本块会失去其意义所在，因此这样可以在无需打开任何其他内容的情况下解释匹配结果。

衍生内容

✎ Edit TR

打开 BPMN 源文件

该子流程大部分尚未构建。 其中的每项任务都处于跟踪状态；参见下表。无论如何它都已完整绘制，因为流水线的形态正是正在商定的内容，而仅展示现有内容的图表无法用于决定要构建什么。

容易被跳过且事后补救成本高昂的步骤是最后一步。生成的描述是某人的主张，而非文件本身的属性。记录是由人类还是智能体编写 —— 对于智能体而言还包括具体的模型版本 —— 能让读者评估其分量，并使得在后续查找被淘汰模型的整套描述成为可能。一旦遗失便无法恢复。

摄取主题

✎ Edit QA TR

打开 BPMN 源文件

仅有部分来源属于主题，且由人工来决定哪些属于主题。 在内容完成衍生后，网关 是否为主题来源？ 会询问正在执行摄取的人员：该文档是否还带有主题 —— 即提供主题服务的已部署站点，或是声明主题的风格指南。这里特意没有设计用于计算得出答案的规则。带有品牌特性的文档是否属于主题来源是一种创作判断，所有者针对 bean j66n 作出了这一定夺。不属于主题的来源将直接跳至构建知识图谱。

该决定位于网关处，而非子流程内部，因为“这不是主题”与“该主题格式有误”是两种不同的结果。前者属于正常情况；后者属于缺陷，子流程会通过拒绝处理来进行报告。

在子流程内部，两类来源仅在一个步骤上有所不同：部署站点提供服务的样式表会读取其属性声明，而指南明确声明的规则则按其书写原样读取。在此之后，各路径汇聚：

  • 将各值映射到共享调色板角色；
  • 将源材料中的矛盾记录为数据，绝不通过擅自挑选一个来静默解决；
  • 源材料未提及的值被标记为一项选择，而非作为测量值呈现；
  • 如果缺少某种布局，子流程会以不完整为由拒绝执行，而不是悄悄降级为仅包含所给定布局的主题。

完整的主题会提交给主题与 UI 审阅，其产出是一个 Theme 节点。它是单一节点类型而非三种，因为调色板词汇是共享的，便签条（sticky）、网页与出版物之间仅几何结构有所不同。

构建 L1 知识图谱

✎ Edit TR

打开 BPMN 源文件

每个文件夹都获得一个独立的 dublin-core.jsonld 作为其真实的基准记录，由 manifest.jsonld 进行引用。dcterms 已经是该语料库的 JSON-LD 词汇表，因此这是对既有活跃上下文的扩展，而非引入新上下文。

文件夹名称即是书目引用键，因此引用与目录是完全相同的字符串。

L1 完整性关卡

✎ Edit TR

打开 BPMN 源文件

若没有此关卡，上述每个衍生步骤在实践中都将变为可选的：文档进入 library/，显示为已摄取，而缺口只有在下一次有人需要该缺失制品时才会显现 —— 此时相关上下文早已荡然无存。

往返检查是翻译检查设计成此种形态的原因。仅向前检查只询问目标语言文本是否通顺，而笃定的误翻也能通过该检查。回译并进行比对则询问含义是否得以留存，这才是真正需要的属性，且无需参考译文。它所无法做到的是判定哪种解读是正确的 —— 该分支会转交给审阅者。

Dublin Core 涵盖了其中的多少？

✎ Edit TR

涵盖了其中一部分，而明确具体涵盖了哪些很有价值，因为答案决定了一个字段究竟是 dcterms 术语还是本项目自创的内容。

Dublin Core 很好地覆盖了书目层 —— dcterms:title、creator、date、language、identifier、hasPart、format、extent。每个文件夹的记录以及归档的部分/整体结构都能很自然地融入其中。

它并不涵盖衍生层。 图表的叙述性描述、文字记录、回译置信度、工作表的列标题，尤其是所生成叙述的来源溯源，均不是 dcterms 术语，而在已发布的词汇表中胡乱猜测 IRI 是错误的做法。

schemas/jsonld.ts 中既有的内部规则决定了其形态：合理泛化是明智的，凭空捏造则不然。 凡是现有词汇表中已有的术语，直接采用；凡是没有的，该术语应放入本项目自己的命名空间中，而不是被硬套进一个近似的 dcterms 术语中。优先采用哪些词汇表 —— 用于溯源的 PROV-O 显然是首选候选 —— 目前尚未确定，必须根据已发布的规范而不是凭记忆来定夺。

编辑已摄取的来源

✎ Edit TR

摄取绝不会编辑语料库内容。它产出 L1 记录；创作和审阅通过发布工作流中的常规流程来消费它们，其中对内容块的修改会经历验证、问题发现以及编辑者的决策。

值得说明的一项耦合是：在编辑会话期间向 uploads/ 放入文件会在后台启动摄取。编辑者不会被阻塞，而新来源在关卡通过时即可被引用 —— 绝不会在此之前。

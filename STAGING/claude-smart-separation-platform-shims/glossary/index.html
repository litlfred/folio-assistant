Glossary

Every term the instances in this repository define or carry, as W3C SKOS. Terms link to the external concepts they match rather than copying them. 3207 terms: 38 authored in 4 glossaries, on this page, and 3169 extracted from knowledge-graph assets in 28 generated schemes, one page per asset type, plus the sources below.

authoredA person wrote or approved the definition.38
candidate, extractedLifted from a knowledge-graph asset's own title and description, verbatim, and not curated. The definition is the asset's text, the source links to the asset, and an asset with no description gives a term with none. A person promotes one by authoring it.3169
could-not-extractThe source names a term the extractor could not read, and says why.0

Already somebody else’s concept?

Extracted candidates are minted from this repository’s own assets and are not, by themselves, checked against any vocabulary. check:term-mapping asks whether each already exists as a concept somebody is authoritative for — SKOS for what a term MEANS, FHIR for a clinical code’s operational semantics — and the two are separate questions with separate answers.

Undetermined is never “no match”. A vocabulary that could not be reached has said nothing, and the column above keeps that apart from a checked miss. The counts are reported and not graded: an unmapped candidate may be a term this corpus is right to coin.

Bootstrap terms

The terms Bootstrap defines, in order: each is defined only by terms above it, and never itself. Read from the schema that defines them, bootstrap/schemas/graph.schema.json, so this glossary cannot say anything that schema does not. SKOS.

1. Node

One file, or one part of a file addressable by an IRI fragment, named by an IRI.

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Node · defined by www.w3.org/TR/json-ld11/#node-objects · source bootstrap/schemas/graph.schema.json#/$defs/Node

2. Reference

A Node's naming of another Node by its IRI.

Uses: Node

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Reference · defined by www.rfc-editor.org/rfc/rfc3987 · source bootstrap/schemas/graph.schema.json#/$defs/Reference

3. Node Schema

A schema a Node can be checked against: a JSON Schema, or a published external schema such as BPMN's.

Uses: Node

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#NodeSchema · defined by json-schema.org/draft-07/schema# · source bootstrap/schemas/graph.schema.json#/$defs/NodeSchema

4. Node Kind

A name paired with a Node Schema.

Uses: Node Schema

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#NodeKind · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/properties/nodeSchemas · source bootstrap/schemas/graph.schema.json#/$defs/NodeKind

5. Subkind

A Node Kind whose Node Schema requires everything another Node Kind's does, so every Node that satisfies it satisfies the other too.

Uses: Node Kind, Node Schema, Node

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Subkind · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/Subkind · source bootstrap/schemas/graph.schema.json#/$defs/Subkind

6. Node Instance

A Node that names its Node Kind, in $schema or front matter, and satisfies that kind's Node Schema.

Uses: Node, Node Kind, Node Schema

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#NodeInstance · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/NodeInstance · source bootstrap/schemas/graph.schema.json#/$defs/NodeInstance

7. Graph Kind

A named set of Node Kinds.

Uses: Node Kind

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#GraphKind · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/GraphKind · source bootstrap/schemas/graph.schema.json#/$defs/GraphKind

8. Declaration

A JSON document, <name>.json, that gives a name and lists directory entries and file entries.

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Declaration · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json · source bootstrap/schemas/graph.schema.json#/$defs/Declaration

9. Extension

A field of a Declaration, or of one of its entries, that is not defined here. A reader that does not recognise the field ignores it, and the rest of the Declaration keeps its meaning.

Uses: Declaration

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Extension · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/Extension · source bootstrap/schemas/graph.schema.json#/$defs/Extension

10. Subgraph

A directory entry of a Declaration: an id, a directory, and the Graph Kinds its Node Instances' kinds belong to.

Uses: Declaration, Graph Kind, Node Instance

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Subgraph · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/Subgraph · source bootstrap/schemas/graph.schema.json#/$defs/Subgraph

11. Asset

A file entry of a Declaration: one file about the repository itself, whose role field says what it is for.

Uses: Declaration

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Asset · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/Asset · source bootstrap/schemas/graph.schema.json#/$defs/Asset

12. Knowledge Graph

The Node Schemas, Node Instances and Assets one Declaration lists, as of one version of the repository. Published as JSON-LD, the statements of each Subgraph's Node Instances form one named graph.

Uses: Node Schema, Node Instance, Asset, Declaration, Subgraph

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#KnowledgeGraph · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json · source bootstrap/schemas/graph.schema.json#/$defs/KnowledgeGraph

13. Dependency

A Declaration's needs entry naming another Knowledge Graph. References may point from this graph's Node Instances into the named one, never back.

Uses: Declaration, Knowledge Graph, Reference, Node Instance

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Dependency · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/Dependency · source bootstrap/schemas/graph.schema.json#/$defs/Dependency

14. Content

Node Instances that describe the subject matter of a Knowledge Graph, such as records, documents, catalogues and their terms, rather than how to work with it.

Uses: Node Instance, Knowledge Graph

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Content · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/Content · source bootstrap/schemas/graph.schema.json#/$defs/Content

15. Task

A unit of work, stated by what it needs to begin and what it produces.

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Task · defined by www.omg.org/spec/BPMN/2.0/#task · source bootstrap/schemas/graph.schema.json#/$defs/Task

A person, an agent or a program that can carry out Tasks.

Uses: Task

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Actor · defined by www.w3.org/ns/prov#Agent · source bootstrap/schemas/graph.schema.json#/$defs/Actor

17. Skill

A Node Instance holding natural-language instructions an Actor follows to carry out a Task.

Uses: Node Instance, Actor, Task

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Skill · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/Skill · source bootstrap/schemas/graph.schema.json#/$defs/Skill

Uses: Node Instance, Actor, Task, Skill

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Role · defined by litlfred.github.io/bootstrap/0.1.0/schemas/graph.schema.json#/$defs/Role · source bootstrap/schemas/graph.schema.json#/$defs/Role

A BPMN flow node: an activity (a task or call activity), a gateway, or an event.

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#ProcessNode · defined by www.omg.org/spec/BPMN/2.0/#flowNode · source bootstrap/schemas/graph.schema.json#/$defs/ProcessNode

A directed connection in a BPMN process from one Process Node to the next.

Uses: Process Node

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#SequenceFlow · defined by www.omg.org/spec/BPMN/2.0/#sequenceFlow · source bootstrap/schemas/graph.schema.json#/$defs/SequenceFlow

A Node Instance holding a BPMN process that coordinates Tasks: its Process Nodes, joined by Sequence Flows, sit in lanes that each name a Role.

Uses: Node Instance, Task, Process Node, Sequence Flow, Role

Bootstrap terms · https://litlfred.github.io/bootstrap/0.1.0/ns#Process · defined by www.omg.org/spec/BPMN/2.0/#process · source bootstrap/schemas/graph.schema.json#/$defs/Process

A named set of writing rules for prose, active in the roles and processes it names. The voice points at the role it is written for; the role names no voice.

  2. Decide which roles content-pipeline-navigator and platform-boundary-guard take on

    Status
    blocked
    Priority
    medium
    Raised by
    agent
    Created
    2026-09-19
    About
    publication-workflow › agents-and-system-actors

    ci-health-watcher is settled: it is a mechanical participant in the CI process, so it takes build-pipeline and validation-pipeline, both actorKind: "system". Declared, and memoryForRoles now discriminates because of it.

    **The other two are not settled by that argument, and the reason is precise.** Both system roles are described as running a fixed program and exercising *no judgement*. That is exactly what makes them the right home for a watcher — and exactly why they are the wrong home for these two:

    - **platform-boundary-guard** decides whether a literal naming one folio belongs in platform code, and whether a new content type needs an adapter or only a profile. Those are judgements; a wrong one is not a failed check. - **content-pipeline-navigator** is closer to mechanical — it knows which stage owns which file — but it also answers "should this be a block kind", which is not.

    ## What differs depending on the answer

    Nothing breaks either way today: memory is scoped by agent and the duplication is already fixed, because one node can reach several agents. What changes is whether a fact written for one of these two reaches an agent standing in that lane, or only the agent named in the file.

    ## Options

    1. **Leave both agent-scoped, and say so in the role model.** Costs nothing, and is honest — neither is a lane anyone else acts in. The cost is that the role axis stays half-used, with one actor on it. 2. **Give them a judgement-bearing existing role** — editor and code-reviewer are the nearest. Cheap, and wrong if the fit is loose: a forced edge is one every later audit trusts as true. 3. **Add roles for them.** Honest edges. But AGENTS.md warns under skill-in-role-or-process against "inventing roles and activities to absorb tools that do not want them", and a role with one actor describes the tool rather than the work.

    No recommendation. The ci-health-watcher case was settled by a property of the work (it exercises no judgement); neither option here has an equivalent, which is why it is a person's call and not an agent's.

    ## If nothing is decided

    Option 1 is the status quo and nothing regresses.

  3. Decide what 'kick off' means mechanically for the two CI-watcher dispatch points

    Status
    in_progress
    Priority
    medium
    Raised by
    agent
    Created
    2026-09-19
    About
    publication-workflow › agents-and-system-actors

    Stated 2026-09-19: a CI watcher *"should kick off during feature development once changes are made to feature branch. and when approved for final publication/merge to main."*

    The two dispatch points are clear. **What performs the dispatch is not**, and the three candidates differ enough that guessing would be wasted work.

    ## ANSWERED, 2026-09-19

    Owner: *"kick off if like task or workflow initation or bean roast"*.

    **Option 2.** A dispatch point is a **task / workflow initiation**, and it opens a **bean** — not a GitHub Actions job. That is the answer the repo's own machinery is already shaped for: an activity carrying <folio:bean op="claim"/> performs the bean operation when the step completes, so "start the watcher" and "record that it is running" are one declared step rather than two mechanisms that can disagree.

    It also settles the cost I flagged against option 2 — that a BPMN activity only fires while somebody is working. With a bean opened at initiation, the work is *durable*: a later session sees the bean whether or not the session that opened it is still alive.

    Remaining, and now narrow: which diagrams host the two steps, and whether the feature-branch one needs a process that does not yet exist.

    ## Options, with what each costs

    1. **A GitHub Actions job.** Fires without anybody present, which is the whole premise of xom7 — the failure being guarded against is a quiet stretch with nobody looking. Cost: it cannot read the session's memory, so the "dispatch an agent with a specific memory context" half does not happen. 2. **An activity in a BPMN process**, performed by a session. Gets the memory context, and puts the dispatch where workflow_next can report it. Cost: it only fires while somebody is working — precisely the stretch that is already covered. 3. **An MCP tool a workflow step calls.** Both, at the price of building the tool and deciding who calls it.

    ## Where the two dispatch points already live

    Both are steps in diagrams that exist, which is why this todo is tagged with them rather than describing them:

    - **"approved for final publication / merge to main"** is Process_Publication (draft-to-publication.bpmn), whose lane carries *Authorise the release* and *Version, tag and publish*. The dispatch point the owner named is that authorisation step. - **"once changes are made to feature branch"** is Process_CodeReview, reached from Process_Review.

    ## What is already true, so this is not started from nothing

    The two dispatch points are process events, so wherever they are performed they should be DRAWN in BPMN under processes/. The likely homes are draft-to-publication for the merge-to-main gate and a feature-branch process that may not exist yet — that needs checking rather than assuming.

    ## If nothing is decided

    Nothing fires. bun run check:ci-health still runs in the session-start sweep and ci-health.yml still runs weekly, so the watcher is not silent — it is just not tied to the two moments named above.

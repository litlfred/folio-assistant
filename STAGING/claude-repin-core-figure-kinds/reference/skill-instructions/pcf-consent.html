pcf-consent

Skill id: pcf-consent · Package: fhir-ig-authoring · Instance: fhir-harness · Modules: schemas/pcf-consent.ts (consentToOdrl, decide, evaluatePcfPolicy, PCF_IMPLICIT_POLICY_SETS), schemas/iti-108-consent-client.ts (findAccessConsents, Iti108ConsentClient) · Beans: folio-assistant-y0o0 (PCF9), folio-assistant-jx7m (PCF5), folio-assistant-a7c1 (PCF6), folio-assistant-r9vk (PCF7), folio-assistant-2egb (PCF8).

Model patient privacy consent directives in FHIR Implementation Guides, translate them into W3C ODRL 2.2 policies, and evaluate three-valued access-control decisions (permit | deny | unknown).

Standards approval & scope (owner decision, 2026-10-30, issue #2702):

  • Approved specifications: IHE IT Infrastructure Technical Framework Supplement — Privacy Consent on FHIR (PCF) 1.1.0 (Trial Implementation, 2023-08-04) and HL7 FHIR R4 Consent (Trial Use, FMG maturity level 2).
  • Basic consent first: implement IHE PCF Basic (IHE.PCF.consentBasic) and Additional PurposeOfUse (IHE.PCF.consentIntermediate with extended HL7 PurposeOfUse codes and nested provision exceptions) first; IHE.PCF.consentAdvanced security-label sensitivity tags are supported by the translator when declared.
  • Referenced by canonical URL only: never copy or re-author IHE PCF StructureDefinitions or ValueSets in an IG; pin the upstream packages in sushi-config.yaml and reference IHE profiles and value sets by their canonical URLs.
  • No IUA claim: do not claim conformance to IHE Internet User Authorization (IUA) or profile ITI-71 / ITI-103 OAuth token exchange unless separately approved; HTTP Authorization headers on ITI-108 reads are passed through opaque to the transport.
  • Trust-anchor neutral: any consent-bearing workflow or verifiable link depends on an abstract trust anchor (for example a national PKI, a regional federation, did:web, or the Global Digital Health Certification Network (GDHCN) as one possible trust anchor among others — never hardcoded as the only one).

1.3 Required structure of a PCF Consent instance

Every conformant IHE PCF 1.1.0 Consent resource carries:

  1. meta.profile: one of IHE.PCF.consentBasic, IHE.PCF.consentIntermediate, or IHE.PCF.consentAdvanced (detectPcfProfile(consent) inspects meta.profile and falls back to structural inspection).
  2. status: "active" for an enforceable consent directive ("draft", "proposed", "rejected", "inactive", and "entered-in-error" carry no active permissions or prohibitions).
  3. scope: http://terminology.hl7.org/CodeSystem/consentscope#patient-privacy.
  4. category: includes http://loinc.org#59284-0 (Consent).
  5. patient: reference to the Patient subject (Patient/<id>).
  6. dateTime and performer (the consenting patient or authorized representative, which becomes the ODRL assigner) and organization (the custodian organization).
  7. sourceReference or sourceAttachment: the signed paper/electronic consent artifact or questionnaire response.
  8. policy: policy[].uri naming the overarching privacy policy (such as one of the four IHE PCF Volume 1 §1:53.2.1 implicit policy URIs).
  9. provision: root provision (type: "permit" or "deny"), purpose codings from http://terminology.hl7.org/CodeSystem/v3-ActReason (TREAT, HPAYMT, HOPERAT in BasicPurposeVS, or extended PurposeOfUse codes such as HRESCH, CLINTRCH, BIORCH, PUBHLTH, ETREAT, BTG, PATRQT), optional period, actor, action, dataPeriod, data, securityLabel, and optional nested provision.provision exceptions.

No draft purpose vocabularies: W3C DPV is a Community Group report and is refused (dpv:* or /dpv returns false in isKnownHl7PurposeOfUse). Always use HL7 v3 ActReason PurposeOfUse codes.

2.2 The four IHE PCF Volume 1 §1:53.2.1 implicit-policy Sets

When a patient has no explicit active Consent on file (or when their explicit Consent has expired), IHE PCF Volume 1 §1:53.2.1 and §1:53.4.2.4 define four overarching jurisdictional baseline policies, exported in PCF_IMPLICIT_POLICY_SETS and resolved by getImplicitPolicySet(uriOrAlias):

Canonical URI (PCF_POLICY_*_URI)Alias(es)ConstantSemantics
https://profiles.ihe.net/ITI/PCF/Policy-basic-normal"basic-normal"PCF_IMPLICIT_BASIC_NORMAL_SETPermit Clinical Treatment: permits odrl:use when odrl:purpose isA TREAT (including ETREAT, BTG, CLINTRL, POPHLTH); non-treatment purposes return deny.
https://profiles.ihe.net/ITI/PCF/Policy-all-normal"all-normal", "opt-out"PCF_IMPLICIT_ALL_NORMAL_SETPermit All Authorized (opt-out baseline): permits odrl:use when odrl:purpose isA PurposeOfUse.

3. Decide — Three-Valued Evaluation, ITI-108 Reads, obtainConsent, and PROV Citations

3.1 decide() and evaluatePcfPolicy() (permit | deny | unknown)

decide(consentOrPolicy, req, options) in fhir-harness/schemas/pcf-consent.ts evaluates a PcfDecisionRequest (actor, actorRoles, actorGroups, action, and scope / top-level purpose, dateTime, target, securityLabel, dataPeriod, author, encounter):

  1. Active explicit Consent governs: if one or more active, non-expired Consent resources (or translated PcfOdrlSets) are supplied, any deny across them returns "deny" (odrl:prohibit), any "permit" (with no "deny") returns "permit", and unresolved scope operands return "unknown".
  2. Missing Scope Operand is "unknown", never "permit": if a rule constrains odrl:purpose, odrl:dateTime, pcf:securityLabel, target, or assignee and the request omits that dimension, evaluation yields "unknown". Under conflict: "odrl:perm" (such as a root deny with a Break-Glass permit exception), if the exception’s constraint is unresolved, evaluatePcfPolicy() returns "unknown" rather than prematurely denying before purpose is supplied.
  3. Expired or absent Consent:
    • If options.implicitPolicy is provided, decide() falls back to the configured implicit-policy Set (IHE PCF Vol 1 §1:53.2.2 & §1:53.4.2.5).
    • If no implicitPolicy is configured: an expired active Consent returns "deny", and an absent or non-active Consent returns "unknown" — never a silent "permit".

3.2 Reading consents via IHE ITI-108 (findAccessConsents, PCF7)

findAccessConsents(query) and Iti108ConsentClient in fhir-harness/schemas/iti-108-consent-client.ts (bean folio-assistant-r9vk) implement the IHE ITI-108 (Find Access Consent, [ITI-108]) RESTful search transaction (GET <baseUrl>/Consent) as a Consent Consumer:

  • Search parameters (buildIti108SearchUrl): patient / patient.identifier, status (defaults to "active"), actor, purpose, security-label, period, date, data, _profile, and _count.
  • Client-side validity filtering (evaluateConsentValidity / filterIti108Bundle): every Bundle.entry.resource of type Consent is verified against FhirConsentSchema. Entries whose status !== "active", whose patient does not match the queried patient, or whose provision.period is expired (end < now) or future-dated (start > now) are excluded from consents and recorded in ignored[] with a structured Iti108IgnoredReason ("not-active", "expired", "not-yet-valid", "patient-mismatch", "invalid-period", "invalid-consent").
  • Third-state failure handling (status: "unknown"): network failures, DNS errors, request timeouts, non-2xx HTTP responses, malformed JSON, non-searchset payloads, or OperationOutcome errors return { status: "unknown", reason, detail } — never an empty consents: [] that a caller could mistake for “no consent on file”. When passing an ITI-108 result into decide(), check result.status === "unknown" first and propagate "unknown".

3.3 Fulfilling odrl:obtainConsent duties on DSAs via injected createPcfConsentEvaluator (PCF6)

In cat-harness/schemas/content/odrl.ts (beans folio-assistant-s4v2, folio-assistant-a7c1, and folio-assistant-6jnx), cat-harness stays free of FHIR resource types and pcf:* keys; a Data Sharing Agreement (@type: "Agreement") carrying an { action: "odrl:obtainConsent" } duty evaluates consent through an injected consentEvaluator: createPcfConsentEvaluator(consents, options) callback supplied from fhir-harness/schemas/pcf-consent.ts (returning { verdict, consent: { id, versionId, uid } } to permits() / permitsWithConsent() / decideWithConsent()):

  • DSA + no Consent (or unreachable ITI-108 registry) → "unknown": when odrl:obtainConsent is due and no active matching PCF Consent (or consent-verification record) is provided, permits() returns "unknown".
  • DSA + matching deny Consent (or expired Consent) → "deny": when the patient’s PCF Consent denies the requested actor, action, purpose, or target, the decision is "deny".
  • DSA + matching active permit Consent → "permit": when an active, in-period PCF Consent permits the request’s actor, action, purpose, and target (and any other DSA constraints and duties hold), permits() returns "permit".

3.3a Owner consent rules (2026-10-30 19:27Z)

The owner set four rules for consent-based agreements. Two are enforced here; the other two are authored in the agreement itself (the dsa document kind and its lifecycle process in folio-assistant-core).

  1. Legal basis. An agreement carries odrl:obtainConsent only when consent is its legal basis. Treatment, public-health law and research waivers do not rest on consent, so their agreements have no such duty and this evaluator is never asked.
  2. Version pinning (enforced here). A Consent names the agreement’s fixed-version URL in R4 Consent.policy.uri. createPcfConsentEvaluator counts a Consent only when that URI equals the agreement’s version (the agreement policy’s uid, or agreementPolicyUri); consentsCitingAgreement() is the filter. An amendment that widens use is a new version URL, so the old Consent no longer counts and new consent is needed. An amendment that narrows use does not need new consent: pass the agreement’s DCAT 3 version chain as agreementVersions (each version’s ODRL policy and its dcat:previousVersion), and an older Consent still counts while every step back to its version is a narrowing amendment. isNarrowingAmendment() decides that from the ODRL rules alone, with no extra field: every newer permission must sit inside an older one (same or narrower action, same target and assignee, each older constraint matched by one at least as tight, each older duty kept), and every older prohibition and obligation must remain. A widening step, a missing version or anything it cannot compare (such as inheritFrom) stops the walk, so new consent is needed (owner card 2026-10-30 19:55Z).
  3. Plain language. Every agreement that needs consent publishes a plain-language summary, hashed with the agreement. That summary is what the person consents to.
  4. Scale (enforced here). The jurisdiction picks one of PCF’s implicit default policies (opt-in or opt-out) and passes it as implicitPolicy. Registry reads may be cached: new Iti108ConsentClient(base, defaults, { ttlMs }). An entry ends at its TTL, at the earliest provision.period.end of its Consents, or at once when consentWithdrawn(id) is called for one of its Consents.

3.4 Citing Consent.id + Consent.meta.versionId in PROV-O decision records (PCF8)

Every consent-based access decision recorded in the hash-chained W3C PROV-O decision log (cat-harness/schemas/content/prov.ts, cat-harness-tools/src/workflow/prov-record.ts; beans folio-assistant-3z44 and folio-assistant-2egb) must cite the exact Consent resource version used:

  • Use extractConsentCitation(consent) / consentPolicyUid(consent) from fhir-harness/schemas/pcf-consent.ts to obtain { id, versionId, uid, status, patient, performer, policyUris }.
  • Include the translated consent policy uid (urn:ihe:pcf:consent:<id>:v<versionId>) in "cat-harness:underPolicy" on the prov:Activity decision record alongside the governing DSA Agreement uid, and record the Consent’s id and meta.versionId citation so any auditor can verify which version of the patient’s consent directive was in force when the decision hash (cat-harness:recordHash chained via cat-harness:previousHash) was computed.

3.5 One-way renderer: ODRL 2.2 Agreement to FHIR R5 Permission (output only, bean jfbm)

Per owner card 2026-10-30 19:23Z (“A: Yes, later bean”), HL7 FHIR R5 Permission (Trial Use) is approved for output only: W3C ODRL 2.2 stays the source of truth and nothing reads Permission back. schemas/odrl-to-fhir-r5-permission.ts provides odrlAgreementToFhirR5Permission(agreement, options) and fhirR5PermissionToFsh(permission, options):

  • FhirR5PermissionSchema and its required value-set code lists are built from hl7.fhir.r5.core#5.0.0’s StructureDefinition-Permission.json and CodeSystem-*.json (permission-status, permission-rule-combining, consent-provision-type, consent-data-meaning), so no field outside FHIR R5 Permission is ever invented.
  • Maps conflict (prohibit / perm) to combining (deny-overrides / permit-overrides); assigner to asserter; shared dateTime constraints to validity; the agreement’s fixed-version uid and dcterms:source to justification.evidence / justification.basis; permission / prohibition to rule.type (permit / deny); target to rule.data.resource; assignee, action (consentaction), and purpose (HL7 v3-ActReason PurposeOfUse) to rule.activity; and delete duty roughly to rule.limit (v3-ActCode#DELAU).
  • Every ODRL 2.2, DCAT 3, or SPDX term with no exact home in FHIR R5 Permission (including @type, profile, inheritFrom, spdx:checksum, isA, exclusive lt/gt bounds, elapsedTime, refinement, and duties or duty constraints) is returned explicitly in dropped: DroppedOdrlTerm[] rather than dropped silently.

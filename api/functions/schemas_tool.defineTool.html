      Build and validate a Tool node.

      Tool nodes are authored as .ts calling this, so a malformed one fails at tsc and in the editor rather than at CI. That is the whole argument for the carrier decision, applied to instances as well as to the schema.

            A function in this instance's own code.

            Added because 17 of the 20 tools this repository already serves have no shell equivalent — they are TypeScript registered on the MCP server, and without this arm they cannot be expressed as Tool nodes at all.

            Why the mcp-only refusal does not apply

            That refinement exists because a Tool reachable only over MCP is not runnable by the harness and projecting it would emit a server that proxies itself. An in-process function is the opposite case on both counts: the harness can call it directly with no server at all, and it is the projection source rather than something to proxy. src/server.ts already does exactly this projection by hand.

            module locates the code; it is NOT a unique key, because one module registers several tools (workflow.ts registers five). The Tool's id is the key, and it is the MCP name the module registers.

            • module: string

              INSTANCE-relative path to the module, e.g. src/tools/workflow.ts.

              The instance, not the repository — this said "repo-relative" while giving an example that is instance-relative, and after the move under cat-harness/ the two stopped being the same thing. The values were right and the word was stale; check:tools now resolves this field against the instance root and invoke.shell against the repository, because a shell command is typed from the repo root while a module is loaded by the instance's own server. Same convention as maintains.source.

            • Optionalregister?: string

              The registrar export, when the module has more than one.

          • Optionalmanual?: true

            The tool is performed by a person following the skill, with no command. beans-manual is the case: editing a bean's front matter by hand is a real mechanism with equal standing to the CLI, and modelling it as an absent shell would have made it indistinguishable from an unfinished record.

          Published artefacts this Tool is authoritative for. See ToolMaintainsSchema.

          Optional because most Tools maintain nothing — they DO something. A Tool that maintains an artefact is the specific case the owner asked for: a zod module whose job is to keep a public JSON Schema true.

        • Optionalrenders?: string[]

          The graph KINDS this Tool draws a viewer for — one page per declared directory of the kind, placed by the Tool itself.

          #1168 B7a, owner 2026-09-24 ("viz scripts become Tools"): until then each directory named its viewer page (coverage.visualiser), which is the directory pointing at what depends on it. The dependent holds the pointer, so the renderer says what it renders. A kind, not a list of pages, because which directories exist is the declarations' answer and a Tool restating it would be a second list free to drift.

          Skills this Tool can satisfy. One skill may have several Tools.

        • Optionalselection?: { cost: string; limits: string; when: string }

          Why to reach for this one. REQUIRED when the Tool has a derived alternative (deriveAlternatives); check-tools enforces it, since whether a Tool has one is a fact about the whole set.

          • cost: string

            What having it available costs. Distinct from install; see above.

          • limits: string

            Where it stops, and which sibling picks up — "none" is a real value, stated.

          • when: string

            The case this Tool is the right answer to.

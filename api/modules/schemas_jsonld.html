    Module schemas/jsonld

    JSON-LD projection of the content block model.

    Blocks are authored as TypeScript manifests and stay that way — the builders in builders.ts are where author-time type checking lives, and content/pipeline/block-module.ts treats a manifest that throws on import as a finding. This module does not replace any of that. It defines the published form: a .jsonld sibling next to each .ts, generated by content/pipeline/gen-block-jsonld.ts, so that

    1. an external consumer can reference a block without a TypeScript toolchain, and
    2. authored blocks and ingested documents (library/**) carry the same @context, the same @type vocabulary and the same edge terms — so one graph loader serves both populations instead of two.

    Why labels are not emitted as IRIs

    This is the hazard the whole module exists to route around, so it is worth stating plainly.

    A folio label looks exactly like a JSON-LD compact IRI: def:foo has the shape prefix:reference. It is not one. The def: part names a block kind, not a namespace, and JSON-LD splits a compact IRI on its first colon. Emitting labels directly as IRI values therefore goes wrong in two different ways:

    • def:quantum-universe would need a def prefix in the context, which would place the block in a per-kind namespace. The same block referenced cross-paper as some-paper:def:quantum-universe would then expand under a per-paper namespace instead. Two IRIs for one block — every graph join silently under-counts, with no error anywhere.
    • unital-groebner-bases:thm:bar splits into prefix unital-groebner-bases and suffix thm:bar. With no such prefix defined, JSON-LD falls back to treating the whole string as an absolute IRI — and unital-groebner-bases:thm:bar is syntactically valid, with unital-groebner-bases as its scheme. The result is a well-formed IRI that means nothing and joins with nothing.

    So @id is minted by resolveLabel, which resolves all three authored reference forms to one canonical relative IRI, and the label is additionally preserved verbatim in folio-assistant-core:label for grep and round-tripping. Nothing in content/** has to change.

    Why @id is relative

    Emitted IRIs are relative (papers/<paper>/blocks/def-foo) and @base lives in the published context. That keeps generator output identical regardless of where a folio is deployed — which matters because the generated siblings are committed and gated on drift: a base-URL change must not rewrite thousands of files.

Forced Along a BPMN vs Managing It — Harness Built, No Model Run Yet

Bean folio-assistant-502c asks an empirical question that deterministic-and-agentic, process-state, and specification-compiled-agents treat as an assumption:

When the same BPMN diagram is run over the same independent task bank under two orchestration arms — Arm 1 (forced, stepped by the token machine one enabled node at a time) and Arm 2 (self-managed, handed the full diagram and managing its own progression) — do outcomes change, and at what compute and token cost?

This page does not answer that question. It records the two-arm runner built for it (cat-harness-tools#739) and what the runner reports when it is run with a simulated agent. No language model was called. The numbers below show that the runner, the token machine’s refusals and the folio-test-run/v1 recording work. They are not evidence about how a model behaves under either arm, and they must not be cited as such.

0. What was actually run (read this first)

Checked against cat-harness-tools#739 on 2026-10-26:

  • The “agent” is a fixed script. Each bank case carries an agentProposal.proposedSteps list written by hand (scripts/eval/bpmn-forced-vs-managed-bank.json). Both arms replay that same list. Nothing in src/workflow/arm-forced.ts, src/workflow/arm-self-managed.ts or scripts/eval-bpmn-forced-vs-managed.ts calls a model or any network service.
  • The forced arm’s “recovery” is the runner, not an agent. After a refusal, runForcedCase stops consulting the script and submits the node that enabled() reports as enabled (candidate = { node: current.node, … }). The forced arm reaching the canonical path is therefore guaranteed by the runner’s construction.
  • The self-managed arm accepts whatever the script says. runSelfManagedCase appends each scripted step to the path without enforcement. Its errors are exactly the violations written into the five temptation cases.
  • Tokens are estimates of payload size, not model usage. Every “token” count is ceil(bytes / 4) of a JSON payload the runner builds (estimateTokens). No tokenizer was run and no API reported usage. “Completion tokens” are the size of the scripted step, not anything a model produced.
  • Wall time is the runner’s own CPU time. Tens of milliseconds for about 220 “turns” per arm (4–5 ms in the first run): there is no inference in them, so they say nothing about the time or compute a model would need.

So the outcome rows are true by design, and the token rows measure how big the two prompts the runner would send are. Neither is the measurement the owner asked for (“give LLM BPMN and force them along it, give LLM BPMN and let them manage workflow”).

1. Experimental Design and the Two-Hash Split (folio-test-run/v1)

Both arms execute against the same normative diagram pair and the same independent 10-case task bank, and each arm emits a folio-test-run/v1 record:

  • Diagram under test: processes/sdlc/test-plan-execution.bpmn (Process_TestPlanExecution, 5 swimlanes), which opens its bean through bean-open.bpmn and closes it through bean-close.bpmn (bean m8gz), evaluates processes/sdlc/decisions/test-certification.dmn at GW_ExitCriteria (certifiedrefusedundetermined) and, on the certified branch, enters processes/sdlc/qa-report-signing.bpmn (Process_QaReportSigning, 3 swimlanes) via call activity Call_Sign, which in turn evaluates processes/sdlc/decisions/signing-route.dmn at Gateway_SigningRoute (apihuman).
  • Independent task bank: cat-harness-tools/scripts/eval/bpmn-forced-vs-managed-bank.json (bpmn-forced-vs-managed-v1, 10 cases: 5 disciplined scenarios covering every DMN branch and 5 temptation scenarios targeting the failure modes documented in the two diagrams). Each case’s facts and expected path are usable as-is with a real model; its agentProposal is the simulated agent’s script.
  • Run command (simulated agent; first run 2026-10-24, re-run 2026-10-26 after bean m8gz added the bean-open/close steps): 
    bun run cat eval:bpmn-forced-vs-managed

3. What the Simulated Run Does and Does Not Establish

It establishes properties of the engine and the runner, which are deterministic and would hold for any agent:

  1. The token machine refuses each scripted violation. complete() in src/workflow/instance.ts raised WorkflowError on every scripted shortcut in temptation cases 5–8 (out-of-order step, hand-asserted DMN outcome, unexpanded CallActivity, skipped Task_ResolveReach with a hand-picked route), 20 times in all, and enabled() dropped the child-only skills on leaving Process_QaReportSigning (case 10). This is a test of the engine, and it passed.
  2. The prompt the forced arm would send is about 31× smaller per turn. The forced arm’s per-turn payload (enabled step plus its TaskContext) averages about 455 estimated tokens; the self-managed payload (the parent diagram, every called diagram, DMN tables and role closure) about 14,162. That is a static property of the two prompt shapes, measured with a byte-count estimate. It is not a cost a model incurred, and it leaves out everything a real run adds: reasoning output, retries a model chooses to make, and caching.
  3. The two-hash recording works (§1).

It does not establish anything about model behaviour:

  • Whether a model handed the whole diagram skips steps, hand-picks gateway outcomes, bypasses subprocesses or leaks context — and how often. The 4 of 5 temptation failures in Arm 2 are the 4 violations the bank’s author wrote in.
  • Whether a model under the forced arm recovers after a refusal, and in how many turns. In this run the runner, not an agent, picked the recovery step.
  • Time or compute. The wall times are a fraction of a millisecond per runner turn.

A gate that checks only the terminal event cannot tell cases 5, 7 and 8 apart from case 1 in Arm 2: that observation is about the gate and holds whatever produced the path. Whether a real model produces such paths is the open question.

4. What Is Confounded Once a Model Is Run

Per Criterion 3 of folio-assistant-502c and deployment-topologies.md §2, even a run with a real model compares two orchestration harnesses on one diagram pair and one task bank; it must not be cited as a model-vs-model comparison. Three factors are structurally confounded between the arms:

  1. Control-flow enforcement is confounded with per-turn prompt length (Levy et al., arXiv:2402.14848). Arm 1 (forced) changes two things at once relative to Arm 2 (self-managed):
    • the token machine (complete()) refuses out-of-order steps, hand-picked DMN outcomes, and unexpanded call activities; and
    • enabled() slices the prompt payload at each turn down to the single enabled node and its lane/subprocess TaskContext (about 455 vs 14,162 estimated prompt tokens per turn). Because reasoning performance degrades with input context length even well inside nominal context windows (Levy, Jacoby & Goldberg 2024, prior-art.md), any difference in path adherence a live run finds would combine mechanical refusal of invalid transitions with shorter per-step context. Separating the two would need a third arm (the full diagram on every turn with complete() refusals, or one step’s prose without them).
  2. Turn count and refusal retries depend on the agent’s shortcut rate. In Arm 1, every attempted shortcut becomes an extra turn (refusalRetries). Against a disciplined agent refusalRetries is 0 and Arm 1 takes one fewer turn per case than Arm 2 (which spends an initial planning turn over the full diagram); against one that keeps guessing unenabled nodes, Arm 1’s turns and tokens grow with the retry cap.
  3. Diagram, engine, and benchmark-mode specificity (folio-assistant-wp49). Any numbers are properties of src/workflow/instance.ts, test-plan-execution.bpmn and the diagrams it calls, bpmn-forced-vs-managed-bank.json and, once run, the model. Per benchmarking-mode (wp49), benchmark outputs are assertions about the harness/runner configuration rather than facts about a folio, so eval-bpmn-forced-vs-managed.ts guards its output path with assertBenchmarkOutputPath and writes only to build/benchmarks/bpmn-forced-vs-managed/.

5. What Is Needed to Answer the Bean’s Question

  1. Replace the script with a model. At each turn, send the payload the runner already builds (turnPromptPayload in the forced arm, stepPrompt in the self-managed arm) to a model and parse its reply as the proposed step, instead of reading agentProposal.proposedSteps. In the forced arm the model, not the runner, must choose the step after a refusal.
  2. Record what the model reports. Take prompt and completion tokens from the API’s usage fields and time the calls; add the model id and sampling settings to the process basis.
  3. Repeat. One run per case gives no spread. Several runs per case per arm, reported with their variation, are the minimum before any rate is quoted.

Until then the bean’s question — do behaviour outcomes change, and how much time and compute does determinism cost — is unanswered.

# Getting started
{: .no_toc }

This page is about the first conversation — what happens between somebody saying
*"I want to create a folio"* and a published site they can open. If you already
have a folio and want the toolchain set up, skip to
[§4 Install and verify](#4-install-and-verify).

1. TOC
{:toc}

---

## 1. "Create a folio" is five different requests

Say that sentence to five people and you will get five different pieces of work.
The agent's first job is not to start; it is to find out which one you meant.

| you mean | you have | what the wrong guess costs you |
|---|---|---|
| **A new folio in a new repository** | nothing yet | — |
| **folio-assistant added to the repository you already have** | your own project, with its own files | a folio scaffolded on top of work nobody looked at first |
| **Another folio in a repository that already has one** | a folio-assistant instance | a second repository you did not want, and a split corpus |
| **A new document inside the folio you already have** | a folio, and a chapter in mind | an entire empty folio, and the chapter still unwritten |
| **Something you would rather describe in your own words** | — | — |

The fourth row is the one worth pausing on. It is not an error on your part —
"folio" is an unfamiliar word, and asking for one when you meant a chapter in
one is the most natural mistake available. An agent that scaffolds on it has
produced an empty repository and not the paragraph you asked for.

## 2. How the agent decides — and why it is a table, not a judgement

The triage is a real, readable artefact rather than a habit an agent might have:

- the process is
  [`docs/workflows/getting-started.bpmn`](https://github.com/litlfred/folio-assistant/blob/main/docs/workflows/getting-started.bpmn);
- the decision at its centre is
  [`decisions/folio-intent.dmn`](https://github.com/litlfred/folio-assistant/blob/main/docs/workflows/decisions/folio-intent.dmn),
  a DMN decision table you can open in any DMN tool and change without touching
  code.

### The three facts

The gateway reads exactly three things, and two of them come from looking
rather than asking:

| fact | how it is obtained |
|---|---|
| `isFolio` | is there a `harness.config.json` in this directory? |
| `repoHasContent` | does the working tree hold files that are somebody's project, as opposed to being bare? |
| `statedIntent` | what you actually **said** — one of the five, or `unstated` |

`statedIntent` is a fact about the *conversation*. It stays `unstated` until you
have said which, and inferring it from tone or from what would be convenient is
precisely the failure the table exists to prevent.

> `isFolio` is about the directory, not about you. Somebody who has used
> folio-assistant for years is still in an `isFolio=false` directory when they
> open a fresh one. Experience changes how much the agent explains; it does not
> change which branch it takes.

### The seven rules

| # | said | is a folio | has content | → |
|---|---|---|---|---|
| 1–4 | any of the four | – | – | that branch |
| 5 | unstated | yes | – | **ask** |
| 6 | unstated | no | yes | **ask** |
| 7 | unstated | no | no | new folio here |

Hit policy is `FIRST`, so rules 1–4 come before any inference: **a person who
says what they want is never overruled by a heuristic about their filesystem.**

### Why two rules return "ask", and why that is the point

Only rule 7 is decidable by looking. A directory that is already a folio is
consistent with three different requests, and a directory with somebody's
project in it is consistent with two. The table does not paper over that — it
returns `ask`.

That matters more than it sounds:

> **`ask` is an outcome of the table, not a decision the agent reaches.**

An agent cannot route to a branch the table did not return, so the question
becomes obligatory rather than polite. An agent left to decide *whether* to ask
will, under any pressure to seem helpful, decide not to — and the three
ambiguous cases are exactly where guessing is most expensive.

When you answer, your answer becomes `statedIntent` and the same table is
evaluated again. That is why the diagram loops back to *Read the repository
facts* rather than jumping straight to a branch: **your answer is evidence, read
like any other fact.**

### Changing it

The table is an XML file with seven rules in it. To add a sixth kind of request,
add a rule and add a matching branch to the gateway — the loader refuses to
start a process whose table can return an outcome no branch is named for, so the
two cannot drift apart. Nothing in `src/` needs to change.

## 3. What the conversation looks like

**The form of the question comes before its content.** The agent establishes how
you would like to be asked — selectable options, ordinary chat, read aloud,
large type — and records it in `.folio/interaction.json` so no future session
asks you again. See [Accessibility](accessibility.html).

Then, when the answer is genuinely ambiguous:

> **You:** I want to create a folio
>
> **Assistant:** This directory already has a folio in it (`content/atlas/`), so
> a few things you could mean —
> 1. **Add something to the folio that's here** — a chapter, a document
>    *(recommended — it is what "create a …" most often means from inside a folio)*
> 2. Add a second folio alongside `atlas`
> 3. Start a new folio in a new repository
> 4. Tell me more
>
> *(No answer is fine — I'll take 1 and show you before writing anything.)*

And then, what to get started **on** — because "a folio" is not a thing anybody
actually wants:

| content type | what it is | needs |
|---|---|---|
| **paper** | a scientific paper or book, formal claims backed by Lean, typeset through LaTeX | Lean toolchain, TeX |
| **document** | structured prose — policy guidance, a standard, a report | pandoc; no Lean, no TeX |
| **WHO SMART DAK** | a Digital Adaptation Kit (L2) — personas, processes, data elements, decision tables | — |
| **WHO SMART IG** | a FHIR Implementation Guide (L3), built from an L2 DAK | Java, SUSHI, IG Publisher |

See [Content types](content-types.html) for what each formalism buys you.

## 4. Install and verify

Follow [Installation](installation.html), then:

```sh
bun run check-deps
```

`bun` should be reported present. Anything your content type needs and does not
have is listed with an install hint — a document folio needs none of the Lean or
TeX rows.

## 5. Connect your LLM harness

Register folio-assistant as an MCP server — see
[Connecting an LLM harness](installation.html#connecting-an-llm-harness) for
Claude Code, Antigravity, Gemini CLI and generic MCP clients.

The tools most relevant to this page:

| Tool | Purpose |
|------|---------|
| `folio_init` | Scaffold a folio. Registered as a **generic** tool, because it runs before the folio has a content type |
| `workflow_start` / `workflow_next` / `workflow_complete` | Run `getting-started.bpmn` as a real process; `workflow_next` says what is enabled now and which skill implements it |
| `work_plan_prime` | Surface the work plan (beans) |
| `check_dependencies` | Probe which toolchains are installed |
| `skill_list` / `skill_fetch` | Discover and load a skill's instructions |

The full tool list is on the [Skills & roles](skills.html) page; content-type
tools appear only when the matching adapter is active.

## 6. Converting a repository you already have

On the `overlay` branch the agent looks before it touches anything:

```sh
bun run scan:repo            # read-only report
bun run scan:repo -- --json  # the same, as facts
```

It sorts what it finds into **three** buckets — `library` (source material
somebody else wrote), `content` (prose authored here), and `unclassified`.

The third one is deliberate. A classifier that forces every file into one of two
buckets has an accuracy nobody can assess, and delivers its mistakes as moved
files. This one tells you what it could not place and lets you decide.

Then three questions, all answerable by picking, all asked **per directory**
rather than per file:

1. **Import at all?** — everything, sources only, nothing, or pick by bucket.
2. **Where does each group go?** — `library/` or `content/`, for the groups it
   was unsure about.
3. **Leave in place, or reorganise?** — *leave in place* is the recommendation
   and is meant. Decluttering is a preference; a broken relative link in your
   README is a defect.

Nothing moves until question 3 is answered. That step is marked
`relaxable="false"` in the BPMN, so no content package can declare it away.

Full discipline: the
[`repo-conversion`](reference/skill-instructions/repo-conversion.html) skill.

## 7. Seeing it published

Creating a folio should end with a link. Immediately after scaffolding:

```sh
bun run pages:bootstrap            # derive the address, report, no probe
bun run pages:bootstrap -- --wait  # probe until the site answers (bounded)
```

It derives the address from `harness.config.json` or the `origin` remote, finds
publish workflows by what they *do* rather than what they are named, and reports
one of three things:

| | means |
|---|---|
| **live** | the site answered. Here is the link |
| **not yet** | a **measured** 404 — the address is right and the first build has not landed there yet |
| **could not check** | no address could be derived, nothing was probed, or the request failed |

The third is not a softer version of the second, and the agent will not tell you
"it should be up shortly" on the strength of it. A measured 404 is evidence; a
failed request is the absence of evidence, and an author who is told the wrong
one goes looking for a site that was never going to appear.

The same three states are a decision table —
[`decisions/pages-live-gate.dmn`](https://github.com/litlfred/folio-assistant/blob/main/docs/workflows/decisions/pages-live-gate.dmn) —
and `scripts/pages-bootstrap.ts` is tested to agree with it exactly, so the
script and the table cannot drift.

## 8. Track the work with `beans`

folio-assistant uses [`beans`](https://github.com/hmans/beans) as the single
work-plan mechanism — durable across sessions, shared between agents, committed
to the repository.

```sh
scripts/install-beans.sh          # install the CLI if missing
beans prime                       # emit work-plan priming for agents
beans list                        # current open items
beans create "draft chapter 1"    # open an item
beans <id> --status in-progress   # claim an item
```

> **Check before you create.** `beans create` mints a fresh id on every call and
> dedupes on nothing. Re-entering a scripted step without an existence check
> produced **14,688** duplicate beans in one folio on a single afternoon. The
> check is in the
> [`todo-manager`](reference/skill-instructions/todo-manager.html) skill.

The `SessionStart` hook surfaces the plan at the start of every session, and the
`work_plan_prime` MCP tool exposes the same surface to any connected agent.

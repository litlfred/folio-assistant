From this catalogue to somebody else’s portal

This instance is a worked example of a general pattern: a knowledge graph reaching readers the repository never hears about. The pattern is the platform’s — the skill is kg-to-portal and the process is kg-to-portal.bpmn. What is on this page is the part only who-iris can say: which stages are actually built here, with this instance’s own numbers.

The one distinction the drawing exists for

A CDN is not a publication host. It is a layer in front of one. PUBLICATION_HOSTS answers what serves the rendering; a cache answers what stands between the server and the reader. Model the cache as the host and the published URL becomes the cache’s — then the day the cache changes, every citation breaks and the old URL stays warm for as long as its TTL says.

This page is served from GitHub Pages and its assets are also reachable through jsDelivr. Both are tool choices. The canonical answer is the one the catalogue records; the CDN is an accelerated route to the same bytes.

Trust: GDHCN, via WHO SMART Trust

Owner, 2026-09-20, in two messages: propsal signing = GDHCN, then smart-trust — which names where the first is specified. The WHO SMART Trust Implementation Guide (smart.who.int.trust, FHIR R5, v1.8.0 as read) publishes GDHCN key material as W3C DID documents.

This corrected an earlier draft on this branch. It said the publisher “signs as a participant”, which left the impression that GDHCN supplies the signing envelope. It supplies the key distribution: a trustlist carries trust anchors — which keys belong to which participant, for which domain and which usage — and says nothing about what you wrap your bytes in. The health-certificate envelope is a separate specification in the same IG, and a document package is not a health certificate. What is settled is where a verifier gets the key.

Three things from concepts_did_gdhcn.md, and the third is the one that matters for the drawing above:

  • Two variants. Embedded carries the keys inline and supports immediate verification; by reference carries only DID ids to resolve, which keeps the root document concise and supports dynamic discovery.
  • The path is a hierarchical filter — /v2/trustlist/$domain/$participant/$usage/did.json, the levels ANDed, with - as a wildcard. A verifier fetches exactly the slice it needs.
  • It is static JSON served from a CDN, on a host named tng-cdn.who.int. So the pattern on this page is not an analogy to how GDHCN works — it is how GDHCN works, one layer down.

Read off the IG, not fetched. Those endpoints are transcribed from input/pagecontent/concepts_did_gdhcn.md on main; tng-cdn.who.int returns 000 from the container that generates this page, the same block iris.who.int and cdn.jsdelivr.net return.

Still open and unread: the key rotation and revocation model (concepts_certificate_governance.md), and whether a document-package signature can be expressed for a GDHCN-aware verifier at all — the envelope specified in that IG is for health certificates, and nothing there covers arbitrary files.

Publishing a large graph: skeleton, payloads, one SQLite file per slice

A corpus the size of IRIS can only be searched on the client if the client never downloads the whole graph. The platform’s answer is late materialization. The graph is published as three things:

  1. The skeleton, as JSON-LD. Each named subgraph — a directory of a declared graph — is published at /subgraph/<harness>/<path>/ as index.jsonld (pointers to its members and child subgraphs) and index.hydrated.jsonld (every member inline, with metadata only). The root has the pointer file only, so no single file is ever the whole graph.
  2. Payloads, by content address. Heavy content — a body, a PDF, a page of sections — lives at /payload/sha256/<hex>, named by the hash of its bytes, with a <hex>.json sidecar giving its media type. A node carries a payload link with sha256 and bytes, so a consumer can decide whether to fetch before it fetches.
  3. Per-slice SQLite. CI flattens one slice into a relational schema: one table per node type, one table per relation, and a contentless FTS5 index. It publishes the result as <slice>.<sha256>.sqlite3, named by the hash of its bytes, with a <slice>.sqlite3.json manifest at a fixed path beside it that names the file. A row holds only the payload pointer, never the payload. The browser downloads the file, checks its sha256 against the manifest, imports it into the Origin Private File System, and opens it with the official SQLite WASM build. Nothing is parsed.

The contract is in the kg-export skill, under “Named subgraphs”, “Payloads” and “Per-slice SQLite”. The procedure is the slice-sqlite-publish process. This page does not restate that contract’s rules; where the two differ, the skill is right.

The slice budget, and what to do above it

As built: the budget is about 5 MB per file (SIZE_BUDGET_BYTES). It is reported in the manifest as overBudget and is not gated. The process says what to do over budget: try the no-body variant first, then stop and report the measurement. All four pilots are under it.

Why IRIS will not fit one slice. This is arithmetic on the pilots, not a measurement. The pilots hold between 1.1 KB per node (kg, 3,121 nodes) and 4.0 KB per row (beans, 723 rows). At those rates, the 273,559 upstream items would make one file of roughly 298 to 1071 MB, before any per-bitstream row. That is about 60 to 214 times the budget.

Recommended, not built: split by subgraph. A slice is one SliceDef, and nothing in the builder requires a slice to be a whole graph. A DSpace community or collection is already a directory-shaped subgraph, so the natural cut is one slice per community or collection. If one of those is still over budget, split it at the next level down. Do not split by row count: a slice should match a subgraph IRI a reader can name. Each split slice keeps the full contract, with its own manifest, row digest and determinism check. A small routing slice would let one search span all of IRIS. It would hold only titles, identifiers and the subgraph each item belongs to, so the client can then open the one slice that has the rows. That is the skeleton pattern again, one level up.

This section has been corrected twice. It first said that only the manifest needs a short TTL, because the client keys its copy by sha256. That held for the browser’s OPFS copy, not for a CDN: the slice file was then published at the same path every build, so a CDN could serve old bytes against a new manifest, the client would refuse them on the sha256 check, and search was down until the cache expired. That is now fixed (bean wixl). The slice file is published at assets/slices/<slice>.<sha256>.sqlite3, and the manifest’s file names it. A fresh manifest names a file no cache has seen. A stale one names an older file that still matches it.

Why not under /payload/sha256/: a payload is a node’s body, linked from that node and removed once nothing links to it. A slice file is linked from no node, so the payload tree would treat it as an orphan. It takes the payload rule that matters, immutable bytes at a hash-named address, without joining that tree.

What a CDN can still hold, as built: for one manifest TTL, a stale manifest together with the older file it names, which is a consistent pair. It can also hold an older file that nothing names until that file expires, or a stale manifest whose file the origin has stopped serving. The page reports that last case as a 404 and asks for a reload. A manifest that names a file with a different sha256 is refused with a visible message, never opened. Each deploy writes only the current file. Old ones do not pile up on the host. GitHub Pages sends max-age=600 for every file and cannot be told to send anything else, so on Pages the manifest’s short TTL is ten minutes.

No CDN layer has been chosen (bean l9v6, still proposed). Whichever one is chosen stands in front of the publication host, as above. The slice files and payloads go out through the same publish-to-CDN step as every other page (bean 7dek, Process_RenderKgToCdn), behind the same four gates (bean xies). The URL-layout check that xies asks for must therefore cover /payload/sha256/ and assets/slices/ too.

How a client picks a slice

As built: assets/slices/index.json (folio-slice-index/v1) lists every slice built into the site. The one search page, slices/search.html?slice=<name>, lists them when no slice is named. Given a name, it reads everything else it needs from the search block of that slice’s manifest. The reader picks. The page checks the name against a pattern before using it in a path.

Recommended for who-iris, not built: keep the reader’s choice, and make the choices follow the catalogue’s community and collection tree. A reader browsing a community opens that community’s slice, named in its index.jsonld. A reader searching all of IRIS opens the routing slice first. Several slices can be open at once, because each is its own file in the pool. What that costs on a phone has not been measured.

What is deliberately not decided

The ingestion method is undetermined, and the process diagram reaches a gateway with no default branch rather than naming one. A pull from the portal, a push to an object store, a git fetch, a signed tarball on a schedule — they differ in who initiates, in what must be reachable from where, and in what happens when a publication is missed. Drawing one as the obvious branch would record a decision nobody made.

The store must be versioned; which store is a deployment choice. Hosted git is one satisfaction of that requirement, not the requirement. A portal showing a graph needs to be able to say which graph — an unversioned store cannot answer “what did this look like last term”, and that is the question a reading list asks every year.

Nothing here was measured against a live CDN. cdn.jsdelivr.net is egress-blocked from the container that generates these pages, so every CDN figure would be quoted rather than measured. The owner confirmed one link by hand on 2026-09-20, and that is the whole of the evidence.

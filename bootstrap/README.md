# bootstrap

## What is about to happen to this repository

Somebody wants this repository set up to write something — a paper, a policy
document, a guideline — with an agent helping. Right now it is just a folder.

**Bootstrapping is the setup step.** When it finishes, this repository will
have a small file saying what kind of thing it is and where to find the
instructions for working on it. Nothing else about it changes: your files stay
where they are.

The instructions are called a **harness**. A harness is a set of written
procedures an agent follows — how to draft a section, how to check a claim,
how to publish. Harnesses live in their own repositories, and this repository
will point at one rather than contain a copy.

## What you need from the person

**One thing: the name of the repository to copy the setup from.** For example
`litlfred/cat-harness`, or `litlfred/f-a-sci`.

> **"make this repo into a `litlfred/f-a-sci` instance"** — that is a complete
> answer. Nothing else needs asking.

You do not need to ask what kind of document they are writing, which
procedures to load, or what style to use. The repository they name already
says all three, and you will read it in step 3.

If they have not named one, ask for it in those words — the name of a
repository — and not for a kind of document. If they answer with a kind
("a paper", "a guideline"), tell them which repositories you know of and ask
them to pick one.

## Do this

1. **Read [`skills/kg-navigation.md`](skills/kg-navigation.md).** It explains
   how to open the files in step 2 and 3. It needs nothing but the ability to
   read a file — no tools, no server.

2. **Open [`bootstrap.jsonld`](bootstrap.jsonld)** and find the entry whose
   `@type` is `Process`. It names a file. (The file is generated by
   `bun run bootstrap:graph` and committed, because its reader has nothing
   installed and cannot run a build.)

3. **Open that file and follow it.** It is a short diagram with two branches:
   if this repository is already set up, load what it says and stop; if it is
   not, get the repository name from the person, read *that* repository's
   setup file — the next section says exactly where it is — and write this
   one's from it.

That is all of it. Step 3 ends with this repository set up.

## Where the other repository's setup file is

**Always the same place:**

```
<name>/docs/bootstrap/initialization.md
```

`<name>` is the `name` in that repository's `harness.json`. So if you were
pointed at `litlfred/f-a-sci`, and its `harness.json` says `name: f-a-sci`,
you open `f-a-sci/docs/bootstrap/initialization.md` inside it.

**It is always there, so you never have to search and never have to ask.**
That is the point of fixing it: you are given one repository name, and
everything after that is read rather than negotiated. A repository that keeps
its setup instructions somewhere else cannot be bootstrapped into by anyone who
was not already told where to look — which defeats being given a name.

It also means you can be pointed at a **kind of harness nobody has written
yet**. You do not need to know what `f-a-sci` or `smart-base` is, or how they
differ; each keeps its own instructions at that path, in its own words, and you
read whichever one you were sent to.

If the file is not there, that is the "something does not resolve" case below.
Do not guess, and do not fall back to another repository's instructions — they
would set this repository up as the wrong thing, which is worse than not
setting it up at all.

## If something does not resolve

Say so and stop. A file named here that is missing, or a name that does not
match anything, is worth reporting — it is not a gap to work around, and
guessing produces a setup nobody asked for.

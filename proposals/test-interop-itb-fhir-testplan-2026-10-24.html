Test plans, FHIR TestPlan and the ITB: one model, several exports

Draft, 2026-10-24. Not built.

Owner decisions, 2026-10-24 (all five answered):

  • D1 = S2. The system under test is a system/v1 record, and runs point at it.
  • D2 = B7 → B5, an option added after the first draft. Each test is tagged in its own code with the assertions it verifies (for example @verifies("req:stt-ver-001#statement/test")). A Tool reads the tags and writes the assertion-to-test map onto each system/v1 record, and CI fails when the map is stale. There is no separate test-binding/v1 node, and the plan never names an implementation. Where section 4 below says test-binding/v1, read “the bindings on the system/v1 record”.
  • D3: cat-harness-tools. The ITB export and the TAR import live in the tools layer.
  • D4 = I1. Plans reach the ITB through OpenTestBed Gherkin.
  • D5 = P3 first. smart-trust-tools tries the fields locally first. The schemas move into cat-harness once they are proven there.

It answers four owner questions of 2026-10-24:

  1. How do test-plan/v1, FHIR R5 TestPlan and the Interoperability Test Bed (ITB, GITB TDL) fit together? Can FHIR TestPlan sit downstream of the ITB? And what does the OpenTestBed organisation already provide?
  2. What are the options for the “system under test” schema?
  3. smart-trust-tools has a test plan that is partly narrative. What formal schema captures it, attached to skills such as hcert-verify, including the Rust library exposed as an MCP service?
  4. Where do machine QA results and the model benchmark fit (model swarm and benchmark, PR #500)?

The short answers:

  • One model, several exports. test-plan/v1 stays the one place a plan is written. FHIR TestPlan and GITB TDL are both generated from it, as siblings. That is what OpenTestBed’s own compiler already does from Gherkin.
  • FHIR TestPlan can sit downstream of the ITB, by reference. A TestPlan’s testCase.testRun.script can point at the GITB test case that executes it. The ITB then runs the plan, and the TestPlan describes it. Converting TDL into TestPlan is lossy and is not recommended.
  • The system under test becomes a node (system/v1): a system, its versions, the actors it plays and the surfaces it exposes (library, WIT component, MCP server, CLI, HTTP). A run names the system, version, actor, surface, target and, for agents, model and configuration. This is the ITB’s own model (a system playing an actor in a conformance statement), so the ITB export is a mapping, not a translation.
  • smart-trust-tools is already mostly formal. Its two plans are test-plan/v1 nodes generated from the skills and the requirements’ success criteria. What is still prose is: the test level of each case, the implementations and targets each case runs on, and the named test that stands for each assertion in each implementation. Three additive fields and one new node, test-binding/v1, make all of it checkable. An MCP server is then one more binding of the same plan.
  • Machine QA and the benchmark reuse the same plan and run records. A machine QA criterion is an assertion id, a fixed finding becomes a regression case, and a benchmark is several runs of one plan against several systems under test.

In smart-trust-tools

The plan is more formal than “narrative” suggests:

  • test/plans/hcert-library-conformance.test-plan.json is a test-plan/v1 node with 15 cases, one per skill (hcert-verify, hcert-sign-cose, vhl-share, …). It is generated by the test-plan Tool (tools/test-plan/make_test_plan.py) from the skills’ satisfies lists and the requirements’ success criteria, and CI fails if it is stale.
  • Each assertion id is a success-criterion address, req:<id>#<statement>/<criterion> (for example req:stt-tst-009#statement/verify). A verdict on an assertion is therefore a verdict on a criterion.
  • test/plans/who-itb-agreement.test-plan.json compares the library with WHO-ITB’s three HCERT tracks. It has the first plan as its predecessor.
  • check:req-nodes checks that each assertion names a criterion, each data path exists, and each predecessor names a plan.

What is still prose, in test/plans/README.md and in the assertions’ expectation text:

  1. The test level of each case: skill tests, conformance vectors, negative vectors, fuzzing, coverage floor, targets, cross-implementation, one TypeScript suite, schema checks, WHO-ITB agreement. This is a table in the README.
  2. Which implementations and targets a case runs on: Kotlin on JVM and Node, Rust on native and wasm32, and Android, which is named but not run. The assertions read “passes in each implementation’s suite”.
  3. Which test stands for an assertion: the convention that a test is named after its requirement (STT-PAY-001 …), with the Kotlin test names pasted into the expectation string. Nothing checks that the named test exists or that each implementation has one.
  4. The library’s interface: the operations a skill uses are listed in each skill page (verifier.verify, trust.trust-store, …, from api/wit/). The plan does not say which interface it tests, so it cannot say that an MCP server exposing the same operations can run it.
  5. Release-review criteria (verification inspection or review) are left out of the plan “to be judged at release” (bean oi32). Nothing records the judgement yet.

In OpenTestBed (read only; an outside organisation)

The ITB’s data model: domains → specifications → actors → test suites, on one side. Communities → organisations → systems, on the other. A conformance statement is one system against one actor of one specification, and test results accumulate against it.

The fact that decides the architecture: OpenTestBed treats FHIR TestPlan and GITB TDL as siblings compiled from one source (Gherkin plus a plan config). It does not derive one from the other.

Can FHIR TestPlan be downstream of the ITB?

Yes, in one precise sense, and no in another.

  • Yes, by reference. FHIR R5 TestPlan.testCase.testRun.script names the script that executes a case: language and source[x], which can be a canonical, a URL or a reference. The export can set it to the GITB test case that the ITB export generated (language GITB-TDL, a URL into the ITB package). The TestPlan then describes a plan that the ITB executes. That is downstream in the sense that matters: the TestPlan points at the ITB, and the ITB does not need the TestPlan.
  • No, by conversion. Generating a TestPlan from TDL would lose the requirements, the criteria and the exit rule, which TDL never held. OpenTestBed does not do it either.

So the export order is: test-plan/v1 → GITB TDL first, then FHIR TestPlan, with testRun.script pointing at the TDL. When a plan has no ITB route, the TestPlan’s testRun.narrative says how it is run instead.

Two routes to the ITB

RouteGainsCosts
I1Emit Gherkin features and an OTB plan config from test-plan/v1, and let otb-gherkin compile them to TDL.Reuses OTB’s compiler, dialects and plugins (hcert-decoder, fhir-validator, jwt, oauth). Output matches what WHO-ITB users already deploy.Each assertion needs a Gherkin step that a dialect implements. Where no dialect fits, the case cannot go to the ITB.
I2Emit GITB TDL directly.No dependency on OTB’s toolchain.We would write and maintain a TDL emitter and our own ITB services.

Recommended: I1. It is the route WHO-ITB’s own community uses, and the HCERT plugin already exists. A case with no dialect stays in-house: its run is a folio-test-run, and the export marks it “not exported: no OTB dialect” rather than leaving it out silently.

Results coming back

C2’s default treats the ITB as an export of runs. This proposal adds the reverse direction for runs the ITB executes: import a GITB TAR into folio-test-run/v1, keyed by the conformance statement (system × actor). The certifier then judges an ITB run with the same DMN as an in-house run. A FHIR TestReport is generated from the run, not stored.

3. The system under test

What it has to say

Each run has to name everything a verdict depends on. For smart-trust-tools that means which implementation (Kotlin or Rust), which target (JVM, Node, native, wasm32, Android), which surface (direct library call, WIT component through jco, MCP tool call), and which version. For an agent it also means which model and which configuration (benchmark gap 1 in PR #500).

The options

ShapeGainsCosts
S1Widen SutRefSchema in place: optional implementation, target, surface, model, configuration (a hash plus a short map).Smallest change, and backward compatible.Every run repeats the system’s description. Nothing says which systems exist, so “certified on every target” cannot be checked.
S2A system/v1 node, plus a run reference to it. The node declares the system’s versions, the actors it can play, its surfaces and its targets. The run says which of each it used.This is the ITB’s model (system, actor, conformance statement), so the export maps one to one. It also lets a check say that a plan has a run for every declared target, which is the claim the smart-trust-tools README makes in prose.One more node kind, and every SUT needs a declaration before it can be certified.
S3Reuse FHIR Device or TestReport.participant.Nothing to design.Breaks the FHIR-free rule. It stays an export target only.
S4Reuse the deployment description’s placements (deployment descriptions, bean o1by).One registry for “what runs where”.A placement says where something runs, not what it is, so it answers a different question. A system/v1 should reference a placement, not replace one.

Recommended: S2, with S1’s fields as the run’s reference to it.

The shape (sketch) 

// schemas/system.ts (cat-harness): what can be tested
SystemSchema = z.strictObject({
  $schema: z.literal("system/v1"),
  id: SLUG,                                   // "hcert-rust"
  title: z.string(),
  kind: SutKindSchema,                        // skill | agent | tool | machine | ig | process
  implements: z.array(InterfaceRefSchema),    // e.g. "smart-trust-tools:api/wit/worlds.wit#hcert"
  actors: z.array(z.string()).min(1),         // roles it can play: "verifier", "issuer"
  surfaces: z.array(z.strictObject({
    id: SLUG,                                 // "library" | "wit-component" | "mcp" | "cli" | "http"
    kind: z.enum(["library", "component", "mcp", "cli", "http"]),
    entry: z.string().optional(),             // package, MCP server id, CLI, URL template
  })).min(1),
  targets: z.array(SLUG).default([]),         // "native", "wasm32", "jvm", "node", "android"
  placement: z.string().optional(),           // a deployment placement, when one exists
});

// folio-test-run/v1: sut widens to a reference (S1's fields, all named by the node)
SutRefSchema = z.strictObject({
  system: SLUG,            // a system/v1 id
  version: z.string(),     // the system version, or a commit
  actor: z.string(),       // one of the system's actors
  surface: SLUG,           // one of its surfaces
  target: SLUG.optional(), // one of its targets
  model: ModelIdSchema.optional(),                  // agents only (bootstrap/models)
  configuration: z.strictObject({ sha256: HEX64, summary: z.record(z.string(), z.string()) }).optional(),
  reach: z.enum([...NETWORK_REACHES, REACH_UNKNOWN]),
});

The current {actor, version, reach} runs migrate by adding system and surface. A converter can fill them in, because today’s actor is always a skill or agent name.

ITB mapping: system/v1 → ITB system; actors[] → specification actors; (system, actor, plan) → conformance statement; a run → a test session result against it.

4. A formal plan for smart-trust-tools, attached to skills

What is added

Three optional fields on test-plan/v1, and one new node.

AdditionOnWhat it replaces
skilleach test caseThe convention that the case id equals the skill name. kg-audit can then check that every skill with satisfies has a case, and that the case’s assertions cover those criteria.
leveleach test caseThe README’s test-level table. Values: skill, vector, negative, fuzz, coverage, target, cross-implementation, interface-suite, schema, agreement, review.
interfacethe plan’s scope“The library”, in prose. It names the contract the plan tests (the WIT world hcert, its operations), so any system that implements that interface can run the plan, MCP servers included.
test-binding/v1a node per systemThe test names pasted into expectation. It maps each assertion id to the selector that runs it in that system, per surface and target.

A sketch of the binding:

  "$schema": "test-binding/v1",
  "plan": { "id": "hcert-library-conformance", "version": "1" },
  "system": "hcert-rust",

    "native":  { "shell": "cargo test --manifest-path tools/hcert-rust/Cargo.toml" },

    "mcp":     { "shell": "node tools/conformance-ts/run.mjs mcp $MCP_SERVER" }
  },
  "bindings": [
    {
      "assertion": "req:stt-ver-001#statement/test",
      "case": "hcert-verify",
      "tests": [
        { "surface": "library",       "target": "native", "selector": "verify::stt_ver_001_valid_signature_verifies" },
        { "surface": "wit-component", "target": "wasm32", "selector": "conformance-ts:STT-VER-001" },
        { "surface": "mcp",                               "selector": "conformance-ts:STT-VER-001" }
      ]
    }
  ],
  "unbound": [                                  // said out loud, never left out
    { "assertion": "req:stt-gen-004#statement/test", "target": "android", "reason": "no Android runtime in CI" }
  ]
}

What becomes checkable that is prose today:

  • Every required assertion has a binding in every system that claims the plan’s interface, or an unbound entry with a reason. (Today: “87 of 94” is counted by hand in bean oi32.)
  • Every selector exists in that system’s suite. A Tool lists the test names (cargo test -- --list, the JUnit report, the TypeScript suite’s manifest) and compares.
  • The run records verdicts per (assertion, surface, target), so “passes on every target” is computed, not asserted.
  • The test-plan Tool keeps generating the plan, and gains a --bindings step that writes each system’s binding from the skills’ tested-by lists and the test names. CI fails if a binding is stale, the same as the plan today.

The MCP server

An MCP server that exposes the Rust library (for example verifier.verify as an MCP tool) is one more surface of the hcert-rust system: a surfaces entry of kind mcp, and a third runner in the binding. The TypeScript conformance suite already drives two packages through api/generated/ts. A third adapter in that suite calls the MCP tools, so the same 45 checks run through MCP with no new test text. The plan does not change, because it tests the interface, not the transport.

The agent that uses it

“Verify HCERT” is also something an agent can be asked to do, using that MCP tool. That is a different system under test (kind agent, with a model and a configuration), against a different plan: does the agent call the tool rather than decode by hand, report the tool’s reason faithfully, and refuse to call an unverified certificate valid? That plan’s cases name the same skill (skill: hcert-verify) and reuse the vectors as test data. It is also where the benchmark of PR #500 gets its first smart-* task (section 5).

Release-review criteria

Criteria verified by inspection or review become cases of level: review, in a separate plan run at release, whose witness kind is human. The certifier’s DMN treats a missing review verdict as undetermined, which is the existing rule. This closes the last part of bean oi32.

The WHO-ITB agreement plan

who-itb-agreement is the first plan that would use the ITB route (I1): its three tracks are already ITB test cases (tc-vhl-001, tc-icvp-001, tc-ph4h-qr-001). Once the data is usable (bean OI-33: no licence file yet, no pinned QR reader, the DEV trust list not reachable from CI), a tester runs the ITB and the TAR import records the result against the plan. Nothing in WHO-ITB or any WHO repository is changed.

A spec-kit success criterionAn assertion id of the form req:<id>#<statement>/<key>, exactly as smart-trust-tools already does (benchmark gap 5).

The first shared task for the benchmark: an agent verifies an HCERT through the MCP tool, scored against the smart-trust-tools vectors. It has fixed data, known right answers, negative cases with named reasons, and no WHO repository to change.

This page says how to render an implementation guide through the harness from a terminal, on your own machine or in an agent’s container. The output is the same just-the-docs site the publish workflow deploys.

A harnessed render has two halves:

  1. Build the IG’s AST once. This is the only step that runs the IG Publisher. It writes output-ast/, one JSON dump per resource.
  2. Render the site from that AST. The harness never reads the Publisher’s output/ HTML. The AST is the one input to the site build.

The steps below are listed in that order. To deploy the result, see Publishing an IG.

Harnessed or bare: two routes

✎ Edit

Harnessed (this layer)Bare (the IG Publisher alone)
When it is takenthe IG repository has an index.config.json naming its landing layer, "site": { "landing": "<layer>" }the repository has no index.config.json, or you pass --bare-ig
What runs the PublisherAstExportCli, an entry point added to a fork of the Publisher (litlfred/fhir-ig-publisher), pinned by committhe repository’s own ghbuild.yml steps (stock publisher.jar, latest release)
What the site is built fromthe AST (output-ast/, or the cache branch)the Publisher’s output/ as it lays it out
What you getthin just-the-docs pages, a JSON-LD node per artefact, the artefact index, search, a language pickerthe Publisher’s HTML
Version pinned?yes: SUSHI, Java and Node in scripts/ig-toolchain.env; the Publisher by the ast-export commitno: the version floats (see the IG Publisher)

Both routes start with one command, stage-local.ts. It takes the harnessed route whenever it can. Do not pass --bare-ig to a harnessed IG unless you want the Publisher’s own pages.

Building the AST also needs network access to packages.fhir.org, the terminology server (default http://tx.fhir.org) and Maven Central. If packages.fhir.org is refused, see the fhir-validation skill, §”When a package host refuses you”.

The layers come from the IG’s index.lock.json. From the IG repository’s root, mount them the way the publish workflow does:

ref=$(python3 -c "import json;print(next(m['ref'] for m in json.load(open('index.lock.json'))['mounts'] if m['harness']=='cat-harness-tools'))")
M=$(mktemp -d) && git -C "$M" init -q
git -C "$M" fetch -q --depth 1 https://github.com/litlfred/cat-harness-tools.git "$ref"
git -C "$M" checkout -q FETCH_HEAD
bun run "$M/scripts/mount-from-lock.ts" --root .

The one command

✎ Edit

From the IG repository’s root, with the layers mounted:

# 1. Build the AST (one Publisher run; minutes to tens of minutes)
bun run cat prepare:fhir-harness

# 2. See what would be built and where, and stop
bun run cat stage:local --repo . --plan

# 3. Build the site and compose the publish commit, pushing nothing
bun run cat stage:local --repo . --dry-run

bun run cat <name> runs a script that any mounted layer declares. prepare:fhir-harness is bash fhir-harness/scripts/ig-ast-build.sh --ig-root ., and stage:local is cat-harness-tools/scripts/stage-local.ts.

Other ways to finish:

CommandWhat it does
bun run cat stage:local --repo . --artifact <dir>writes a bundle you can open as a page, instead of pushing
bun run cat stage:local --repo .publishes. On the default branch it publishes the site root; on any other branch, a preview at branches/<branch>/

You can skip step 1 when the IG’s cache branch already holds an AST that is valid for your commit: the render restores it.

Step by step

✎ Edit

stage-local.ts runs these named steps in order. The layers supply them, so you can also run any one of them on its own with bun run cat <step>:

#StepScriptWhat it does
1ig-site:astig-repo-site.ts astrestores the AST from the cache branch cat/fhir-harness/fhir-ast/<package id> (or keeps a valid output-ast/), and refuses a stale one
2ig-site:sidecarsthe landing layer’s ownoptional: API sidecars from the AST, when the landing layer has this step
3ig-index:buildbuild-ig-indexes.tsthe artefact index, menu and releases in fhir-artifact-index/
4ig-site:composeig-repo-site.ts composethe thin artefact pages, with the IG’s own pages composed at the site root
5ig-site:openapicat-harness-toolsoptional: a page per OpenAPI operation, when the IG has openapi/cat-openapi.config.json
6ig-site:publisher-pagesig-repo-site.ts publisher-pagesserves the AST’s data, guards against leftover Publisher chrome, stamps the build
7ig-site:barig-repo-site.ts barthe language picker and the IG’s slim bar

The scripts’ own usage lines:

ig-repo-site.ts ast [--ig <checkout>] [--work <dir>]
ig-repo-site.ts compose <site source> [--ig <checkout>] [--baseurl <base>] [--plantuml-jar <jar>] [--work <dir>]
ig-repo-site.ts publisher-pages <built site> [--ig <checkout>] [--work <dir>]
ig-repo-site.ts bar <built site> [--ig <checkout>]

ig-ast-build.sh [--ig-root DIR] [--tx URL] [--ast-export-ref SHA] [--work DIR] [--template-repo ID=OWNER/REPO]…

To publish an AST you built yourself to the cache branch, so the next render and CI can reuse it (only from a default-branch commit):

bash fhir-harness/scripts/ig-cache.sh seed --ig-root . --push

When it refuses

Message or symptomCauseWhat to do

index.config.json has no site.landingthe IG is harnessed but does not say which layer’s chrome it wearsadd "site": { "landing": "<layer>" }
a prerequisite is missingdocker, python3 -m venv, bash or curl was not foundinstall it; the plan names which one
ig-ast-build: the AST just built is not validthe inputs changed during the buildcommit or stash, then build again
the Publisher cannot fetch a packagepackages.fhir.org is unreachablesee the fhir-validation skill, §”When a package host refuses you”

Exit codes of ig-ast-site.sh: 1 means no AST could be restored; 3 means the AST was restored but could not be turned into pages.

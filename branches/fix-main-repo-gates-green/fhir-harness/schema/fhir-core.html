Description

fhir-core.ts — the FHIR core specification's StructureDefinitions, one graph per STABLE FHIR release, keyed by canonical URL.

Owner, 2026-11-14: "fhir structured definitions and base resources etc should be loaded in fhir-harness for stable fhir releases to represent it as a harnessed KG." Owner, 2026-11-15: "i want to refer to HL7 offiically published .json etc for their resources, just use fhir-harness to derived stuff (e.g. UML) that is not part of core IG publisher"; "reference published hl7. assets as authoratative".

So HL7 is the authority and this layer holds three things, none of which restates a definition:

  • folio-fhir-core-pins/v2 (fhir-core/pins.json): HL7's own package for each release, at the URL HL7 publishes it (https://hl7.org/fhir/<release>/hl7.fhir.<r>.core.tgz), with the sha1 and sha512 of HL7's bytes. A mirror (the FHIR package registry) may be listed with ITS hashes; it only ever fills the cache. Stable releases only.
  • folio-fhir-core-release/v2 (fhir-core/<release>/manifest.json): what was read from HL7's package, one entry per StructureDefinition chosen by isCoreDefinition, keyed by canonical URL, naming HL7's published JSON for it, the file in the package and the sha256 of that file's bytes. A release whose package could not be fetched or verified is status: "unread" with the reason, and has NO definitions: unread is not empty.
  • folio-fhir-core-class-model/v1 (fhir-core/<release>/class-model.json): the UML class model, which HL7 publishes only as pictures, derived from the package and citing the definition and element of every node.

A local copy of the bodies (fhir-core/<release>/cache/) is a CACHE, labelled as one in the directory itself: written by fhir-core.ts materialise, never committed, each file held to the sha256 HL7's package gave it. resolve answers with HL7's URL, and names the cached file only when asked.

WHO-free: nothing here is an IG's, let alone WHO's.

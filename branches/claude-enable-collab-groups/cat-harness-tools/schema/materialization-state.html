Description

The materialization STATE vocabulary — whether the bytes are here, and how a held copy proves it is unchanged.

Only the vocabulary lives in the harness

The three states and FixitySchema are here because harness modules speak them (schemas/library/referenced-source.ts, cat-harness.ts, binary-release.ts). The rest — the five gates (size, restrictions, retention, source loss, copyright), the purposes, and the record that binds them — stays in the content core's schemas/materialization.ts, because each gate is a decision a person makes about CONTENT, asked in sample-import.bpmn. Core re-exports these names.

Three states

  • referenced — the node exists, we know where, we hold no bytes.
  • materialized — the bytes are here.
  • unknown — we have not established which.

Collapsing unknown into referenced reports a clean scan over content nobody looked for. Collapsing referenced into materialized is worse: corpus-grep searches library/ only, so a referenced node reads as ABSENT.

There is deliberately no default. A node that does not declare its state is invalid, not unknown.

A remote-KG subscription is a materialization

Subscribing to an external knowledge graph (kg-subscribe, subscribe-kg.bpmn, the kg-subscription skill) is a materialization whose MINIMUM is the chosen subgraphs' METADATA, held under library/<source>/. The chosen subgraphs are materialized as metadata; everything else the remote declares is referenced; a subgraph whose declaration could not be read is unknown. Taking more than the metadata is an ordinary materialization of those nodes, with core's five gates. No subscription feature reads this yet.

Description

The two documents the discussion process carries, as Zod.

These shapes describe bootstrap, and deliberately do not live in it

bootstrap/README.md promises a Bootstrapping Agent that it needs no harness, no server, no tools and no work plan, and that what it reads is "a file you read, not something you run". Measured: that directory holds .md, .json and .bpmn and no executable code. So its shapes cannot be Zod in it — owner, 2026-09-20, "bootstrap should not know zod at all". They live in this sibling layer, bootstrap-tools: Zod is an AUTHORING TOOL for the Knowledge Graph, "different tools can/will be used, but the core KG should be unchanged", and what bootstrap carries is only what it generates.

bootstrap/skills/discussion.*.schema.json is GENERATED from here. The $ids are unchanged and must stay so: they are a published contract, and the filenames are cited from discussion.bpmn, a harness's tool registry, the generated skill docs and .pot catalogues in five languages.

What Zod cannot carry across, and why it is handled rather than accepted

.refine() exports nothing to JSON Schema. Measured with zod-to-json-schema: no allOf, no if/then, no trace of the rule. The output document has two conditionals that a consumer relies on, so they are re-applied by the generator (JSON_SCHEMA_CONDITIONALS) rather than left to vanish. The refinements below are kept ANYWAY, because they are what makes the Zod type honest for anything validating in-process; the generator's table is what makes the published document honest. Two forms of one rule is a thing to be uneasy about, which is exactly why discussion.test.ts asserts the generated schema and the Zod schema agree on the same corpus of documents.

DiscussionInputSchema · JSON Schema

FieldTypeRequiredDescription
openarray of "harness" | "repositories"yesWhich unknowns this exchange is to settle. At least one, or there is nothing to ask.
askedOfobjectyesWho is being asked. The two participant kinds are symmetric — the same skill serves human-to-agent and agent-to-agent — but the answer's weight differs, so the kind is recorded rather than inferred.
askedOf.kind"person" | "agent"yes
askedOf.idstringnoSession id, handle or name, where one is known. Absent is normal for a person.
candidatesarray of stringnoHarnesses the agent has already narrowed to from context — a repository whose root already holds a declaration, <name>.json, is not a blank slate. Narrowing first is what keeps this to one question.
knownRepositoriesarray of objectnoRepositories already evident from the checkout, each with the part it is known to play. Offered so the participant confirms or corrects rather than recites.
knownRepositories[].urlstringyesClone URL or path. Not required to be reachable — a Bootstrapping Agent may have been told about a repository it cannot yet fetch.
knownRepositories[].role"read-from" | "written-to"yesWhich part this repository plays. A flat list loses the distinction, and the distinction is the whole reason for determining them: it is where the new declaration lands.
knownRepositories[].notestringno
contextstringnoWhat the agent read to get this far, in one or two sentences. Lets the participant answer without re-establishing the situation.

DiscussionOutputObjectSchema · JSON Schema

FieldTypeRequiredDescription
outcome"settled" | "unsettled"yesunsettled is a real outcome, not an error: a participant may decline, and the process has an end for it. What an unsettled result must never contain is a guess.
harnessstringnoThe harness this repository is to become — bootstrap, or any Harness built on it. Required when outcome is settled and harness was open.
repositoriesarray of objectnoThe repositories involved, each with the part it plays. Recorded as pairs rather than a flat list: read-from and written-to may be one repository or two, and which is which is the answer.
repositories[].urlstringyesClone URL or path. Not required to be reachable — a Bootstrapping Agent may have been told about a repository it cannot yet fetch.
repositories[].role"read-from" | "written-to"yesWhich part this repository plays. A flat list loses the distinction, and the distinction is the whole reason for determining them: it is where the new declaration lands.
repositories[].notestringno
determinedBy"asked" | "assumed"noasked means a participant said so. assumed is permitted only for a default the README itself states, and then assumption must say which. An agent that reaches for assumed because nobody answered has produced an unsettled result, not an assumed one.
assumptionstringnoRequired when determinedBy is assumed: the documented default relied on, and where it is stated.
answeredByobjectyesWho settled it. An answer from a sibling agent is evidence of a different weight from the person who wants the harness — both are admissible, neither is conflated with the other.
answeredBy.kind"person" | "agent"yes
answeredBy.idstringnoSession id, handle or name, where one is known. Absent is normal for a person.
exchangearray of objectyesWhat was actually put and what came back, in order. One entry is the expected case — the skill's rule is to ask the fewest questions that settle it.
exchange[].askedstringyesThe question as put, with its candidates named. A question a reader must go and research is not ready.
exchange[].answeredstringnoThe reply as received. Absent means the question was put and nothing came back, which is one route to unsettled.
exchange[].atstring (date-time)no
stillOpenarray of "harness" | "repositories"noRequired in substance when outcome is unsettled: what remains undetermined, so the next actor resumes rather than restarts.

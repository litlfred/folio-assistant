Description

Device screens: what one person sees on one device at a moment of a journey, as data.

What a device screen is

A screen is one device mock a room is shown beside a journey step: the phone a father holds the family's records on, the tablet a nurse scans a card with, the scanner at a gate. It is a node of its own (owner, 2026-11-06, option A) so any journey can have screens without an app of its own; the journeys viewer draws each as a static device frame, linked both ways with the walkthrough steps it shows.

| field | what | |---|---| | id | the screen's code, as a room calls it (S4, P4-scanner); its URL segment | | device | the frame it is drawn in: phone, tablet, scanner, desktop, kiosk | | owner | the actor whose device it is: drawn beside the device, with their avatar | | steps | the journey steps it shows, {scenario, step} | | blocks | what is on it, top to bottom: typed blocks, data only | | try | what to try on it in the room | | states | other versions of the screen a facilitator can switch to live (a tampered card, a wrong passcode) |

Blocks are data, never markup

A block is one of a closed set of types, each with typed fields; there is no free HTML, and an icon is a name from SCREEN_GLYPHS, a closed list the viewer draws. So a screen says WHAT is shown (a QR code signed by Thailand, a passcode with its digits hidden, a record list whose rows are a FHIR example's resources) and the viewer decides how it looks.

| block | shows | |---|---| | header | the app's name, a line under it, its brand colour and a status chip | | personCard | an actor (name and avatar from the actor's persona), with fields and chips | | qr | a QR code of payload, shown or being scanned, with a badge and a caption; may name the FHIR example it carries | | passcode | a passcode, its digits shown or hidden | | statusBadge | a verdict: verified, unverified, failed, emergency or info, with its detail | | recordList | rows of icon, label, code and status; may bind to a FHIR example's resources | | fields | labelled values, as a form shows them | | consent | who may see what until when, and whether it is granted | | alert | a message at a severity | | actions | buttons, labels only | | note | a line of small print |

A block may say column: "side": on a device wide enough (tablet, desktop, kiosk in landscape) the side blocks are drawn in a second column, as a clinical screen splits; on a phone or a scanner every block is in one column, in order.

States: the same screen, switched live

A room learns most from a contrast: the same verification screen with a valid card and with a tampered one. A screen's states are those other versions. The screen as its blocks say is the first state (labelled stateLabel, "As shown" by default); each entry of states is another, with an id (its URL value, ?state=tampered), a label for the switch, and what it changes:

| field | what | |---|---| | blocks | blocks that replace the screen's blocks with the same id | | hide | ids of the screen's blocks this state does not show | | try | what to try in this state, shown under the switch |

A block may also say only: ["locked"]: it is drawn in those states and no other (an alert that appears after the third wrong passcode). So a state never repeats the whole screen, only what differs, and the checks below see every block of every state.

What resolves, and where it is checked

owner, a personCard's actor, a step {scenario, step}, and a qr or recordList example are references; check:journey-refs (scripts/journeys/check.ts) resolves them as it resolves a journey's. Inside one screen the kind checks itself: a block id may appear once.

Every person on a screen is fictional, as on the journeys.

Description

Software libraries — one outside library a layer's code IMPORTS, at the version that layer's lockfile pins, with its licence, who imports it, and the type shim that types it. Never the bytes.

A node answers "which licence does this library carry, which files import it, and which shim types it" (e.g. types/bpmn-moddle.d.ts).

The core, extended

A library is outside-software's core — name, version, digest, source, SPDX licence and licenceSource — plus what only an imported library has:

  • range — the version range the layer's package.json asks for;
  • dev — whether it is a devDependencies entry;
  • usedBy — the layer's files that import it, layer-relative and sorted;
  • shim — the types/*.d.ts that declares it, when one exists;
  • vendored (1.1.0) — the directory its bytes are kept in, for a bundle the layer keeps rather than installs, which then has no range and no dev.

It is a NODE KIND (nodeKind()) whose one parent is the core's mixin, OutsideSoftwareKind. Two core fields are narrowed. name is an npm package name, which may be scoped (@scope/pkg), so its ref splits at the LAST @. source is a URL: a library comes from a registry tarball, never an OCI image. The digest is the core's own, so it may be sha512 — what bun.lock records.

Generated, never hand-written

A node is DERIVED from three inputs of the layer that imports it: its package.json (range, dev), its bun.lock (version, integrity, tarball) and the installed package's own package.json (licence). The writer is libraries:derive and the gate libraries:check, both in the tools layer.

One node per layer per library

Each layer keeps its own libraries/, declared in its own <name>.json, because each layer pins its own version in its own lockfile. A library two layers share has two nodes, one in each, which may disagree on the version.

The file name is not the name

A node is <file-stem>.library.json (libraryFileName), so its stem never equals its name field — the rule findDeclarationFile uses to recognise an instance declaration (directory-conventions, §"Every other marker"). The version is not in the file name, so a bump rewrites one file rather than renaming it.

A vendored bundle (1.1.0)

Some layers keep a library's prebuilt bytes in the repository rather than installing them — e.g. scripts/assets/vendor/<name>/<version>/, so a page makes no request to a CDN. The imports INSIDE those bytes are not imports the layer must declare.

A vendored node has vendored: { path } — the bundle's directory, layer-relative — and the same core: the name and version the bundle was taken at, the registry tarball, its digest, and its licence with where that was read. It has no range and no dev; every other node has both, so a missing range is never silently "vendored". A vendored node is stamped 1.1.0 (one stamped 1.0.0 is refused); a layer's own installed nodes are stamped 1.0.0 (librarySchemaTag). Both families are listed in the typology.

Its file is vendoredLibraryFileName — the version IS in the name, because a layer may keep two versions of one bundle side by side; a new version is a new directory.

A layer below the kind is held by the writer's layer (1.2.0)

A layer below this kind's layer (bootstrap-tools needs only bootstrap) may not name it, so it cannot declare a libraries/. Its nodes are held by the layer that owns the writer, under libraries/held/<layer>/.

A held node names the layer it describes in layer (the instance name, as needs names it); pages place the node under that layer. usedBy and shim stay relative to that layer, not to the holder. layer is present exactly on a held node, which is stamped 1.2.0 (librarySchemaTag).

✎ Edit

Publishing is the command-line render, run on a GitHub runner and pushed to the IG repository’s gh-pages branch. There is no separate recipe: the workflow runs the same stage-local.ts command that you run by hand.

GitHub workflows here are started by hand (workflow_dispatch). Nothing publishes on push.

Why binaries stay off gh-pages: GitHub Pages serves at most 1 GB. On one measured IG, 966.5 MB of its gh-pages was Publisher binaries copied into branch previews. See the ig-binary-artefacts skill.

What is published now

✎ Edit

This layer itself publishes:

  • These pages, on the platform’s documentation site: https://litlfred.github.io/folio-assistant/fhir-harness/.
  • Its JSON-LD context, which every node it writes points at: https://litlfred.github.io/fhir-harness/ns/context/v1.jsonld.
  • The reusable workflow and the templates, from the repository: .github/workflows/ and templates/ig-repo-site/.

An IG built on this layer publishes at its own repository’s Pages address, https://<owner>.github.io/<repo>/. Every such site has the same shape:

PathWhat it is
/the IG’s home page
/artifacts.html, /toc.htmlthe artefact list and the table of contents
/fhir-artifact-index/index.jsonthe artefact index, machine-readable
/artifact/<Type>-<id>.jsonldone JSON-LD node per artefact
/folio-build.jsonthe build stamp
/branches/<branch>/branch previews

The layers that build particular guides link their live sites from their own pages.

Deployment targets: GitHub Pages and Cloudflare

✎ Edit

GitHub Pages is the only target that is built and running. The publisher writes the site to gh-pages, and GitHub serves it.

The harness declares the targets it allows, so a new one is a declared option rather than a hidden switch:

  • PUBLICATION_HOSTS (in cat-harness-tools schemas/kg/cat-harness.ts): github-pages, local-server, jurisdiction-endpoint or none. A missing value does not default to github-pages.
  • ARTIFACT_STORE_KINDS (in schemas/sdlc/artifact-store.ts): github-release, object-store (R2, S3 and similar) or site-tree, each with publicBaseUrl, immutableUrls and cacheTtlSeconds. A store that is not declared is refused; it never falls back to GitHub.
  • The render-kg-to-cdn skill treats each CDN as its own Tool with its own process. Only the GitHub Pages Tool exists today.
OptionStatus for IG sitesHow it would work
GitHub Pagesin usegh-pages branch → https://<owner>.github.io/<repo>/. Limits: 1 GB per site, 100 MB per file

Cloudflare Pagesnot set upconnect Cloudflare Pages to the IG repository’s gh-pages branch with no build command, so it serves the same files from Cloudflare’s edge. Nothing in the pipeline changes
Cloudflare R2 + CDNnot set up for IG sitesupload the built site, or only the release binaries, to an R2 bucket as an object-store artifact store. This would be a new deploy Tool, run with wrangler

One layer in this checkout already deploys to Cloudflare: the WHO IRIS mirror’s iris-cdn.yml puts content-addressed files into R2 and keeps its release history in a git repository on Cloudflare. It is a model for an R2 target, not an IG deploy.

Two things carry over to any host. The site is built for one base URL (SITE_BASEURL, for example /<repo>), so serving it from another path, such as the root of a custom domain, means building it with that base URL, not copying the files. And Cloudflare Pages caps each deployment’s file count (at the time of writing, 20,000 files on the free plan) and file size (25 MiB). An IG with many artefacts and languages can pass the cap, so count the files on gh-pages first.

Before choosing Cloudflare, decide three things: who holds the API token (it is a repository secret, never in a file); whether previews (branches/) move too or stay on GitHub; and whether the canonical URL changes. A canonical URL that moves breaks every link already published.

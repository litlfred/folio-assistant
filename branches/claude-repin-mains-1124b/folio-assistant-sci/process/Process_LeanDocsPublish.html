summaryBuild a folio's Lean render — the doc-gen4 HTML of the Lake packages the folio holds — keep it on its own branch store, and publish it inside the folio's site with the harness navbar and rail.
descriptionBuild a folio's Lean render — the doc-gen4 HTML of the Lake packages the folio holds — keep it on its own branch store, and publish it inside the folio's site with the harness navbar and rail. The visualiser is the Lean KNOWLEDGE-GRAPH viewer (owner, 2026-11-19: "use thin html and dynamic loading"): lean-kg-publish turns doc-gen4's per-module declaration data into one viewer page and JSON shards the page loads on demand. doc-gen4's static HTML is a non-default fallback only. Three places, and each step says which it reads and writes. The SOURCE is the Lake packages in the folio's own tree (folio/<paper>/lean/), never moved. The RENDER lives on a branch store the folio declares (a directory of graph typology lean with source: { kind: "branch", keyedBy: "tip" }, on a branch under cat/folio-assistant-sci/), mounted at the declared path by state:mount exactly as beans/ is; it is never committed to the folio's main. The PUBLISHED pages are the site's route named by that declaration's coverage.visualiser (_site/lean/index.html → lean/). The build is a Lake run over the folio's warm olean cache: expensive, and able to damage the cache (a Lake build over an untraced restore evicts it), so it sits with the Lean toolchain and refuses rather than risks. Its output is pushed to the branch store (branch-store.ts push --id <id>), so a site build needs no Lean toolchain at all: it mounts the store and rails the render, a file pass that cannot touch the cache, after the site is built and before the chrome check and deploy. A site rebuilt without a Lean change starts at the mount. Only End_Ready publishes: a refused guard, a failed build, a store that did not take the push, a mount that failed and an unrailed page are each reported as such, never as a complete site without Lean docs.

Description

fhir-core.ts — the FHIR core specification's StructureDefinitions, one graph per STABLE FHIR release, keyed by canonical URL.

Owner, 2026-11-14: "fhir structured definitions and base resources etc should be loaded in fhir-harness for stable fhir releases to represent it as a harnessed KG."

Two families, both in the fhir-core-definitions typology:

  • folio-fhir-core-pins/v1 (fhir-core/pins.json): which package each release is read from — hl7.fhir.r4.core#4.0.1, hl7.fhir.r4b.core#4.3.0, hl7.fhir.r5.core#5.0.0 on packages.fhir.org — with the registry's sha1 shasum and the sha512 integrity of the tarball's bytes. Ballots and previews are not pinned: a stable release only.
  • folio-fhir-core-release/v1 (fhir-core/<release>/manifest.json): what was read from that package, one entry per StructureDefinition chosen by isCoreDefinition, keyed by canonical URL, naming the file it is materialised to and the sha256 of its bytes. A release whose package could not be fetched or verified is status: "unread" with the reason, and has NO definitions field: "could not determine" is never an empty graph.

The StructureDefinition bodies themselves (fhir-core/<release>/ StructureDefinition-<id>.json) are the package's own bytes, unmodified, so the manifest's sha256 checks them; they are materialised by fhir-core:materialise and not committed (12 MB of JSON across the three releases, every byte of it already pinned by the package hash).

WHO-free: nothing here is an IG's, let alone WHO's.

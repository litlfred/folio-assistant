l3-dependency-choice

Skill id: l3-dependency-choice · Package: authoring-who-smart-guidelines · Stage 5 of smart-guideline-end-to-end, task Task_DepsL3 of smart-guideline-end-to-end.bpmn (opt-in smart-base.collab). Adjudicated by the FHIR modeller and the terminologist.

The L3 half of l2-dependency-choice: the same decision row, reuse-first precedence, decision-comparison table and DecisionRequest, with IGs as candidates and an IG index as evidence.

Input and output

The contract is input.schema.json and output.schema.json.

  • In: the l1Kg (stage 2), the l2Assets (every stage-4 l2-dak-authoring pass’s artifacts), stage 3’s l2Dependencies, and any candidate IGs already known.
  • Out: l3Dependencies (level: L3), rows of the same dependencyRow whose components name canonicals, and indexes, the ig-artifact-ingestion index each row was read from, with its sidecarApi state. Stage 6 (fhir-harness l3-fhir-authoring) reads the adjudicated rows as sushi-config.yaml dependencies.

Steps

  1. Candidates. Those given, plus each IG that implements a DAK stage 3 chose to reuse, adapt or extend.
  2. Index each one with ig-artifact-ingestion. The index is the evidence; an IG whose root was never read has sidecarApi: unknown, which is not absent.
  3. Match. For each L2 asset and L1 node, find the profile, value set, CQL library or PlanDefinition in the index that already implements it. The matches are the row’s evidence; what is taken is its components (reuse, adapt, extend, not-used). For each artefact type taken, record the toolchain stage 6 will use: how the candidate builds and tests its CQL and examples, found by the search in smart-base-tools §Adapting a DAK.
  4. Decide, table, ask and go on, exactly as l2-dependency-choice steps 2–4.

smart-guideline-end-to-end

Skill id: smart-guideline-end-to-end · Package: authoring-who-smart-guidelines · Process: smart-guideline-end-to-end.bpmn

This skill holds the order of the stages, the hand-off between them and the adjudication rule. What a stage does is in its own skill; if a stage needs something its skill does not say, fix that skill, not this one. Every record uses an existing schema (What it reuses).

Input and output

The contract is input.schema.json and output.schema.json.

  • In: the request, verbatim; the useCase when stage 0 is already done; the guideline’s feature branch.
  • Out: every stage’s artefact under the name the stage table gives it (useCase, l1Sources, l1Kg, l2Dependencies, l2Assets, l3Dependencies, ig, applicationBrief, wireframes, application), and one adjudications entry per stage with its QaReview and outcome. The guideline is done only when no outcome is pending.

The rule that shapes everything: adjudication is QA, not a gate

Every stage ends in a fork: the agent goes on to the next stage while a person adjudicates the last one.

stage n (agent) ──┬──► stage n+1 (agent)          keeps going
                  └──► adjudicate stage n (human)  runs beside it
  1. Every stage is adjudicated, and the guideline is not done until every adjudication is recorded. Not waiting is not skipping.
  2. An asset built on unadjudicated input says so. Each derived KG node names its inputs in wasDerivedFrom (hash-pinned; smart-base/L1/schemas/graph.ts); the edge’s open properties carry adjudication: pending until the input’s review closes.
  3. A rejection reopens the stage, and the flag spreads downstream. A request-changes or reject decision files a bean against the stage. Every asset derived from the rejected item gets adjudication: rejected-upstream on that edge and is re-derived when the stage is redone, not deleted ahead of time: the re-derivation may come out the same.
  4. The agent never adjudicates. It may prepare the review material; the verdict is recorded by the person in the role the stage table names.

The order is a rule: L1, then L2, then L3

QA-not-a-gate is about verdicts. It never licenses skipping a stage.

  1. Each stage’s output exists before the next stage starts. Stage 2 writes the L1 extraction for every source of the use case; stage 4 writes the L2 assets; only then does stage 6 write FSH, CQL or any other L3 file. Source documents (a schedule poster, a slide deck) are stage-2 input, never direct input to L3.
  2. Sign-off is requested before the next stage starts. Each asset’s review item (Process_Review) is opened, staged and handed to its adjudicating role. The verdict is not awaited, but an asset whose review was never requested has not finished its stage.
  3. Every L3 asset names the L2 asset it implements, and every L2 asset the L1 node it rests on, in wasDerivedFrom with the edge’s adjudication state. An L3 asset with no L2 upstream is a finding, even with a green build and passing tests.
  4. A request that skips stages is still this process. “Adapt X to using these documents" is stages 0–6. If the request names no L1/L2 work, the agent does it anyway and says so.

A new repository carries a pointer to this skill and a platform mount (smart-guideline-create §6).

In l2-dak-authoring.bpmn the Clinically accurate? decision runs beside assembly: a parallel fork after the authoring join starts clinical validation and assembly together. changes needed sends the work round again, re-assembling the DAK; validated ends in its own event.

Between stages 5 and 6, Task_L3Ready runs l3-readiness (in: l1Kg, l2Assets, the reviews requested and the L3 artefacts about to be written; out: ready and the findings), and Gateway_L3Ready decides on it. No goes back to stage 4.

Publication of the IG (the end of dak-l3-ig.bpmn) is not on the path to stage 8: an application can be built against an unpublished IG.

Every adjudication calls cat-harness’s generic review, Process_Review (processes/content/review-task.bpmn), which runs the review that fits the change and accepts or sends back; disagreement goes to Process_Adjudication.

Staging: every review looks at a staged preview

Each stage commits to the guideline’s feature branch, which feature-staging (Process_FeatureStaging) stages on the site its section Which site names: a guideline in its own repository on that repository’s Pages, smart-base itself by a staging re-pin on folio-assistant’s site. An IG repository’s site needs its AST cache seeded first (fhir-ig-create, new-repo step 5).

The IG Publisher’s branches/ preview (ghbuild.yml, /deploy) is never the preview for this content. A review item links to the staged page through staging-review, which returns before (main) and after (staging) URL pairs. A new guideline with no repository yet is staged inside the current one first (in-repo, a staged sub-KG, the smart-guideline-create default).

Per-asset review

Every asset a stage creates or changes gets its own review item; one reused unchanged gets none. The review item shows the asset on the staged preview the way its reviewer reads it, not as source. At L2 it is a run of l2-component-edit-review.bpmn, whose skill gives each row’s checker, renderer and reviewer:

Forms are designed as wireframes at L2

A data-entry form is designed once, at L2, and the L3 Questionnaire is derived from that design.

  1. Stage 4: design. For each business-process activity where a persona records data, the agent runs wireframe-design-review in its design use, with intent from the L2 assets: the persona (who), the activity and its user scenario (what they do), and the core data elements it captures (what it shows). That gives two or more candidates, each with a web and a mobile layout, using real content: data-element labels, value sets and the DMN rules that show or hide a field. Each field carries the id of its core data element in a data-element attribute. The agent goes on with its recommended candidate; the review and the choice (Process_Adjudication, Process_OptionsAnalysis) are that form’s stage-4 adjudication.
  2. Stage 6: derive. The Questionnaire follows the chosen wireframe: one item per field, in its order and grouping, each item’s definition pointing at the logical-model element of the same core data element, and enableWhen taken from the same DMN rules.

  3. Stage 6 review: fidelity. fhir-harness’s skill fhir-questionnaire-wireframe (Process_QuestionnaireWireframeReview) runs on each built Questionnaire with the chosen wireframe. Its check, check-wireframe-questionnaire, pairs the wireframe’s data-element attributes with the items’ definitions (or code[].code), per data-layout; a field with no item, an item with no field, or a different order is a finding:

    bun run fhir-harness/scripts/check-wireframe-questionnaire.ts <wireframe.html> <Questionnaire.json>

If the chosen wireframe changes later, the Questionnaire derived from it is flagged rejected-upstream. A change request on either side (✍ suggest or the questionnaire-change issue form) says which side was edited, and the other is brought back in line (fhir-questionnaire-wireframe, step 7).

An adaptation is reviewed as a diff. When the asset came from a stage-3 or stage-5 dependency with decision: adapt, the review item shows before (the upstream asset at its pinned version) and after side by side, with the change highlighted and the L1 node that justifies it. At L3 the diff is fhir-harness’s ig-ast-delta (element-level, per resource); at L2 and for anything rendered, before-after-preview with a DiffRenderer (cat-harness-tools/schemas/ui/diff-renderers.ts). A changed asset with no L1 justification is a finding: the KG must say whether an adaptation is local evidence or local policy.

The record of a review item is a cat-harness QaReview (qa-review/v1, cat-harness-tools/schemas/sdlc/qa-review.ts): subject is the asset, and each verdict is a Decision whose role is the adjudicator’s role id:

outcomemeaning here
approvethe asset stands
request-changesreopen the stage for this asset. If the reviewer wrote the fix themselves, it goes in an AuditNote and the agent applies it as given
rejectthe asset is wrong at the root (wrong source, wrong dependency). Reopen the stage that chose it

At L1, recommendation-extraction keeps its review: {by, at} fields on the mapping; the QaReview records the stage’s review beside them.

New guideline or adaptation: one process

An adaptation is this process with stages 3 and 5 returning adapt decisions, so stages 4 and 6 show diffs. A new guideline is the case where those stages return only reuse, extend or nothing.

What this does not change

  • The WHO DAK component set and L1–L4 layering: smart-stack-layering.
  • How a new repository or IG is set up: smart-guideline-create. Run it before stage 4 if the guideline has no home yet.
  • The persona-swimlane lifecycle (planning, QC, translation, publication) on the IG’s Authoring Process page. This process says what goes into its phases 2a and 2b, and what comes before and after them.

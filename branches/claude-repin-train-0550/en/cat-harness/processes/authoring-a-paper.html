Authoring a paper

Process_PaperAuthoring · advisory · 11 step(s)

How a scientific paper or book folio is authored end to end, with Lean for its formal claims and LaTeX for its typesetting. Source of truth: this file. Open it in bpmn.io, Camunda Modeler, or any other BPMN 2.0 tool. The SVG under docs/assets/img/workflows/ is generated from it by bun run cat render:bpmn — never hand-edit the SVG. The <bootstrap.processes:skill> extension on an activity names the folio-assistant skill that implements it; <cat-harness.processes:bean> marks a step that reads or writes the shared work plan in beans/.

Review, publish and committee feedback are core’s shared Process_FolioReviewPublish, called after rendering. Its no answer, changes asked, comes back to Task_AuthorBlocks.

Lanes — who acts

lanerolewhat it does here
Author (person)authorThe plan set here — chapters, the blocks each needs, what gets formalised — is not revisited: GW_Published’s ‘no’ branch re-enters Task_AuthorBlocks, not this lane, so a scoping mistake surfaces only as rework downstream.
Work plan (beans)work-planOpens and claims the bean, then turns the author’s plan into beans, so a resumed session or another agent can pick up Task_Scaffold.
Authoring agent (system)authoring-agentScaffolds the repo from the author’s plan and writes every block, including every revision: GW_Published’s ‘no’ branch returns here, not to Lane_Author.
Lean toolchain (lean-mcp)lean-toolchainOwns its own loop: Gateway_LeanGreen, computed by decisions/lean-build-gate.dmn from the build result, sends ‘not yet’ back to Task_Formalize. The paper reaches Task_Validate only when it says green.
Build pipelinebuild-pipelineValidates and renders the Lean-green manuscript, calls the shared review-and-publish process (Call_ReviewPublish), and closes the bean once GW_Published says yes. It decides nothing itself.

Seed the work plan
Task_SeedPlan		Work plan (beans)todo-managerThe plan becomes beans, so a resumed session or a sibling agent can pick it up.
Scaffold the folio repo
Task_Scaffold		Authoring agent (system)content-planCreate the folio repository with bun run cat init-folio (or the folio_init tool): content/, the document, chapter and first block manifests, the builder shim, AGENTS.md, .mcp.json, the session-start hook and the beans store, with the platform linked rather than copied.
Author blocks
Task_AuthorBlocks		Authoring agent (system)content-authorEvery block edit runs the HCI validation gate — see editing-hci-validation.bpmn.
Formalise in Lean
Task_Formalize		Lean toolchain (lean-mcp)lean-formalization
proof-verification		Give each formal block (definition, theorem, lemma, proposition, corollary, conjecture, proof) a .lean sibling that Lean 4 accepts, in the order lean-formalization sets out. A compiling declaration is not a formalised claim: check vacuity and narrative drift before calling it done, and record the status with proof-verification.
Validate
Task_Validate		Build pipelinecontent-validateRun content validation over the folio: schemas, the content profile (formal kinds only in a paper), cross-block consistency and that the Lean builds. Loop back rather than rendering over a failure.
Publish extracted statements
Call_PublishStatements		Build pipelinecalls Publish extracted statements with source links
publish-extracted-statements		The paper draws on library sources; every statement quoted or extracted from them is published in an appendix page of the paper and in the shared extraction viewer, each linked to its library entry and section, before the paper is rendered. These pages are EXPOSITION about sources, never part of a proof: nothing published here enters a formal statement or its Lean sibling. The sub-process is core’s, the same for every content type; the paper supplies only the page look.
Render PDF and HTML
Task_Render		Build pipelinelatex-authoringTypeset the paper through LaTeX to PDF and HTML. Run latex-preflight first to catch compile-breaking source patterns before a full compile. The preamble, class and macros belong to the folio, never to the platform.
Review and publish
Call_ReviewPublish		Build pipelinecalls Review and publish a folio
content-review		Core’s shared review-and-publish process (Process_FolioReviewPublish): the reviewer reads the rendered folio and approves it, asks for changes, or sends a working draft to the Authoring Committee.
Close the bean
Call_BeanClose		Build pipelinecalls Close the bean
todo-manager		Process_BeanClose: end the bean in a state that says why — complete and archive it, scrap it with its reasons and archive it, or record the blocker and hand it back. The one place resolve and archive are drawn; placed straight before the end so the engine’s resolve sees nothing left but the archive step.

Decisions

decisionwhat decides itbranches
Bean claimed?
GW_BeanYours		Reads which end Process_BeanOpen reached. claimed: the bean is in progress and this process works it. not yours: a sibling session or a human holds it, nothing was written to it, and this process stops here rather than work a bean it does not own (bean-coordination).claimed → Seed the work plan
not yours → Not yours: left alone
Build green, no sorries?
Gateway_LeanGreen		Answered by the Lean build after formalisation: is it green with no sorry left? not yet loops on formalisation; green goes on to validation. A build that passes with a deferred (closeable) sorry is not green; a sorry standing in for an open conjecture does not hold the gate.not yet → Formalise in Lean
green → Validate
Published?
GW_Published		Reads which end Process_FolioReviewPublish reached. yes: Published, so the bean is closed. no: Changes asked, or Feedback in, so the work goes back to Task_AuthorBlocks with the feedback.yes → Close the bean
no → Author blocks

Every reference a journey or a workshop names resolves

Read every user-scenario and workshop node in the checkout through the layers’ declared directories, with the journeys viewer’s own resolver, and resolve what each names: actors (personas, a step’s lead, experiences[].actor, handoff.from/to, illustrationStyle.cast[].actor), user stories, realisedBy BPMN files (instance-relative) and the element ids in them, uses blocks in a directory declaring building-blocks, req: requirements, FHIR examples and a step’s dak assets (data sets, decision tables, indicators) in a fhir-artifact-index (could not determine while the index is built at publish), illustration.src files, follows/partOf/parts/includes journeys (parts and includes forming no cycle; an includes held against the call activity its step’s realisedBy names, could not determine when the call names no process), the trustLadder code list and each record.state code of it, and ArchiMate views; and each workshop’s scenarios, steps[] {scenario, step} and <scenario>#<step> refs; each device screen’s owner and personCard actors, its steps[] {scenario, step}, and the FHIR examples its qr and recordList blocks name; and every persona’s avatar image path. Every journey is a DAK user scenario (the kind specialises it): its DAK personas, the roles its persona actors play, must be non-empty and each a declared role; a persona may be an actor or (0.4.0) a role. What is derived is not also written: a listed part’s follows or partOf, personas equal to the parts’, a lead equal to the lanes’ first actor, are each a redundant finding, and a 0.4.0 step with no experiences whose lanes no persona plays is a finding. A node that does not parse is a finding. One line per finding, naming the layer, file and step. Exit 0 every reference resolves (or no layer holds a journey or a workshop, which is said); 1 one does not; 2 the declarations could not be read.

Skills it satisfies

A skill states the capability; this Tool is one way to exercise it. Each skill’s declared input and output contract follows, where it has one.

journey-maps

Journeys and workshops as knowledge-graph content: a DAK user scenario told as a journey map (user-scenario kind: ordered steps, per person what they do and feel, pain points, enablers, the record’s trust state, and edges to stories, BPMN tasks, requirements, FHIR examples, building blocks and the DAK’s data sets, decision tables and indicators), the building-blocks catalogue its steps use, a workshop that teaches from it (workshop kind: modules, objectives, questions for the room on each step, reference tables, sheets, job aids), the journeys-viewer visualiser that draws them for a layer and the layers it mounts, and the check:journey-refs gate that every reference they name resolves. Read before writing a journey or a workshop, before declaring the viewer, and before building a journey walkthrough app of your own.

Source: cat-harness/skills/ui/ui-core/journey-maps.md.

Also satisfied by: journeys-viewer.

The skill declares no I/O contract (schemas/skills/journey-maps/{input,output}.schema.json).

Processes and tasks

No process step names a skill this Tool satisfies.

How it is deployed and reached

  • Command line. From the repository root: bun run cat check:journey-refs. cat check:journey-refs runs bun run cat-harness-tools/scripts/check-journey-refs.ts (declared in cat-harness-tools/package.json).
  • GitHub Actions. No workflow in this checkout runs its command.

As an API: its operation in the OpenAPI document and the MCP tool list of its layer.

limitsA realisedBy process and an illustration.src are resolved in the journey’s own layer only, as the viewer draws them; the other references are looked up in the journey’s layer first, then in every layer the checkout mounts.
costOne read of the checkout’s declared directories, as the viewer makes; milliseconds per journey.

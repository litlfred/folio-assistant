Publish a folio’s or an IG’s site from the agent’s own checkout — the one agent publish path

Build a repository’s site in the agent’s checkout and push it to the publish branch, as a preview or as the main site, without an Actions runner. Which build is read from the repository: a declared site.build recipe (built by build-instance-site), else the reusable workflow its own workflow files call — folio-staging.yml for a folio, the WHO SMART Base IG’s ghbuild.yml for a FHIR IG, whose build job is planned step by step and run as written. For an IG it then applies the harness chrome over the built output (sync-docs-harness, then rail-standalone-pages --foreign-site --instance <the IG>): every page gains the rail and the icon row #fa-navbar-row, and the IG’s own content is left byte for byte. A root publish is REFUSED when the chrome cannot be applied, and a clean root deploy is refused over any root whose index.html wears the icon row unless the new output does too, so a chromed root is never replaced by bare IG Publisher pages. Every run prints its plan first, and the plan lists the chrome step; --plan stops there, --dry-run composes the commit in a temporary worktree and pushes nothing, --artifact writes a claude.ai Artifact bundle instead.

How it is deployed and reached

  • Command line. From the repository root: bun run cat stage:local. cat stage:local runs bun run cat-harness-tools/scripts/stage-local.ts (declared in cat-harness-tools/package.json).
  • GitHub Actions. 1 workflow line(s) run its command:
workflowline
cat-harness-tools/.github/workflows/folio-site-publish.yml294if ! bun run cat-harness-tools/scripts/stage-local.ts --repo . $PLAN 2>&1 \| tee "$RUNNER_TEMP/stage-local.log"; then

when to choose it
whenEvery agent-run publish of a folio’s or an IG’s site, preview or main: it is what the current build pipeline uses (the IG repositories’ site-publish.yml run this same command on a runner).
limitsAn IG repository’s main site is built from its AST, read from the cache branch fhir-harness’s ig-ast-refresh keeps current, by the steps its site.build recipe declares (profile: ig-repo-site): the theme side bar and search, the harness rail and icon row, the served directories and the folio-build.json stamp, measured against the live root (https://github.com/litlfred/cat-harness-tools/pull/202). A stale AST is refused, never built from Publisher HTML. A root publish is refused when the composed site lacks anything the current root has (site-parity), judged on the pages. Without a site.build recipe an IG falls back to its own workflow’s Publisher steps, which need a Docker daemon and give the rail and icon row only.
costAn IG: the whole IG Publisher build (tens of minutes), then about two minutes of rail over ~3,600 pages. A folio: its build command. Then one push, and GitHub’s own Pages deploy.

Description

Caches — one node per CI cache a layer DECLARES: its key recipe, where its entries live, who produces and consumes them, its trust class and budget. Never the entries.

Rule 6 of cache-first CI (skill cache-first-ci, owner 2026-11-05): every cache is a node of kind cache, and a viewer shows each cache's stored key against the key today's pins imply, so staleness is COMPUTED, never claimed. Rule 7: a harness DECLARES its caches; the implementation is one, here (cached-step, cache:key).

Two families of one kind

  • cache/1.0.0 — one cache this layer declares (CacheSchema).
  • cache-inventory/1.0.0 — a dated snapshot of the caches found across the harness repositories, before each declares its own (CacheInventorySchema). A snapshot says when and how it was taken; it is never read as a declaration.

What the node does NOT hold

The stored key, the age, the size and the hit rate of a cache are facts about the cache service, not about the declaration: they come from the daily cache report (cache-report.sh) and are joined by the viewer. A node carrying them would be a claim that goes stale the day it is written.

The key is derived (bean 4rbc)

KeyRecipeSchema names HOW the key is computed — cache:key (the f017 fingerprint), cache:key --base (the cone's tree-free base), the runner's hashFiles over a lock, or a mount-free script that implements a recipe (.github/ci-image/key.sh) — never a list of inputs typed by hand. hand-listed exists only to RECORD a key found that way, so the viewer can say so; it is a finding, not a recipe to copy.

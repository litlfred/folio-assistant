Offering the knowledge graph

When a person is done with requirements on some workflow, ask whether and how to add them to the knowledge graph, and give options. CRDM sign-off is the usual moment: without this step, agreed requirements exist only as an issue and a conversation, and no later agent finds them.

What this skill is NOT

It is not a decision procedure for where a node goes. That is placement, and it is an agent’s procedure: which instance, which declared graph, which kind of node, which stub convention. Run it after this skill has an answer, not instead of it.

It is not general guidance on asking questions. That is interaction-modality §4.1, and this skill does not restate it — it obeys it, and supplies what the options are here.

It is not what to do when the author CORRECTS a rule. That is symbiotic-interaction §2, and it runs the other way: the node already exists, the author has just said it is wrong, and the correction is written into it in the same turn without an offer, because offering there asks the author to repeat a correction already made.

The line between the two is one question: does the rule already have a home? A ruling on something already in the graph is an edit and needs no offer; a ruling that implies a node which does not exist is this skill’s case, unless the author named the destination themselves.

The division in one line:

This skill decides what to offer. symbiotic-interaction §2 decides what needs no offering. placement decides where the answer lands. interaction-modality decides the shape of the asking.

The rule

The agent never picks a destination silently.

An agent that decides on its own that a requirement “is really a skill” and writes one has made a node nobody asked for, in a graph somebody else maintains. If the person does not answer, the default applies — and the default creates nothing.

One question, not two

“Should this enter the knowledge graph at all” and “as what” are asked as one question: destinations as options, none among them, and a stated default. Two rounds cost a low-dexterity person a real interaction; listing none keeps the single question from forcing an answer.

One question for the SET, not one per requirement

A CRDM run can agree many requirements. Asking once per requirement is redundant entry (WCAG 2.2 SC 3.3.7), so the offer names the set and asks once. If the person wants different destinations for different items, they say so and the agent asks follow-ups about the ones that differ. That path is opened by their answer, never assumed.

The options are DERIVED, never invented

The destinations are the graphs this instance declares, in <name>.json — read at the time of asking, never a list typed from memory.

Not every declared graph is an authorable destination. A store that is incoming (uploads), derived (qa, health, translation-sources) or a record of something that already happened (issue-marks, memory) is not somewhere a requirement is authored into. Offer the graphs whose nodes a person writes:

The design-memory asset, and the question that identifies one

A design record — an asset produced while building a feature, accessing data, or managing or rendering a type of content, but not the content to be displayed — goes into docs/. One question separates this class from every other destination:

Was this produced while BUILDING something, rather than being the thing that was built?

A requirement set, an options analysis, a measured comparison, the reasoning behind a schema: each is an artefact of the work rather than its output. It is not subject matter, so it is not folio. It is not a rule an agent follows, so it is not a skill (a skill is read by an agent about to act; a design record by a person asking why is it like this). It is not work outstanding, so it is not a work item. It is memory, and docs/ is where an instance keeps memory a person reads.

Not fsh-guts

fsh-guts is the declared non-rendered trashcan, whose content may be thrown away or lost. A proposal not yet agreed can afford to be lost; the reasoning behind something already built cannot.

WHOSE docs/ — the owning instance’s, not the repository’s

docs/ is not one place. It is a declared graph, and the instance that owns a harness, feature or tool owns its detailed information, design and planning. Ask placement Step 1’s question: which instance owns this? A design record for a cat-harness feature files in cat-harness/docs/; one for a folio’s own subject matter does not belong in the platform at all.

What else belongs there, and the line against a skill

Besides the design record, docs/ holds:

  • how to reach the data a piece of content describes — endpoints, credentials policy, shapes, quirks of a source;
  • everything past the competence line, which is the sharp test:

A skill carries what a competent practitioner needs IN ORDER TO DO the task. Anything beyond that is documentation.

Background, derivations, options not taken, and an API’s full surface when the task touches three calls are documentation. Conversely, a rule an agent must follow, filed in docs/, is a rule skill_fetch will never serve.

Where in that instance’s docs/ is placement’s question, not this one.

none is a real answer: a requirement whose whole content is “the button should be blue” becomes a commit and nothing else.

What the agent does with the answer

  1. Run placement for the chosen kind — it decides instance, graph and node kind, and catches a hardcoded path or a literal naming one folio.
  2. Create a work item for the authoring work, parented to the feature’s epic. The offer produces a decision, not a node; writing it is work, and work is a work item before it is a file.
  3. Record the answer where the next agent will see it — on the issue, with the round summary issue-working already requires.

On none, record that too (“asked, answered none, because the requirement is carried by the code”): otherwise it is indistinguishable from never having asked.

Description

QA reports — what a pipeline TOOL recorded about its own run.

Like the other committed QA artefacts (*.qa.json, *.script-qa.json, *.kg-qa.json, health-report/v1), the file declares what it is with a $schema tag, not by its extension or directory.

The shape already exists upstream: every DAK pre- and post-processing script in WHO's SMART Base repository instantiates a QAReporter and writes a phase report — successes, warnings, errors, the files it processed, the files it EXPECTED, and the files that were missing — and the IG Publisher writes qa.json, uploaded as a workflow artifact. This kind gives it somewhere to live.

Not the qa kind

  • a qa witness judges an ARTEFACT this repository produced, against criteria that artefact is supposed to meet;
  • a health report judges the REPOSITORY itself;
  • a qa-report records what a TOOL did on one run. Its subject is an execution, not an artefact and not a repository.

The field names are UPSTREAM's

total_successes, files_expected, completion_timestamp — snake_case, against this repository's own convention, so an upstream report validates here byte for byte and a change upstream fails validation instead of being quietly re-mapped. The wrapper fields this module ADDS — $schema, producer, source, toolchain — are ours, camelCase where compound.

Three things enforced structurally

1. A summary cannot disagree with its own details. total_errors must equal details.errors.length, and so on. 2. files_missing must be a subset of files_expected. A file cannot be missing if nobody expected it. This keeps "the DMN directory held no decisions" distinguishable from "the DMN directory was not found". 3. running is never a pass. A report that never finalised carries no completion_timestamp, and a consumer must not read its zero errors as a clean run. Same rule as check-ci-health.ts, restore-staging.ts, kg-qa.ts and health-report.ts: could-not-determine is never rendered as clean. Enforced by requiring completion_timestamp exactly when status is terminal.

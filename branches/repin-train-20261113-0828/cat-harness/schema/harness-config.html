Description

Cross-folio dependency schema for folio-assistant instances.

A folio-assistant instance can depend on other instances for content, skills, and translation resolution. Dependencies are declared in harness.config.json under dependencies.folioAssistant and walked depth-first in listed order, overlaying content and skills on the root — later overlays earlier, as in FHIR/SUSHI.

The pin differs from SUSHI

SUSHI names a dependency as packageId: version; FolioAssistantDependencySchema names a git ref that DEFAULTS TO THE DEFAULT BRANCH, which can change silently. A SHA may stage, only a published semver version may publish: [directory-conventions](../skills/kg/kg-core/directory-conventions.md) §"Pinning a reference — a SHA may stage, only a version may publish", enforced by bun run cat check:published-refs. The full scheme is cat-harness/docs/proposals/instance-versioning.md.

What gets resolved across dependencies

| Resource | Resolved? | How | |---|---|---| | PO translations | ✅ | translations/<locale>/, fallback chain step 4 — the only path with a live consumer (pipeline/po-resolve.ts) | | Kind headings | ✅ | kindHeading in schemas/content/translation.ts: English on each block-kind node, other locales in its owner's translations/<lang>/block-kinds.po | | Skills | ✅ | resolveSkillDirs reads each instance's DECLARATION, and LOCAL_PACKAGES in src/tools/skill-fetch.ts is built from it, so a dependency's packages are served. Two nearby call sites stay root-only on purpose — see its docs | | Declared directories | ✅ | declarationChain + resolveDirectories, materialised by materialiseDeclaredDirectories | | Block kinds | ✅ | loadContributions → schemas/content/contributions.ts | | Adapters | ✅ | loadContributions, as a module specifier | | MCP tools | ✅ | loadContributions, as registrar callbacks | | Content blocks | ❌ | no resolver | | QA criteria | ❌ | criterion definitions are root-only |

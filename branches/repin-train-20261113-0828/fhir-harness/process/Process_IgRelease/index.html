summaryHow an IG repository's release is cut, and how a missed one is caught up (skill `ig-binary-artefacts` §"Releasing").
descriptionHow an IG repository's release is cut, and how a missed one is caught up (skill `ig-binary-artefacts` §"Releasing"). (Owner, 2026-11-10: "need to add this to process (and how to catchup if not tagged) of build".) THE RULE. A release is a governance decision. The owner tags the IG's CURRENT version from `sushi-config.yaml`, `v<version>`, on the default branch. The tag starts the IG's `ig-release.yml` caller, which builds the tag in full and makes a GitHub DRAFT release carrying `package.tgz` (and its R4/R4B variants), `ast-data.zip` and `SHA256SUMS`. The owner publishes the draft. An agent never chooses a version, never pushes a tag and never publishes a release. THE CATCH-UP. Every AST refresh of the default branch runs `ig-release.ts check` (advisory, never failing the run): an untagged current version is reported with the commit that set it, for the owner to tag; a tag with no release is reported with the by-hand run of the release workflow; a draft is reported as waiting for the owner. The site is not the release: it is published from the AST cache (`ig-ast-cache.bpmn`) and carries none of these files.

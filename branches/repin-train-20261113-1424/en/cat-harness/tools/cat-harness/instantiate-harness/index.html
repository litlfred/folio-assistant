Instantiate a harness over a repository that has none: pin, mount, open the setup-only PR, render the preview

The scripted step of the initiation process (getting-started.bpmn, the repo-conversion skill §4). Reads the harness’s declaration at its pin and every needs, transitively (a need beside the layer that needs it unless –repo-of says otherwise, at its default branch’s tip unless –pin says otherwise, its declaration’s name checked), seeds them all into the repository’s index.config.json with the consent given (remote-mount --seed --whole), sets site.landing to the harness, site.agentRun and mountApprovers, mounts the closure (remote-mount: index.lock.json and the .gitignore mounts block), installs it as root workspaces with the hoisted linker, writes the root bootstrap (.github/cat.ts and .github/mount-from-lock.sh from cat-harness-tools templates/root-bootstrap/) and sets the root’s cat script to bun .github/cat.ts, so bun run cat … mounts the layers itself on a later fresh clone, re-renders the agent surface from the mounted generators, runs the harness’s instantiate:<harness> checkout script when a mounted layer declares it, and commits on a branch (default harness/). Then, unless --local, pushes the branch, provisions gh-pages when absent (`pages-bootstrap --provision`), opens the setup-only PR, runs `prepare:` when declared (what the site is built from and nobody commits, such as an IG's AST) and renders the branch's preview at gh-pages branches// (`stage-local`); with --local the site is built and composed and nothing is pushed. It imports only node:*, so it runs from a fresh clone of cat-harness-tools before anything is mounted: it lays the platform's own closure, at the pins the repository will mount, into a temporary root to run the mount from. On a repository with nothing mounted yet, run the same file from a fresh clone: `git clone --depth 1 https://github.com/litlfred/cat-harness-tools /tmp/cht && bun run /tmp/cht/scripts/instantiate-harness.ts …`. Two more flags, not declared as ports because no constrained type carries them yet: `--pin =` pins one layer of the closure, `--repo-of =<owner/repo>` says where a need lives.

Skills it satisfies

A skill states the capability; this Tool is one way to exercise it. Each skill’s declared input and output contract follows, where it has one.

repo-conversion

Lay folio-assistant over a repository that already exists, without losing or silently moving what is in it. Scans the tree read-only, classifies candidate files into library (external source) and content (authored here) with an explicit third bucket for what it cannot classify, scans outside the content tree for mathematical evidence and refutations, lists the content markers (an IG, a DAK, processes, work items, library, Lean, folio manifests) the harness could declare and declares only the ones the person picks, puts the three questions the scan cannot answer to the author as selections, and hands ingestion to one agent or a small swarm. Use when a user wants an existing repo converted to a folio, asks to import what is already there, asks whether their PDFs/notes/drafts can come along, or asks what else in a repository an existing harness could declare.

Source: cat-harness/skills/conduct/conduct-core/repo-conversion.md.

Also satisfied by: folio-init.

The skill declares no I/O contract (schemas/skills/repo-conversion/{input,output}.schema.json).

remote-mount

Bring a harness, and every layer it depends on, into a checkout that does not hold it, from another repository at a pinned commit, as declared directories with a lock: a source.remote entry in the downstream’s root index.config.json (legacy: remoteMounts on its declaration) and mountDefaults on the harness. Covers when to mount and when to subscribe instead, why there are no submodules and no .deps/, the transitive closure through needs and gitlinks, overrides by id, the lock, and the three states.

Source: cat-harness/skills/kg/kg-core/remote-mount.md.

Also satisfied by: build-instance-site, index-config-migrate, kg-retrieve-npm, mount-from-lock, npm, subgraph-index-package, ci-standing-repin.

The skill declares no I/O contract (schemas/skills/remote-mount/{input,output}.schema.json).

How it is deployed and reached

  • Command line. From the repository root: bun run cat harness:instantiate. cat harness:instantiate runs bun run cat-harness-tools/scripts/instantiate-harness.ts (declared in cat-harness-tools/package.json).
  • GitHub Actions. No workflow in this checkout runs its command.

As an API: its operation in the OpenAPI document and the MCP tool list of its layer.

When a host it reaches is refused:

host / errorremedy
github.comnone: The closure is fetched from GitHub and the branch, preview and PR are pushed there; offline nothing can be pinned.
when to choose it
whenA repository that mounts no harness yet is to be harnessed: an existing FHIR IG adopting a FHIR harness, a repository becoming a folio overlay. Its PR is the setup-only PR repo-conversion §4 asks for before any content PR.
limitsThe harness’s own adoption steps are its checkout scripts instantiate: and prepare:; a harness that declares neither is mounted and rendered with what its layers already declare, and a site that needs a build input nobody produced (an IG with no AST) is refused by the render step with its reason. Re-pinning an already harnessed repository is remote-mount --seed, not this.
costThe mount: a blobless fetch of each layer of the closure and one install (a few minutes). Then the harness’s prepare step (an IG’s AST: a full IG Publisher run) and the render.

Staging a feature branch preview, and taking it down

Process_FeatureStaging · strict · 13 step(s)

The lifecycle of a feature branch’s review preview: staged on a push, taken down when its pull request closes, or removed by an explicit dispatch. THE LIFECYCLE OF A REVIEW PREVIEW, drawn rather than described. Bean 7yvd, owner: “make sure all workflows documented as bpmn”. This is the first .github/workflows/*.yml documented here, and it was chosen because its shape was the least visible: three jobs, eight if: branches, a confirmation gate and a deletion trigger, written down only in a sixty-line YAML comment.

Three entry points, and they are three different processes sharing a file. A pull request opened or pushed to STAGES a preview — or, when branches/<slug>/_build-record.json on gh-pages shows the agent already built this exact merge tree via stage-local.ts, DEFERS the critical-path build, sets preview/agent-build to pending, and lets preview-verify-sweep.yml dispatch an off-critical-path full CI rebuild (verify_pr) that either confirms the agent’s files in place or replaces them on mismatch (#2881). A pull request CLOSED asks whether the preview should go. A dispatch removes ONE preview that the first two can no longer reach — bean w2g5: the health sweep can only ever report a preview whose pull request is already closed, so by the time anybody reads the finding the event has fired, the job has run and the label was absent. Labelling afterwards fires nothing.

TWO GATEWAYS, and both are three-state rather than yes/no. Removal confirmed? reads a merge as confirmation in its own right (bean 1feu) while still requiring a label for a close without a merge. Still in use? refuses on a live signal AND on could-not-tell, because a preflight that has gone blind must not read as permission.

EVERY PATH THAT CHANGES branches/ WRITES TO THE RENDER LOG, and the two removal paths write the record in the SAME COMMIT as the removal. A separate log push can fail alone and leave a preview that vanished with nothing saying why, which is the state bean plj1 left the publish branch in for months.

The single human step is the dispatch confirmation. Everything else is mechanical, which is what makes build-pipeline the right lane rather than a convenient one.

Lanes — who acts

lanerolewhat it does here
CI/CD Pipelinebuild-pipelineRuns all three entry points — stage, cleanup, cleanup-dispatch — as one actor because none of the work in any of them needs judgement; the one step that does, confirming a dispatch deletion, was carved out into Lane_Human rather than left here. Every path that changes branches/ writes its render-log entry in the SAME commit as the change, because a log push that can fail on its own is exactly how a preview vanishes with nothing on the branch saying why.
A FOURTH trigger starts none of them, and that is deliberate rather than an omission from this diagram. merge_group is declared on the workflow so it REPORTS in the merge queue — a required check that never reports on a merge_group event leaves every queued pull request pending forever — and all three jobs skip on it. A preview exists for the reviewers of a pull request; a queue entry has none and lives for minutes. Without the skip, stage’s existing guards all pass on a queue run (github.event.action is empty and the event is not a dispatch), so it would publish branches/<slug>/ named after the ephemeral gh-readonly-queue/... ref, and nothing would ever remove it — Start_Closed below fires on pull_request_target: closed, and a queue branch is never a pull request that closes. That is the plj1 shape arriving once per MERGE rather than once per pull request.
Human actoruserThe only lane whose actor cannot be a machine — deletion-requires-confirmation is not satisfied by a click, so H_Confirm must repeat the slug rather than approve generically, which is what stops a confirmation from an earlier run being replayed against a different preview. It precedes Start_Dispatch rather than following it, so the dispatch entry point cannot fire at all until this lane has acted.

Defer build and queue verify sweep
Task_Defer		CI/CD Pipelinefeature-stagingSet the preview/agent-build commit status on the PR head to pending, post the preview-build-verify notice on the PR, and exit the critical-path run so the runner is free. Task_Build		CI/CD Pipelinefeature-stagingBuild the preview from the PR’s head (or, on an off-critical-path verify_pr dispatch, rebuild refs/pull/<n>/merge in full to verify an agent-built preview) and write _build-record.json: regenerate the generated docs, trim what this preview does not need, render the BPMN diagrams, then Jekyll, TypeDoc and the knowledge-graph export, with the staging banner and SEO identity claims stripped. It is a PREVIEW build (CAT_BUILD_TYPE=preview, owner 2026-11-01): only what the change reaches, and every whole-corpus index (builtAtPublish entries marked index: true, and the search index) is main’s copy, put back rather than rebuilt. A branch frozen for public comment is dispatched with build_type: full instead. Skill feature-staging, section Build types. A PREVIEW REBUILDS ONLY ITS DEPENDENCY CONE (owner cards Q-CONE-1 C and Q-CONE-2 B, 2026-11-01): main’s writer records say what each derive:publish writer and each step of the QA working copy READ. A writer or QA step whose recorded reads all match is not run, and main’s outputs for it are put back. Every other one runs. QA is not left out of a preview, only narrowed to what the change can reach. Inside a preview’s QA build, skill:register also leaves to derive:publish the two pages that derive:publish builds anyway and that no later QA step reads (skills:docs and lsi:viz), so they are built once.
Push to the CDN under branches/
Task_Deploy		CI/CD Pipelinecalls Render a Knowledge Graph to a CDN
render-kg-to-cdn		A PREVIEW IS THE GENERAL STEP WITH A DIFFERENT ROOT (owner, 2026-09-30: “independent of staging vs publication … just rendering”). Process_RenderKgToCdn, entered with the tree Task_Build rendered, branches/<slug>/ under the site root as the publication root URL, and GitHub Pages as the target, so its gh-pages Tool pushes. For this target the push is keep_files: true with a destination_dir, so it adds one directory beside whatever else is on the branch; it is also RETRIED once: five other workflows push to gh-pages without joining this one’s concurrency group, and a queue does not help because GitHub CANCELS a pending job when a newer one arrives for the same group rather than queueing it. Measured 2026-09-19: three staging runs from three different branches inside 17 seconds, two cancelled. The call returns the push’s status and message; the render log and the PR comment that follow are this process’s own. THE PREVIEW CAP rides in the same commit (owner ruling 2026-10-02, issue #1868: “cap the maximum number of previews (<= 10) and rotate old ones off”, amended 2026-10-04 to a SIZE budget: “Cap by size, not count”, “3gb”): staging-rotate.ts keeps this preview plus the most recently updated others while their total fits MAX_PREVIEW_BYTES = 3 GB and removes the rest, oldest first, each with a removed render-log entry and its record retired into branches/_retired/. Every push attempt re-reads gh-pages and re-decides rather than rebasing, so a lost race never pushes a stale removal. A rotated-off preview is regenerated by the next push to its PR branch.

Agent build matches tree?
GW_AgentBuilt		Check whether branches/<slug>/_build-record.json on gh-pages was written by the agent (builder = “agent”) for the exact git tree of refs/pull/<n>/merge (record.tree = MERGE_SHA^{tree}). When an agent has already built and pushed the preview for this exact merge tree via stage-local.ts, the preview is already live on gh-pages and the critical-path PR run does not rebuild it. no — build now → GW_MergeBuild
Verified identical to agent build?
GW_VerifyMatch		On an off-critical-path verify run (verify_pr), preview-record.ts compare checks the CI rebuild’s _build-record.json against the agent’s record on gh-pages across every file outside the per-build metadata (staging.json, _build-record.json, .staged-at, build.yml). When every file hash matches (same = true), the agent’s deployed files on branches/<slug>/ stand untouched and the deploy and render-log commits are skipped. On a normal CI build, or when the verify rebuild differs (same = false) or the merge tree moved (same = stale), the flow proceeds to push CI’s build to branches/<slug>/ (guarded on verify runs so a newer preview is never overwritten).no, or CI build → Push to the CDN under branches/
yes — keep agent files → GW_MergeComment
Removal confirmed?
GW_Confirmed		THREE inputs, two outcomes, and bean 1feu set the split: a MERGED pull request needs no label, because the merge IS the confirmation — a person decided the content belongs on main, which says more about the preview than a label does. A pull request closed WITHOUT merging still needs staging:cleanup, because there the preview is the only rendering of that work: not redundant, the last copy.
The branch taken is emitted as reason=merged \| labelled \| closed-unmerged-and-unlabelled and written into the log entry, so an audit of a removal can tell which rule did it.		merged, or labelled → Remove the preview and log it
closed unmerged, no label → Append retained, with why it stays
Still in use?
GW_Live		THREE states, and the third is why this gateway exists. Still in use → refuse, exit 1. COULD NOT TELL → refuse, exit 2. Only a determined absence of every liveness signal removes anything. Refusing to delete is the only recoverable direction, and a preflight that has gone blind must not read as permission.no signal — safe to remove → Remove it AND append removed — one commit

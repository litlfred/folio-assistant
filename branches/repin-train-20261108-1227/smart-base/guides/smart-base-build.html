Render it from the command line

✎ Edit

From a checkout of litlfred/smart-base, mount the layers that index.lock.json pins (the commands are on the FHIR IG layer’s page, §”What you need installed”), then:

# See what would be built and where
bun run cat stage:local --repo . --plan

# Build the site and compose the publish commit; push nothing
bun run cat stage:local --repo . --dry-run

# Or write a bundle you can open as a page
bun run cat stage:local --repo . --artifact ./_preview

The render restores the AST from the cache branch cat/fhir-harness/fhir-ast/smart.who.int.base, which already holds one.

When the AST is stale (you changed input/, sushi-config.yaml or ig.ini), rebuild it with the DAK pre-processing by starting the repository’s IG AST refresh workflow (.github/workflows/ig-ast-refresh.yml) on your branch. Running bun run cat prepare:fhir-harness on your machine builds an AST without the DAK pre-processing, because that script does not run a pre-export step. Use it only to check that the FSH compiles.

To run the DAK pre-processing on its own, for example to inspect what it writes: bun run cat smart-base:dak-pre-export. It changes files under input/; restore them with git checkout -- input sushi-config.yaml before you commit.

The plain WHO build, with the IG Publisher alone

✎ Edit

This repository keeps the files of the stock WHO build, which runs the IG Publisher with no harness:

CommandWhat it does
./_updatePublisher.shdownloads the latest publisher.jar, so the version floats
./_genonce.shruns the Publisher once over the IG; the HTML is in output/
./_gencontinuous.shruns it again on every change

In CI the same build is .github/workflows/ghbuild.yml: six DAK pre-processing steps, the Publisher, then nine post-processing steps that write the DAK API, the JSON Schemas and the JSON-LD vocabularies. bun run cat stage:local --repo . --bare-ig publishes that output as it is.

Use this route to compare with WHO’s own build. The harnessed site above is what this repository publishes.

The publishing pipeline

✎ Edit

Every workflow here is started by hand from the Actions tab. Nothing publishes on push.

WorkflowWhat it does
ig-ast-refresh.ymlcalls the FHIR IG layer’s reusable refresh, with pre-export: bash smart-base/scripts/dak-pre-export.sh and the WHO template. Seeds the AST cache from main
site-publish.ymlmounts the layers and runs stage-local.ts --repo .. On main it publishes the gh-pages root; on another branch, branches/<branch>/
pr-preview.ymla pull request preview, deployed after a collaborator approves it in the pr-preview environment
ghbuild.ymlthe plain WHO build (above)
release.ymlchecks publication-request.json for a release

The gh-pages root publish also keeps ns/, 0.1.0/ and sitepreview/ (site.build.keep in index.config.json): the JSON-LD context and vocabulary that publish-context.yml writes.

Deployment targets

✎ Edit

SMART Base deploys to GitHub Pages only. The options, and what each would take, are on the FHIR IG layer’s page: Deployment targets: GitHub Pages and Cloudflare.

Two points are particular to this IG:

  • The canonical is http://smart.who.int/base. It names WHO’s publication, not this site, so moving this site to another host or domain does not change the canonical. It does change every link to litlfred.github.io/smart-base/ that is already published.
  • The site is large, with six languages and an OpenAPI page per operation. Count the files on gh-pages before choosing Cloudflare Pages, which limits the number of files per deployment.

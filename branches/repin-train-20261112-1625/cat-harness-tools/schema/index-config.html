Description

index.config.json — the instantiation root's INDEX (folio-index-config/v1).

Proposal: cat-harness/docs/proposals/index-config.md.

A checkout that instantiates several harnesses has ONE <base>/index.html. The index is the one file that says which harnesses are instantiated, where each comes from, and which lands at /. When it exists at the root it is AUTHORITATIVE:

| question | answered by | |---|---| | which harnesses are instantiated | harnesses[].name — or, in an index with no harnesses, every instances[].name (the old reading) | | which layers are mounted, and where each comes from | layers[].source (spelled instances in the old form) — local.at, or remote (a remoteMounts entry without its harness) | | each one's configuration | the imported <name>.config.json (when it exists), overlaid by the entry's inline fields | | which one is / | site.landing — an instance name, or "hub" | | whether an agent publishes it | site.agentRun — true when the repository is agent-run | | what the checkout is called | title and description, which index:render writes into the root README.md and AGENTS.md |

Two forms (cat-harness#1138)

An INSTANCE is an instance of a node kind; a repository in the stack is a LAYER; Harness is one node kind (owner, 2026-11-08). The old form has one list, instances, that says both which layers are mounted and — because every name in it was read as instantiated — which harnesses are instantiated. The new form says the two apart:

{ "layers":    [{ "name": "guide-base", "source": { "remote": { … } } }, …],
  "harnesses": [{ "name": "guide-base" }] }

Parsed, both forms give instances (the layers, under the old name until the P4 code rename) and, for the new form, harnesses. formatIndexConfig writes layers exactly when harnesses is present, so a file keeps the form it was written in. layers without harnesses is refused: it would read as "every layer instantiated" under a name that says otherwise.

Without it, readers infer the instances from the root *.config.json files, site.landing flags and the root declaration's remoteMounts.

index is reserved

The file ends in .config.json, so a scan reading "each root *.config.json is a harness" would read a harness called index. rootConfigStems in instance-roots.ts is the one scan and excludes it, and IndexInstanceSchema refuses an instance of that name.

The mount lock stays a separate, generated file: index.lock.json

The lock records what the declared mounts RESOLVED to; it is generated by mount:remote and never hand-edited. Readers accept index.lock.json first and the legacy <root-instance>.mount-lock.json as a fallback, and BOTH present is an error (lockFilesIn in instance-roots.ts; restated node-only in mount-from-lock.ts).

The .gitignore block

Every remote instance's mount path is ignored by a GENERATED block in the root .gitignore (ignoreBlockLines); with an index, mount:remote does not write .git/info/exclude. check:index-ignores is the gate.

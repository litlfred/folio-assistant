Description

Test data sets (fixed and generated) and SME review case/verdict pairs.

Fixed and generated sets are separate node kinds

A test plan (test-plan/v1, schemas/sdlc/test-plan.ts) binds each case to test data of one of two kinds, and the two do NOT have the same audit standing:

  • Fixed (test-data-fixed/1.0.0) — small, curated or hand-authored records committed to the repository, cited to a source or guideline where applicable, and reviewed by an SME when they exercise domain logic. Once reviewed (review present, or backed by sme-case-verdict/1.0.0 pairs), a fixed set is usable as certification evidence (isEvidence in schemas/sdlc/test-plan.ts).
  • Generated (test-data-generated/1.0.0) — a deterministic recipe (contentType, specialisation, template, params, seed, and the canonical sha256 digest of that recipe). It is never stored materialised: a test run synthesises the records from the recipe at execution time and records the recipe's digest on folio-test-run/v1, so no generated file can be hand-patched away from its generator.

The two kinds live in separately declared graph directories (test-data-fixed vs test-data-generated), AND each file carries both its versioned $schema tag and an explicit kind: "fixed" | "generated" discriminator. A consumer (discriminateTestDataSet) tells which it is reading from the file content, never from the directory path.

Per-content-type specialisation

How a recipe synthesises records or how a fixed set's payload is structured depends on the folio's contentType. The general curation workflow (sdlc/processes/test-data-curation.bpmn) delegates the content-type step to a called subprocess (specialisation):

  • "fhir-templating" (FHIR_TEMPLATING_SPECIALISATION) is one named specialisation for FHIR IG / DAK content (MeasureReport cohorts, bundle templates, questionnaire responses).
  • Other content types supply their own specialisations (e.g. "markdown-fixture" for document folios, "lean-counterexample" for formal-proof folios, "tabular-cohort" for epidemiological tables).

Nothing in this schema hardcodes FHIR resources or DAK fields at the platform layer.

SME review of decision support and indicator definitions

For domain logic — clinical or scientific decision-support rules and indicator definitions — "passing" means a subject-matter expert agrees the output on a realistic case or cohort is right. That requires two distinct units of review under one sme-case-verdict/1.0.0 node kind, discriminated by subjectKind:

  • "decision-support" — the unit of review is a worked case (case: input state, decisionLogicRef, systemOutput, optional expectedGuidance).
  • "indicator-definition" — the unit of review is a cohort plus an expected value (cohort: indicatorRef, populationSize, inputs, expectedValue, computedValue, optional period, numerator, denominator).

Every sme-case-verdict/1.0.0 node records the SME's attributable human identity (reviewer: kind: "human", provider, handle, role) and the review date (reviewedAt), because a review without them is not audited. The review is governed by sdlc/processes/sme-test-data-review.bpmn, where the SME sits in a lane whose role (clinical-sme) is judgementOnly: true — no procedure yields the answer.

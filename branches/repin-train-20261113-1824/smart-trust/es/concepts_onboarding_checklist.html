Lista de verificación de la integración

Este repositorio contiene una lista de comprobación para la incorporación de los Participantes en la red de confianza. Incluye las CSCA, la información de autenticación, la información de firma y otros archivos pertinentes para la incorporación de un participante. En los pasos siguientes se incluyen videoguías de cada paso.

Onboarding Process

Requisitos previos para la incorporación

Antes de comenzar el proceso de integración, asegúrese de que estén disponibles las siguientes herramientas, permisos y configuraciones de entorno. Esta lista de comprobación es fundamental para que la configuración se realice sin problemas.

Herramienta/requisito Descripción Cuenta de GitHub - Asegúrese de tener una cuenta de GitHub activa con acceso a los repositorios pertinentes. - Permisos: confirme los permisos necesarios en el repositorio (acceso de lectura/escritura si es necesario para hacer push de commits). OpenSSL - Necesario para generar y gestionar certificados digitales. - Versión mínima: 1.1.1 o posterior. - Verificar: openssl version. - Configuración de rutas: asegúrese de que OpenSSL se haya añadido correctamente a la ruta del sistema. - Descargar OpenSSL cURL - Necesario para transferencias de datos desde la línea de comandos; especialmente útil para solicitudes a la API. - Versión mínima: 7.68.0 o posterior. - Verificar: curl –version. - Descargar cURL Git - Imprescindible para el control de versiones y la interacción con repositorios de GitHub. - Versión mínima: 2.28.0 o posterior (recomendada por sus capacidades de configuración mejoradas). - Verificar: git –version. - Descargar Git GPG - Gnu Privacy Guard - Imprescindible para firmar sus etiquetas de git en su repositorio privado. - Versión mínima: 2.2 - 2.4; cualquier versión anterior está obsoleta. - Verificar: gpg –version. - Descargar GPG Editor de texto o IDE (opcional) - Utilice un editor de texto o IDE fiable, como Visual Studio Code, Sublime Text o Notepad++, para editar archivos. - Extensiones: si utiliza VS Code, considere añadir extensiones para Markdown y para la integración con GitHub. - Descargar Visual Studio Code Permisos de red y de cortafuegos - Acceso a la red: asegúrese de que la configuración de red permita el acceso a GitHub y a otros recursos externos necesarios (p. ej., puntos de conexión de la API). - Permisos de cortafuegos: verifique los permisos del cortafuegos para evitar problemas de conectividad. Herramientas de CLI y configuración de rutas - Confirme que todas las herramientas (p. ej., openssl, curl, git) estén disponibles en el PATH del sistema para acceder a ellas fácilmente desde la línea de comandos. - Compatibilidad de sistemas operativos: estas instrucciones son aplicables a Linux, macOS y Windows. Configuración del entorno - Variables de entorno: defina las variables de entorno necesarias (p. ej., claves de API, tokens o rutas) según lo especificado. Recursos adicionales y documentación - Familiarícese con la documentación complementaria, incluidas las referencias de la API, las directrices de seguridad y las políticas de tratamiento de datos necesarias para el proceso de integración. </div>

Guardar para más tarde: asegúrese de guardar de forma segura elementos como las claves GPG, los secretos, los nombres de usuario de GitHub, la URL del repositorio de GitHub, el PAT (token de acceso personal) de GitHub y otras configuraciones, ya que se necesitarán en los pasos siguientes.

Generar la clave GPG

  • Cree claves GPG para las personas responsables de cada entorno > Nota: Antes de generar una nueva clave GPG, asegúrese de haber verificado su dirección de correo electrónico. Si no la ha verificado, no podrá firmar commits ni etiquetas con GPG. > Consulte el vídeo GPG key Creation como referencia
  • Descargue e instale las herramientas de línea de comandos de GPG para su sistema operativo. En general, recomendamos instalar la versión más reciente para su sistema operativo.
  • Abra Git Bash
  • Genere un par de claves GPG. Como existen varias versiones de GPG, puede que tenga que consultar la página de manual (man) correspondiente para encontrar el comando de generación de claves adecuado.

  • Si tiene la versión 2.1.17 o posterior, pegue el texto siguiente para generar un par de claves GPG.

      Shell
  gpg --full-generate-key

  • Si no tiene la versión 2.1.17 o posterior, el comando gpg –full-generate-key no funciona. Pegue el texto siguiente y pase al paso 4.

      Shell
  gpg --default-new-key-algo rsa4096 --gen-key
  • Cuando se le solicite, indique el tipo de clave que desea o pulse Intro para aceptar el valor predeterminado. (El predeterminado es RSA)
  • Cuando se le solicite, indique el tamaño de clave que desea o pulse Intro para aceptar el valor predeterminado. (La clave debe cumplir los requisitos de clave GPG de la gobernanza de certificados; RSA 4096 los cumple.)
  • Introduzca el tiempo durante el cual debería ser válida la clave. Pulse Intro para indicar la opción predeterminada, que significa que la clave no caduca. Salvo que necesite una fecha de caducidad, recomendamos aceptar este valor predeterminado.
  • Verifique que sus selecciones sean correctas.
  • Introduzca la información de su identificador de usuario.

    Nota: cuando se le pida que introduzca su dirección de correo electrónico, asegúrese de introducir la dirección verificada de su cuenta de GitHub. Para mantener privada su dirección de correo electrónico, utilice la dirección no-reply proporcionada por GitHub. Para más información, consulte “Verifying your email address” y “Setting your commit email address.”

  • Autenticar
  • Utilice el comando gpg –list-secret-keys –keyid-format=long para enumerar la forma larga de las claves GPG de las que tiene tanto la clave pública como la privada. Se necesita una clave privada para firmar commits o etiquetas. 
      Shell
  gpg --list-secret-keys --keyid-format=long

    En algunas instalaciones de GPG en Linux puede que tenga que utilizar en su lugar gpg2 –list-keys –keyid-format LONG para ver la lista de sus claves existentes. En ese caso, también tendrá que configurar Git para que utilice gpg2 ejecutando git config –global gpg.program gpg2.

  • En la lista de claves GPG, copie la forma larga del identificador de la clave GPG que desee utilizar. En este ejemplo, el identificador de la clave GPG es 3AA5C34371567BD2:

      Shell

  $ gpg --list-secret-keys --keyid-format=long

  uid                          Hubot <hubot@example.com>
  ssb   4096R/4BB6D45482678BE3 2016-03-10

  • Pegue el texto siguiente, sustituyendo el identificador de la clave GPG que desee utilizar. En este ejemplo, el identificador de la clave GPG es 3AA5C34371567BD2:

      Shell

  gpg --armor --export << replace with your actual GPG key ID >>
  # Prints the GPG key ID, in ASCII armor format

    Guardar para más tarde: asegúrese de guardar de forma segura la clave GPG, ya que se necesitará en los pasos siguientes.

  • Copie su clave GPG, que comienza por —–BEGIN PGP PUBLIC KEY BLOCK—– y termina por —–END PGP PUBLIC KEY BLOCK—–.

  • Añada la clave GPG a su cuenta de GitHub. > Consulte el vídeo Adding GPG key to repository como referencia

  • Vaya a SSH and GPG Keys

Crear certificados

Preparación de certificados para DEV y UAT

Descargo de responsabilidad: este script está diseñado para crear certificados autofirmados únicamente para entornos que no son de producción, como DEV y UAT; no está pensado para utilizarse en entornos de producción. Para usarlo, elija el script adecuado para su sistema operativo:

Unix/Linux: Utilice el script bash gen_all_certs.sh en el sistema operativo Linux/Unix/Mac.

Windows: Utilice el script de PowerShell gen_all_certs.ps1 en el sistema operativo Windows.

Estos scripts, junto con los archivos de configuración proporcionados, sirven de orientación para la preparación de certificados.

Si su sistema operativo es Unix/Linux/Mac
  • Para personalizar los parámetros del certificado, actualice el archivo DN_template.cnf, que utilizará el script gen_all_certs.sh.
  • Modifique los siguientes parámetros predeterminados del certificado según sea necesario.
export OSSL_COUNTRY_NAME="XC"
export OSSL_STATE_NAME="Test State"
export OSSL_LOCALITY_NAME="TEST"
export OSSL_ORGANIZATION_NAME="WHO"
export OSSL_ORGANIZATIONAL_UNIT_NAME="R&D"
export OSSL_COMMON_NAME="NationXC_TNP

Nota: OSSL_COUNTRY_NAME debería ser el nombre ISO de 2 letras del país, que se corresponde con el nombre utilizado en el repositorio.

Si su sistema operativo es Windows

En Windows, utilice el script de PowerShell gen_all_certs.ps1. Puede modificar las variables de entorno directamente en el script o definirlas en su sesión actual de PowerShell:

1.Abra PowerShell en su equipo Windows.

2.Defina las variables de entorno necesarias.

$env:OSSL_COUNTRY_NAME="XC"
$env:OSSL_STATE_NAME="Test State"
$env:OSSL_LOCALITY_NAME="TEST"
$env:OSSL_ORGANIZATION_NAME="WHO"
$env:OSSL_ORGANIZATIONAL_UNIT_NAME="RND"
$env:OSSL_COMMON_NAME="NationXC_TNP"

Nota: OSSL_COUNTRY_NAME debería ser el nombre ISO de 2 letras del país, que se corresponde con el nombre utilizado en el repositorio.

Tenga en cuenta que necesita tener OpenSSL instalado (p. ej., Win64 OpenSSL v3.3.0 Light) y añadido a su variable de entorno PATH. Es posible que también tenga que permitir la ejecución definiendo una directiva de ejecución.

Set-ExecutionPolicy -ExecutionPolicy Unrestricted -Scope Process
Cómo ejecutar el script:
  • Una vez ejecutado el script, este generará todos los certificados y claves en una subcarpeta con el nombre de la fecha y hora actuales.
  • Notas: al ejecutar el script “gen_all_certs.sh” en un sistema operativo Unix/Linux/Mac, proporcione como argumento del script el archivo “DN_template.cnf”, que contiene la información relativa al país necesaria para generar todos los certificados requeridos (TLS, SCA, UP)
**For Mac/Linux/Unix**
cd scripts/certgen
./gen_all_certs.sh DN_template.cnf	    ## Provide DN_template.cnf file as a script argument.
zsh ./gen_all_certs.sh DN_template.cnf      ## Use this if you are using Zsh on your Ubuntu system.
        
**For Windows:**
cd scripts/certgen
./gen_all_certs.ps1

Esta configuración genera todos los certificados (TLS, SCA, UP) y claves necesarios en una subcarpeta con marca de tiempo, según la configuración especificada en DN_template.cnf para Unix/Linux y las variables de entorno definidas en la sesión actual de PowerShell para Windows.

Preparar las carpetas

Nota: mantenga sus claves privadas a salvo y seguras. No las comparta con nadie.

Copie los certificados generados en las carpetas correspondientes y cambie los nombres de archivo para que sigan la convención de nomenclatura. En el caso de certificados TLS autofirmados, CA.pem es simplemente una copia de TLS.pem (compruebe que keyUsage contenga keyCertSign). CA.pem debería existir, ya que se utiliza para verificar el certificado de cliente TLS al conectarse a la aplicación TNG. Los archivos que deben copiarse en las carpetas correspondientes son los siguientes:

  • SCA.pem -> onboarding/DCC/SCA
  • UP.pem -> onboarding/DCC/UP
  • CA.pem -> onboarding/DCC/TLS
  • TLS.pem -> onboarding/DCC/TLS

Nota: en los entornos DEV y UAT, si los archivos se generan mediante un script, elimine la carpeta generada antes de hacer commit de los archivos.

Preparación de certificados para Prod

Esta guía sigue las plantillas de certificados definidas en la gobernanza de certificados. Los certificados de clave pública generados siguiendo esta guía incluirán los campos mínimos requeridos; si es necesario, pueden añadirse otros campos en los archivos de configuración. Los certificados autofirmados se utilizan normalmente en los entornos DEV y UAT.

Para producción, se recomienda encarecidamente utilizar certificados firmados por una autoridad de certificación (CA) de confianza. Esto es solo un ejemplo de referencia sobre cómo utilizar un certificado de una CA de confianza en un entorno de producción. Debería consultar los procedimientos específicos de la autoridad de certificación (CA) pública de confianza que elija para obtener instrucciones exactas y detalladas Referencia: recomendación de utilizar un certificado de una CA pública de confianza en Prod

Solo se admiten los siguientes algoritmos de firma para el certificado.

  • ECDSA con SHA-256
  • ECDSA con SHA-384
  • RSASSA-PSS
  • DSA con SHA-256
  • Heredado: SHA-256 con cifrado RSA
Ejemplo de generación del certificado de la SCA (TNPSCA)

Consulte el vídeo SCA Creation como referencia

  • sca.conf: cree un nuevo archivo llamado sca.conf y sustituya las entradas dn por los datos de su jurisdicción.

      [req]
  prompt = no
  default_md = sha256
  distinguished_name = dn

  [dn]
  C = DE
  ST = NRW
  L = Bonn
  O = MinistryOfTest
  OU = DGCOperations
  CN = SCA_DGC_DE_01

  [ext]
  basicConstraints = critical, CA:TRUE, pathlen:0
  keyUsage = critical, cRLSign, keyCertSign
  subjectKeyIdentifier = hash

  • Generación del certificado: abra un símbolo del sistema en la carpeta donde se encuentra sca.conf y utilice el siguiente comando de OpenSSL para crear la clave privada (CAprivkey.key) y el certificado (CAcert.pem):

  • Para Prod se recomienda utilizar únicamente un certificado emitido por una CA de confianza. El comando siguiente para generar certificados autofirmados suele recomendarse solo para el entorno DEV/UAT.

      openssl req -x509 -new -days 1461 -newkey ec:<(openssl ecparam -name prime256v1) -extensions ext -keyout CAprivkey.key -nodes -out CAcert.pem -config sca.conf
Ejemplo de generación de DSC

Ejemplo de generación de DSC. Los certificados del firmante de documentos (DSC) deben estar firmados por la SCA. Por lo tanto, debe crear el certificado de la SCA (con la clave privada correspondiente) antes de poder emitir DSC.

  • DSC.conf: consulte el vídeo DSC generation and deletion como referencia

  • Cree un nuevo archivo llamado DSC.conf en la carpeta donde se encuentra la clave privada de su CA y añada los siguientes campos:

      [ext]
  keyUsage = critical, digitalSignature
  subjectKeyIdentifier = hash
  authorityKeyIdentifier = keyid:always
  crlDistributionPoints = URI:http://crl.exampledomain.example/CRL/SCA.crl
  extendedKeyUsage = 1.3.6.1.4.1.1847.2021.1.1,1.3.6.1.4.1.1847.2021.1.2,1.3.6.1.4.1.1847.2021.1.3

  • Se recomienda que la SCA proporcione listas de revocación de certificados. Por lo tanto, sustituya el URI de crlDistributionPoints por la información de su jurisdicción.

  • El campo extendedKeyUsage es opcional; para los certificados de COVID se recomienda utilizar los valores siguientes para restringir aún más el certificado DSC, de la siguiente manera:

Campo         Valor\ extendedKeyUsage   1.3.6.1.4.1.1847.2021.1.1 para emisores de pruebas\ extendedKeyUsage   1.3.6.1.4.1.1847.2021.1.2 para emisores de vacunación\ extendedKeyUsage   1.3.6.1.4.1.1847.2021.1.3 para emisores de recuperación\

  • El ejemplo anterior contiene los tres usos de clave extendidos.

  • Crear una solicitud de firma de certificado (CSR): para crear un certificado para un firmante de documentos, cree primero una solicitud de firma de certificado, preferiblemente en la máquina que utilizará el certificado, para evitar tener que copiar después la clave privada (DSC01privkey.key) a esa máquina. La CSR debe contener la información del nombre distintivo (DN) que se incluirá en el DSC. Abra un símbolo del sistema y utilice el siguiente comando para crear la CSR:

      openssl req -newkey ec:<(openssl ecparam -name prime256v1) -keyout DSC01privkey.key -nodes -out DSC01csr.pem

  • Si es necesario, puede repetir este procedimiento para crear varias CSR para distintos DSC (en distintas máquinas). Cuando se le solicite, introduzca la información necesaria (p. ej., C = su jurisdicción (OBLIGATORIO), O = su organización (OPCIONAL), CN = un CN no vacío y único (OBLIGATORIO), …).

  • Emitir el certificado: copie la CSR (DSC01csr.pem) en la carpeta donde se encuentra la clave privada de su CA. Abra un símbolo del sistema y utilice el siguiente comando para emitir el DSC (DSCcert.pem):

      openssl x509 -req -in DSC01csr.pem -CA CAcert.pem -CAkey CAprivkey.key -CAcreateserial -days 730 -extensions ext -extfile DSC.conf -out DSCcert.pem

  • Recomendaciones importantes para Prod: sustituya CAcert.pem y CAprivkey.key por material de firma de una autoridad de certificación oficialmente de confianza en lugar de utilizar uno autofirmado propio.

Ejemplo de generación de TNPUP
  • uploadCert.conf

    Consulte el vídeo UP Creation como referencia

  • Cree un nuevo archivo llamado uploadCert.conf y sustituya las entradas dn por los datos de su jurisdicción.

      [req]
  prompt = no
  default_md = sha256
  distinguished_name = dn

  [dn]
  C = DE
  ST = NRW
  L = Bonn
  O = MinistryOfTest
  OU = DGCOperations
  CN = NationX_TNPUP

Ejemplo de generación de TNPTLS
  • TLSClient.conf

    Consulte el vídeo TLS Creation como referencia

  • Cree un nuevo archivo llamado TLSClient.conf y sustituya las entradas dn por los datos de su jurisdicción.

      [req]
  prompt = no
  default_md = sha256
  distinguished_name = dn

  [dn]
  C = DE
  ST = NRW
  L = Bonn
  O = MinistryOfTest
  OU = DGCOperations
  CN = NationX_TNP_TLS

  [ext]
  keyUsage = critical, digitalSignature
  extendedKeyUsage = clientAuth

Nota: tenga en cuenta que los certificados autofirmados también deberían contener el uso de clave de firma de certificados (keyCertSign), para que pueda verificarse la (auto)firma del certificado.

```
plaintext
[ext]
keyUsage = critical, digitalSignature, keyCertSign
extendedKeyUsage = clientAuth
```

  • Generación del certificado: abra un símbolo del sistema en la carpeta donde se encuentra TLSClient.conf y utilice el siguiente comando de OpenSSL para crear la clave privada (TNP_TLS.key) y el certificado (TNP_TLS.pem):

      plaintext
  openssl req -x509 -new -days 365 -newkey ec:<(openssl ecparam -name prime256v1) -extensions ext -keyout TNP_TLS.key -nodes -out TNP_TLS.pem -config TLSClient.conf

Certificados de clave pública RSA. Si desea utilizar certificados RSA, puede seguir usando los archivos de configuración proporcionados arriba. Durante la creación de la CSR o del certificado, sustituya -newkey ec:<(openssl ecparam -name prime256v1) por -newkey rsa:4096 para obtener una clave RSA de 4096 bits. Tenga en cuenta que RSA NO SE RECOMIENDA para el DSC y, si desea utilizar RSA como algoritmo de firma de documentos, cree una clave RSA de 2048 bits o, como máximo, de 3072 bits, debido a las limitaciones de espacio de los códigos QR.

Proporcionar

Consulte el vídeo Signing (tag) certificates como referencia

  • Los comandos de Git para configurar, hacer commit y push de commits firmados también están disponibles aquí

  • Por último, haga commit y push de los cambios y cree una etiqueta firmada para la versión que desee poner en uso, siguiendo los pasos que se indican a continuación:

  • Enumera todas las claves GPG disponibles en su sistema

      gpg --list-key

      OutPut
	  
  gpg --list-key
  /home/test/.gnupg/pubring.kbx
  -----------------------------
	
  pub   rsa4096 2024-09-19 [SC]
  CD822874C7862BA4BB6B950E40CC62009D9A00B0
  uid           [ultimate] Test User1 (This GPG Key is for XXC test Country) <youruser@yourdomain.com>
  sub   rsa4096 2024-09-19 [E]

Nota: el PUB ID en la salida anterior es CD822874C7862BA4BB6B950E40CC62009D9A00B0. En su caso, debe sustituirlo > por el identificador real de su clave pública GPG para configurar Git de modo que utilice una clave GPG para firmar commits o etiquetas en el siguiente comando.

  • Configure la clave de firma que se utilizará globalmente para los commits y las etiquetas de Git

      git config --global user.signingkey << replace with your Pub ID >>
  • Obtiene la clave de firma GPG actual configurada para Git 
      git config --get user.signingkey
  • Configura el nombre de usuario y el correo electrónico globales de Git 
      git config --global user.name "Your Git UserName"
	
  git config --global user.email "Your email Id"
  • Prepara (stage) todos los cambios para el siguiente commit 
      git add .
  • Cree un commit de Git firmado con un mensaje de commit, 
      git commit -sm "added all certificates files"
  • Haga push de los cambios a la rama main. 
     git push origin main
  • Cree una etiqueta de Git firmada con un mensaje 
      git tag -s v1.2 -m 'my signed 1.2 tag'

  • Muestra los detalles de una etiqueta concreta

      git show v1.2
  • Envía (push) todas las etiquetas locales al repositorio remoto 
      git push --tags
  • Para comandos de git más detallados, consulte el Apéndice

Todos deben firmar; siempre es una buena idea. Firmar etiquetas y commits es estupendo, pero si decide utilizarlo en su flujo de trabajo habitual, tendrá que asegurarse de que todos los miembros de su equipo sepan cómo hacerlo. Para ello, puede pedir a todos los que trabajan con el repositorio que ejecuten git config –local commit.gpgsign true, de modo que todos sus commits en el repositorio se firmen automáticamente de forma predeterminada. Si no lo hace, acabará dedicando mucho tiempo a ayudar a otras personas a reescribir sus commits con versiones firmadas. Asegúrese de entender GPG y las ventajas de firmar antes de adoptarlo como parte de su flujo de trabajo habitual.

Generar DSC

Cargar DSC

El archivo de configuración del nombre distintivo (DN) que se analizará como fuente, DN_template.cnf, es un ejemplo.

Sustituya los parámetros OSSL_COUNTRY_NAME, OSSL_STATE_NAME, etc., del archivo DN_template.cnf por sus valores reales.

El script espera al menos dos argumentos: un archivo de configuración (DN_template.cnf) que contiene la plantilla del nombre distintivo (DN) y un subdirectorio donde se encuentran los archivos PEM y KEY de la SCA (autoridad de certificación de firma). Puede proporcionarse un tercer argumento opcional para especificar la finalidad del DSC (p. ej., test, vax, rec). Si no se proporciona este argumento, el DSC se generará para todas las finalidades.

Cómo ejecutar el script de generación de DSC gen_dsc.sh

./gen_dsc.sh DN_template.cnf path/to/sca_directory [test/vax/rec-purpose]

./gen_dsc.sh: nombre del script

/path/to/sca: cree el directorio SCA que contiene SCA.pem y SCA.key

Cómo ejecutar el script upload_dsc.sh para cargar el paquete CMS: upload_dsc.sh

./upload_dsc.sh /path/to/subdir  /path/to/DSC_dir [DCC]

./upload_dsc.sh: nombre del script

/path/to/subdir: cree el directorio subdir que contiene UP.pem y UP.key.

/path/to/DSC_dir: cree el directorio DSC_dir que contiene el archivo DSC.pem.

DCC: el nombre de dominio que se utilizará. Si se omite, el script utilizará DCC de forma predeterminada.

Importante: si el comando anterior se ejecuta correctamente, significa que su paquete CMS se ha cargado en la puerta de enlace

Pasos para obtener y utilizar un certificado firmado por una CA
  • Generar una solicitud de firma de certificado (CSR) Para empezar, genere una CSR con el siguiente comando de OpenSSL. Esta solicitud incluirá una nueva clave privada y un archivo de configuración:
openssl req -new -nodes -newkey ec:<(openssl ecparam -name prime256v1) -keyout CAprivkey.key -out CAreq.csr -config sca.conf

CAprivkey.key: este archivo contiene la clave privada.

CAreq.csr: este archivo contiene la solicitud de firma de certificado.

sca.conf: este es el archivo de configuración de OpenSSL que se utiliza durante la generación de la CSR.

  • Enviar la CSR a una autoridad de certificación (CA) pública: Envíe el archivo CAreq.csr generado a la CA pública que elija. La CA utilizará esta CSR para emitir un certificado. Tras la aprobación, la CA le proporcionará:

  • Enviar la CSR a la CA pública: Envíe el archivo CAreq.csr generado a la CA pública que elija. La CA utilizará la CSR para emitir un certificado y le proporcionará el certificado firmado y, posiblemente, una cadena de certificados o certificados intermedios.

  • Usar el certificado firmado por la CA: Cuando reciba el certificado firmado por la CA, lo utilizará en lugar de generar un nuevo certificado autofirmado. Así puede sustituir los marcadores de posición por el certificado firmado: cp signed_CA_cert.pem ${subdir}/CAcert.pem cp CAprivkey.key ${subdir}/CAprivkey.key

Más información sobre los comandos de Git para commits, firma y etiquetado

Firmar su trabajo

  • Git es criptográficamente seguro, pero no infalible. Si recibe trabajo de otras personas a través de Internet y desea verificar que los commits proceden realmente de una fuente de confianza, Git ofrece varias formas de firmar y verificar el trabajo mediante GPG.

  • En primer lugar, para firmar cualquier cosa necesita tener GPG configurado y su clave personal instalada.

      $ gpg --list-secret-keys --keyid-format=long
  /Users/hubot/.gnupg/secring.gpg
  ------------------------------------
  sec   4096R/3AA5C34371567BD2 2016-03-10 [expires: 2017-03-10]
  uid                          Hubot <hubot@example.com>
  ssb   4096R/4BB6D45482678BE3 2016-03-10

  • Si no tiene una clave instalada, puede generar una con gpg –gen-key.

      $ gpg --gen-key

  • Cuando tenga una clave privada con la que firmar, puede configurar Git para que la utilice para firmar definiendo el parámetro de configuración user.signingkey.

      $ git config --global user.signingkey 3AA5C34371567BD2!

  • Ahora Git utilizará su clave de forma predeterminada para firmar etiquetas y commits si lo desea.

Firmar etiquetas

  • Si tiene configurada una clave privada GPG, ya puede utilizarla para firmar etiquetas nuevas. Solo tiene que usar -s en lugar de -a:

      $ git tag -s v1.5 -m 'my signed 1.5 tag'

Verificar etiquetas

  • Para verificar una etiqueta firmada, se utiliza git tag -v . Este comando utiliza GPG para verificar la firma. Para que funcione correctamente, necesita tener la clave pública del firmante en su llavero:

  error: could not verify the tag 'v1.4.2.1'

Firmar commits

  • En las versiones más recientes de Git (v1.7.9 y posteriores), también puede firmar commits individuales. Si le interesa firmar directamente los commits y no solo las etiquetas, basta con añadir -S a su comando git commit.

      $ git commit -a -S -m 'Signed commit'

  You need a passphrase to unlock the secret key for
  user: "Scott Chacon (Git signing key) <schacon@gmail.com>"
  2048-bit RSA key, ID 0A46826A, created 2014-06-04

  [master 5c3386c] Signed commit
   4 files changed, 4 insertions(+), 24 deletions(-)
   rewrite Rakefile (100%)
   create mode 100644 lib/git.rb

  • Para ver y verificar estas firmas, git log también tiene la opción –show-signature.

      $ git log --show-signature -1
  commit 5c3386cf54bba0a33a32da706aa52bc0155503c2
  gpg: Signature made Wed Jun  4 19:49:17 2014 PDT using RSA key ID 0A46826A
  gpg: Good signature from "Scott Chacon (Git signing key) <schacon@gmail.com>"
  Author: Scott Chacon <schacon@gmail.com>
  Date:   Wed Jun 4 19:49:17 2014 -0700

      Signed commit

  • Además, puede configurar git log para que compruebe las firmas que encuentre y las muestre en su salida con el formato %G?.

      $ git log --pretty="format:%h %G? %aN  %s"

  5c3386c G Scott Chacon  Signed commit
  ca82a6d N Scott Chacon  Change the version number
  085bb3b N Scott Chacon  Remove unnecessary test code
  a11bef0 N Scott Chacon  Initial commit

  • Aquí podemos ver que solo el último commit está firmado y es válido, y que los commits anteriores no.

  • En Git 1.8.3 y versiones posteriores, se puede indicar a git merge y git pull, con la opción –verify-signatures, que inspeccionen y rechacen la fusión de un commit que no lleve una firma GPG de confianza.

  • Si utiliza esta opción al fusionar una rama que contiene commits que no cumplan la condición de estar firmados y ser válidos, la fusión no se realizará.

      $ git merge --verify-signatures non-verify
  fatal: Commit ab06180 does not have a GPG signature.

  • Si la fusión contiene únicamente commits firmados válidos, el comando merge le mostrará todas las firmas que ha comprobado y luego continuará con la fusión.

      $ git merge --verify-signatures signed-branch
  Commit 13ad65e has a good GPG signature by Scott Chacon (Git signing key) <schacon@gmail.com>
  Updating 5c3386c..13ad65e
  Fast-forward
   README | 2 ++
   1 file changed, 2 insertions(+)

  • También puede utilizar la opción -S con el comando git merge para firmar el propio commit de fusión resultante. El ejemplo siguiente verifica que todos los commits de la rama que se va a fusionar estén firmados y, además, firma el commit de fusión resultante.

      $ git merge --verify-signatures -S  signed-branch
  Commit 13ad65e has a good GPG signature by Scott Chacon (Git signing key) <schacon@gmail.com>

  You need a passphrase to unlock the secret key for
  user: "Scott Chacon (Git signing key) <schacon@gmail.com>"
  2048-bit RSA key, ID 0A46826A, created 2014-06-04

  Merge made by the 'recursive' strategy.
   README | 2 ++
   1 file changed, 2 insertions(+)

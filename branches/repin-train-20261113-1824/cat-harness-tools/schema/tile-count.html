Description

The number a graph tile shows, DECLARED BY THE PROJECTION.

Declared, not computed

graph-tiles.ts builds a tile from the DECLARATION, never from the projection: a tile's EXISTENCE stays declaration-derived, and only its NUMBER is read from here. A live projection with no declared visualiser is still a finding, not a tile.

There is no uniform entry count: a projection holds several arrays (schemas has roots, modules, decls, edges), and a meaningful number may not be an array length at all (uploads WAITING, not uploads). Only the generator knows which number is the one, so the generator says.

KEYED BY DIRECTORY, because one projection can serve two tiles

uploads and library are two tiles over one dataset: the queue lives in assets/library/index.json, and gen-uploads-viz.ts publishes a viewer and no projection of its own. So that file owes two numbers — entries for the corpus tile, waiting for the queue tile — which a single {count, unit} per file could not carry.

unit is not decoration

8 on a tile is ambiguous in a way 8 entries is not, when the same projection also lists uploads. The unit also reaches the accessible name.

Absent is a THIRD STATE

readTileCounts yields nothing for a projection that declares no counts, declares malformed ones, or cannot be read — and never 0. An absent count and an empty graph are opposite facts; the UI draws no badge at all for the first.

A malformed entry is dropped WITHOUT dropping its siblings, so one bad declaration in a shared projection cannot silence the tile beside it.

A badge is exactly as fresh as its projection

The badge and the page it opens read the SAME document, so they cannot disagree. A committed projection's lag therefore shows on the tile: assets/beans/index.json is existence-gated, and docs-site.yml regenerates before publishing. A number read from a LOCAL checkout is the committed projection's, not the site's; compare against the deployed page, or regenerate first.

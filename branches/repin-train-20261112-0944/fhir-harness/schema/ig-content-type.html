Description

The ig content type: a repository declares itself the source of a FHIR implementation guide with contentTypes.ig in its root index.config.json.

Why a section, and why here

The owner chose the section on 2026-10-30 ("A. ig section in index.config"), in the same form as the other index.config.json content-type sections (bean cz17, item 3; IndexSectionMarker in cat-harness). The rejected alternative was to treat sushi-config.yaml as the marker. That file is SUSHI's: it says what SUSHI builds. It does not say which parts of the repository this harness reads.

This layer registers the type because an IG is this layer's subject. Core and the harness do not name an IG: the layer that owns the model registers the entry, and a layer that cannot serve it does not name it.

The section declares what is read, and nothing else is read

The owner, 2026-10-30T12:41Z: "a harness can point to a repo, but doesnt want to automatically slurpo up all content in a repo. harness desclares what it it pays attention to in the repo."

So contentTypes.ig is not a flag. It carries include: the repository-relative paths this harness pays attention to. An entry ending in / is a directory and covers everything under it. Any other entry is one file. igDeclares answers whether a path is covered, and assertIgDeclares refuses one that is not. A section with no include, or an empty one, declares nothing: readIgSection returns its problems, and nothing reads it as "everything".

"contentTypes": {
  "ig": { "include": ["sushi-config.yaml", "ig.ini", "input/fsh/", "input/pagecontent/"] }
}

The IG Publisher and SUSHI still read what they read. The list bounds the harness, not those tools.

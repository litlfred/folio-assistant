Build an IG repository’s own site from its cached AST, with no instance declaration

The three checkout scripts the platform’s site build runs for a repository that holds an IG and only mounts layers (index.config.json): ig-site:ast restores the AST from the IG’s cache branch (ig-cache.sh restore) and judges it, refusing a stale, cannot-tell or absent one (a stale one is accepted for a preview by default, refused with SITE_ACCEPT_STALE_AST=0, and never accepted for the root); ig-site:compose derives the artefact index from the AST (binding any IG API sidecars a layer above left in $SITE_WORK/ig-api/), writes the thin artefact pages, stages the IG’s input/ and sushi-config.yaml (menu read at build time, palette from the webpage theme of the top layer the repository mounts, edit links from its origin) and composes it at the ROOT of the host site source; ig-site:publisher-pages serves each of the AST’s resources once, as <Type>-<id>.json at the root (no ast-data/ mirror) — reduced (minified, no narrative, no ELM data, the ELM attachment pointing at the full copy) when the pages read the full resources by raw URL from the AST cache commit, and off with SITE_ROOT_RESOURCES=0 — the artefact index (or fhir-artifact-index/index.ref.json, pointing at the cache’s copy) and the sidecars (or none, read from the cache), refuses a page wearing the IG Publisher’s chrome, repairs repeated element ids and stamps folio-build.json. Never runs the Publisher and never reads its output. Compose lists the pages it puts in the site in FOLIO_SITE_UPSTREAM_PAGES, so the site build reports the IG’s own dead links rather than refusing the publish over them.

Skills it satisfies

A skill states the capability; this Tool is one way to exercise it. Each skill’s declared input and output contract follows, where it has one.

ig-build-pipeline

The bare FHIR IG pipeline — FSH to SUSHI to the IG Publisher to a pages branch, with no pre-processing and no post-processing. What this layer runs, what it emits, and the list of things it deliberately refuses to know about. Owns the AST cache lifecycle: an IG site is built from the AST on its cache branch, the publish refuses a stale one, and the reusable ig-ast-refresh.yml is the one writer. Owns what an IG reader may read: contentTypes.ig.include in the repository’s index.config.json, and the legacy warning for a repository that declares none. Read before adding anything to fhir-harness, before onboarding, converting or changing the workflows of an IG repository, and before publishing an IG site.

Source: fhir-harness/skills/fhir-ig-base/ig-build-pipeline.md.

How it is deployed and reached

  • Command line. From the repository root: bun run fhir-harness/scripts/ig-repo-site.ts.
  • GitHub Actions. No workflow in this checkout runs its command.

When a host it reaches is refused:

host / errorremedy

when to choose it
whenPublishing an IG repository’s own site, as stage-local.ts does for a harnessed IG repository.
limitsNeeds the IG’s AST cache branch (ig-ast-refresh.yml writes it) and the network to fetch it; asks the IG’s origin for its default branch for edit links (absent, pages carry none). Never runs the Publisher.
costSeconds to restore and compose; serving the AST is proportional to its size.

# WHO SMART Guidelines knowledge graph

> **Migrated from WorldHealthOrganization/smart-kg `README.md` at 3f5e477** (issue #359). smart-kg is deprecated (owner, 2026-10-16); this copy is the one to edit. Paths now point at smart-base: each layer is a named subgraph, `smart-base/<Layer>/schemas/` (L1, L2, L2-bpmn, L2-dmn, L3), the engine and these docs are in `smart-base/L1/schemas/`, and the generated JSON, contexts, Turtle and Cypher are in each layer's `generated/`. A command written `npx tsx <path>` runs from the repository root after `npm ci` in `smart-base/L1/schemas/`.

A governance, traceability and discoverability layer over the SMART Guidelines artefacts — **not a
replacement for them**. BPMN XML, DMN XML and FHIR JSON stay authoritative; this graph carries
identity, cross-model edges and provenance, and points at those artefacts by URL.

**L1 first**, because L1 is the layer nothing currently represents. A WHO recommendation is prose in
a PDF: no identifier, no structure, and no way for a tool to follow a citation to it.

**L2 second**, in three parts, because L2 is not one thing. `DAK.fsh` declares a Digital Adaptation
Kit as **nine components**, each pointing at a file by URI and saying nothing about its interior.
So the DAK component layer is one graph, and the interiors of BPMN and DMN files are two more —
different vocabularies (OMG's, not WHO's), different extractors, different failure modes.

## The problem, concretely

`smart-base` ships a real immunization decision table,
`input/dmn/DAK.DT.IMMZ.D2.DT.BCG.dmn`. It declares an output column whose description reads:

> *"Reference for the source content (L1)"*

**L1 traceability is provided for at decision-rule granularity, by WHO's own tooling — as a free-text
string no tool can follow.** One rule has it filled in:

> *"WHO recommendations for routine immunization – summary tables (March 2023) (1)"*

The other 24 do not. Both halves of that matter: turning the string into a resolvable, versioned,
hash-pinned link is what this repository is for, and **counting how many rules have no source at all
is a question nothing can answer today.**

```bash
npx tsx smart-base/L2-dmn/schemas/extract-citations.ts input/dmn/DAK.DT.IMMZ.D2.DT.BCG.dmn
# 25 rules, 1 distinct L1 citation(s), 2 nodes, 1 edges
# coverage: 1/25 rules cite an L1 source (16 carry no annotation at all, 8 stop short of the reference column)
#   ^ a gap in the source, not in this tool. Reported so it can be fixed upstream.
# bpmn link present: http://smart.who.int/immunizations/bpmn/Determine.bpmn#if the client is due for a bacille...
```

Note the second line: the DMN also carries a `dmn:usingTask` href into the BPMN. The BPMN↔DMN
cross-model edge everyone wants **already exists in the artefact** — it just has no graph to live in.

## The L1 model

L1 holds **what WHO says and where it is printed**, and the pointers a DAK uses to reach it. Thirteen
classes in three groups, eighteen closed value sets, and **no edge pointing out of L1**: every higher
layer points down into it. Each class is grounded in an artefact that exists today and was checked
against real ones — the *WHO handbook for guideline development* (2014), the antenatal care guideline
(2016) and its web annexes, the HIV strategic information guidelines (2022), and the immunization
DAK's workbooks. `smart-base/L1/schemas/generated/l1.json` cites them by section and page in `groundedIn`.

**Layout: where it is printed** — `publication` (typed `identifiers`, `publicationType`,
`grcStatus`, `reviewBy`, `sha256`), `publication-section`, and `publication-element`: a table, row,
footnote, figure, chart, image, flowchart, box or list. An element stores only what no content node
holds; a table's `columnMap` says which column is filled from which content field when it is
re-rendered, so a recommendation's words are stored once however often they are printed.

**Content: what WHO says** — every content node is `definedIn` exactly one publication (its
authority) and `presentedIn` any number of sections or elements, in any publication. Restatement is
simply those two pointing into different publications.

- `recommendation` — verbatim `statement`; `kind` (recommendation, context-specific, research-context,
  good practice statement, no-recommendation); `direction`, optional `strength` and
  `overallCertainty`; `status` and `changeStatus`; slots `intervention`, `interventionType`,
  `population`, `setting`, `provider`, `timing`, quoted from the source. `partOf`, `supersedes`,
  `refines` between recommendations.
- `remark` — typed: definition, implementation, precaution, contraindication, subgroup, research gap,
  training.
- `key-question` — PICO in WHO's own words; `outcome` is a node, because evidence attaches to it and
  one list is shared by several questions; `evidence` is one row of an evidence profile, typed by
  scale (GRADE or GRADE-CERQual).
- `health-intervention` — an intervention from a catalogue (UHC Compendium, ICHI, CDHI, digital
  ones included), a peer of recommendation; a DAK draws on both.
- `indicator` — identified by its reference number (PRV.3), printed in several places and stored
  once; it `measures` an intervention or a recommendation and is `justifiedBy` the recommendation
  its rationale cites.

**References: how a DAK points here** — `citation` (one per citation string, `citationKind`
reference or placeholder), `reference-entry` (one row of an artefact's own reference list:
"(1)" resolves once, and every citation numbered to it shares the result), and `terminology-code`.

### Boundaries, structurally enforced

**Terminology is a leaf.** `terminology-code` carries `system`, `code`, `display`, `version` and
nothing else, and the ontology licenses no edge out of it. This graph records that a code was cited,
never what it means. An unknown code system is reported, because a misspelt one silently breaks
joins across guidelines.

**L1 points nowhere.** DAK files are the DAK's material, so `external-artifact`, `appearsIn` and
`implementedBy` live in L2 and point down at L1. Before 3.0 they sat in L1 too, which gave "which
artefacts implement this recommendation?" two paths and every extractor a choice of one.

**Judgements say so.** Reading a PDF is never `derived`: the model sets a minimum derivation per class
and edge, and a `decided` judgement records who made it and when. `ambiguous` is a terminal state for
a citation, not a failure, and a placeholder never resolves.

**Identity comes from what WHO prints.** L1 IRIs live under one WHO-wide namespace and are built from
the ISBN (or IRIS handle, DOI, ISSN) and the published number, by `smart-base/L1/schemas/kgid.ts`, so two extractions
of one guideline give one node. Each content node carries a `contentHash` of its verbatim text, so a
corrected PDF is re-checked node by node rather than wholesale.

## The L2 models

`DAK.fsh` describes itself as "a complete Digital Adaptation Kit with metadata and all 9 DAK
components". The component layer carries all nine — eight as classes, and `healthInterventions` as
`l1:health-intervention`, the catalogued interventions L1 declares.

| # | Component | Class | Points at |
|---|---|---|---|
| 1 | healthInterventions | `l1:health-intervention` | Dublin Core references |
| 2 | personas | `persona` | ActorDefinition / GenericPersona |
| 3 | userScenarios | `user-scenario` | narrative, plus persona ids |
| 4 | businessProcesses | `business-process` | a BPMN file, by URI |
| 5 | dataElements | `data-element` | a FHIR canonical |
| 6 | decisionLogic | `decision-support-logic` | a DMN file, by URI |
| 7 | indicators | `program-indicator` | numerator/denominator prose |
| 8 | requirements | `functional-requirement` · `non-functional-requirement` | statements, actors |
| 9 | testScenarios | `test-scenario` | a Gherkin feature file, by URI |

Every component reaches its file through `sourcedFrom`, whose target is an `l1:external-artifact`.
The BPMN and DMN subgraphs then describe that file's interior **at the same IRI** — so opening a
file never creates a second name for it.

### Two mechanisms for one problem

A DAK links its components together four times, and it does so two different ways:

| Link | Mechanism | Resolves |
|---|---|---|
| requirement → persona | `actor = Canonical(SGAuthoring.Persona.X)` | **46 / 46** |
| BPMN pool → persona | `@name` == ActorDefinition `title` | 6 / 8 |
| DMN decision → BPMN task | `usingTask/@href` fragment == task `@name` | 0 / 1 |
| DMN clause → data element | names inside expression prose | 0 / 10 |

The first is a canonical reference and it resolves exactly. The rest are string matching, and they
resolve when the strings happen to agree. Same estate, same personas — **the mechanism that works
already exists; BPMN and DMN just do not use it.** That is the finding this layer makes visible,
and it is more useful than any individual broken link.

```
warning: participant "Clinical SME" -> persona unresolved
warning: participant "QC Reviewer"  -> persona unresolved
```

Both personas exist, titled *"Clinical Subject Matter Expert"* and *"Quality Control Reviewer"*.

### Coverage is the other half

```
DAK component coverage (DAK.fsh declares nine):
  · healthInterventions  none in this IG
  ✓ personas             22 instance(s)
  · userScenarios        none in this IG
  · businessProcesses    none in this IG
  ...
  ✓ requirements         41 instance(s)
  7 of 9 components have no instance here.

2 file(s) present with no component declaring them:
  input/bpmn/SGAuthoring.DAKLifecycle.bpmn  (would be businessProcesses)
  input/dmn/DAK.DT.IMMZ.D2.DT.BCG.dmn       (would be decisionLogic)
```

smart-base defines the model rather than instantiating a DAK, so most components being empty is
expected there. The gap that is **not** expected is the last two lines: a BPMN and a DMN sit in the
input tree with no component declaring them. Nothing else in the estate reports either direction.

## Using it

**The schema:**

```bash
# a published IG -> the L3 index, with coverage across every artefact type
npx tsx smart-base/L3/schemas/extract-l3.ts --ig <path-to-IG> --out /tmp/l3.json

npm run build --prefix smart-base/L1/schemas   # regenerate every layer's generated/ (JSON, contexts,
                                               # Turtle, Cypher) and the FSH, plus all.{cypher,ttl}
npm run check --prefix smart-base/L1/schemas   # fail if any of it is stale
npm test --prefix smart-base/L1/schemas        # includes the negative tests: tier 2 fails on what it claims to catch
```

**Extraction, when you point it at a DAK.** Output goes wherever you say; nothing is written back
into this repository.

```bash
# DMN -> L1 citation nodes, with coverage
npx tsx smart-base/L2-dmn/schemas/extract-citations.ts <file.dmn> --out /tmp/l1.json

# dak.json + the FSH tree -> the nine components, with coverage across all of them
npx tsx smart-base/L2/schemas/extract-dak.ts --dak <dak.json> --fsh <input/fsh> \
  --bpmn-dir <input/bpmn> --dmn-dir <input/dmn> --out /tmp/dak.json

# one BPMN file's interior
npx tsx smart-base/L2-bpmn/schemas/extract-bpmn.ts <f.bpmn> --personas <dir> --out /tmp/bpmn.json

# one DMN file's interior; pass --bpmn to resolve usingTask instead of recording it unresolved
npx tsx smart-base/L2-dmn/schemas/extract-dmn.ts <f.dmn> --bpmn <f.bpmn> --out /tmp/dmn.json

# tier 2. Several documents at once, so a reference from one to another resolves across the set.
npx tsx smart-base/L1/schemas/validate.ts /tmp/l1.json /tmp/dak.json /tmp/bpmn.json /tmp/dmn.json
```

TypeScript, run with tsx after `npm ci` in `smart-base/L1/schemas/` (zod; jsonld for the context tests).

**Neo4j** — `cypher-shell -f smart-base/L1/schemas/generated/all.cypher` for the whole model, or one
`smart-base/<Layer>/schemas/generated/<layer>.cypher` at a time **in dependency order**: a layer licenses edges onto
classes from the ones it imports, and Cypher does not treat an empty `MATCH` as an error, so loading
out of order silently drops those edges. Every class node carries `layer`, so one subgraph is
selectable on its own. See [`smart-base/L1/schemas/docs/VISUALIZING.md`](VISUALIZING.md).

**Protégé** — `smart-base/L1/schemas/generated/all.ttl` is the whole model merged, 1885 triples, and parses as one document.
Pairwise edge licensing is carried as qualified sub-properties, since licensing here is per
class-pair while an OWL object property has one global domain and range.

## Validation

| Tier | Checks | By |
|---|---|---|
| **T1 Shape** | Document matches the graph schema | JSON Schema 2020-12 |
| **T2 Conformance** | Node types are declared classes; edges are licensed; references resolve across the document set; properties are declared; values come from their value sets; L1 IRIs have their scheme's shape; content hashes match the stored text; derivation meets each class's and edge's minimum, and a decided judgement says who and when; a strength has a direction; GRC status, quoted slots, overall certainty and one-copy-of-the-words are checked; a `resolved` citation or join actually resolves, and a placeholder never does | `smart-base/L1/schemas/validate.ts` |
| **Goals** | L1 still answers what it exists for: impact, coverage, citation resolution | `smart-base/L1/schemas/test/goal.test.ts` |
| **T3 Fidelity** | Does the graph faithfully represent the PDF, the BPMN, the DMN? | Human. Never auto-passed |

T2 is negative-tested by [`smart-base/L1/schemas/test/negative.test.ts`](../test/negative.test.ts) — 54 cases, run in CI.
The documents it checks are built in the test rather than committed, because this repository holds
no data; the L1 ones quote the real ANC and HIV guidelines and carry their real ISBNs. Each rule above
has a case that breaks it and expects the located message, in the subgraphs as well as in L1. Some
cases assert the opposite — a free-text BPMN branch label, an unresolved join, a reference into another
layer's document, an ANC recommendation with a direction and no strength, a slot quoted from a table
caption — because a check that fires on the normal case trains people to ignore it. Findings that are
judgement calls (unrecorded GRC status, an unquoted slot, an unknown code system, overall certainty
above the lowest critical outcome) are warnings, and their cases assert they are warnings.

The goals are tested by [`smart-base/L1/schemas/test/goal.test.ts`](../test/goal.test.ts), which runs the queries in
[`smart-base/L1/schemas/l1-queries.ts`](../l1-queries.ts): a superseded recommendation reaches its replacement,
where it is printed, the evidence behind it and the DAK artefact implementing it; coverage counts
unrepresented recommendations and DMN rules cited / placeholder / none; a citation reaches its
publication through its reference entry, with the mechanical step and the judgement told apart.
When an evaluation criterion for L1 is agreed, it becomes a case there.

Loading an ontology also checks it: every class an edge names and every predicate it uses must be
declared in that layer or something it imports, and every value-set binding must name a declared
property and a declared value set. That check caught a real typo the first time it ran.

## Status

**The extractor works on real data.** It reads a DMN, finds the L1 reference column by its
description rather than by column index, deduplicates citations across rules, preserves the `(1)`
back-reference into the source bibliography, and hash-pins the source file.

**It deliberately does not resolve citations.** Matching *"WHO recommendations for routine
immunization – summary tables (March 2023)"* to a publication node is a judgement, and the schema
requires a note and evidence for a judgement. An extractor that resolved silently would be
manufacturing provenance.

**All three L2 extractors have been run against real data.** Against smart-base they produced 386
nodes and 516 edges: 234 from `dak.json` and the FSH tree (22 personas, 41 requirements, 170
statements, 46/46 canonical references resolved), 100 from the lifecycle BPMN, 51 from the BCG
decision table, 2 from the citation extractor. Those documents are not committed here — this
repository is the schema.

**smart-base disagrees with itself about scheme.** `dak.json` declares `https://smart.who.int/base`;
the BPMN's `targetNamespace` is `http://smart.who.int/base/bpmn` and the DMN's is
`http://smart.who.int/immunizations`. An IRI is an identity key, so two schemes for one authority
split every persona into two unconnected nodes. `kgid.ts` normalises to https and every extractor
warns that it did — the graph joins, and the inconsistency stays visible for someone to fix.

**Not built yet:** no PDF extractor, so `publication` and `recommendation` nodes must currently be
authored by hand; the L3 subgraph; and the FHIR projection (CPG-on-FHIR is already a smart-base
dependency, EBM-on-FHIR is not — the mapping is intent until checked against the installed IG
packages).

**Known limits, stated rather than hidden.** No data dictionary instance ships in smart-base, so
every `data-element` recovered from a DMN is a name that was referenced rather than a definition
that was found. The BCG table's `usingTask` points into `Determine.bpmn` in the immunizations DAK,
which is not in this clone, so that join is recorded unresolved rather than guessed at. No DAK in
the estate ships a Gherkin feature file, so `test-scenario` has no instance and the feature file's
interior is deliberately unmodelled.

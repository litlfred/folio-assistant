smart-guideline-end-to-end

Skill id: smart-guideline-end-to-end · Package: authoring-who-smart-guidelines · Process: smart-guideline-end-to-end.bpmn

This skill is the order, the hand-off between stages and the adjudication rule. Each stage is its own named skill with its own input and output contract. What a stage does, it says in its skill; nothing here repeats it. Every record a stage or review leaves uses a schema that already exists, named in What it reuses. If a stage needs something its skill does not say, fix that skill. Do not add it here.

Input and output

The contract is input.schema.json and output.schema.json.

  • In: the request, verbatim; the useCase when stage 0 is already done; the guideline’s feature branch.
  • Out: every stage’s artefact under the name the stage table gives it (useCase, l1Sources, l1Kg, l2Dependencies, l2Assets, l3Dependencies, ig, applicationBrief, wireframes, application), and one adjudications entry per stage with its QaReview and outcome. The guideline is done only when no outcome is pending.

The rule that shapes everything: adjudication is QA, not a gate

Owner, 2026-10-14: “while adjudication is required at every step, it is a QA issue, not a gate. so once agent produces L2 it can produce L3.”

So every stage ends in a fork, not a decision:

stage n (agent) ──┬──► stage n+1 (agent)          keeps going
                  └──► adjudicate stage n (human)  runs beside it

What follows from that:

  1. Every stage needs adjudication, and the guideline is not done until every adjudication is recorded. Not waiting is not the same as skipping. The process ends only when the last stage and all its adjudications are in.
  2. An asset built on unadjudicated input says so. Each derived KG node already names its inputs in wasDerivedFrom (hash-pinned, so a changed input makes it stale; smart-base/kg/src/graph.ts). The adjudication state of an input goes on that edge’s open properties, beside the resolutionStatus and reviewStatus that recommendation-extraction already puts there: adjudication: pending while the input’s review is open. This is provenance, not a warning banner. When the review closes, the property updates.
  3. A rejection reopens the stage, and the flag spreads downstream. A request-changes or reject decision files a bean against the stage. Every downstream asset derived from the rejected item gets adjudication: rejected-upstream on that edge, and is re-derived when the stage is redone. It is not deleted ahead of time: the re-derivation may come out the same.
  4. The agent never adjudicates. The person who signs is named by role (table below). An agent may prepare the review material, never record the verdict. This is recommendation-extraction’s sign-off rule applied to every level.

The order is a rule: L1, then L2, then L3 (owner, 2026-10-15)

QA-not-a-gate is about verdicts. It never licenses skipping a stage. Owner, 2026-10-15: “this is a process failure to not make L1 and L2 assets first and have sign off”, ruled as order strict, sign-off QA:

  1. Each stage’s output exists before the next stage starts. Stage 2 writes library/<bib>/l1-extraction/ for every source of the use case; stage 4 writes the L2 assets; only then does stage 6 write FSH, CQL or any other L3 file. Source documents (a schedule poster, a slide deck) are stage-2 input, never direct input to L3.
  2. Sign-off is requested before the next stage starts. Each stage’s review items (Process_Review, one per asset) are opened, staged and handed to their adjudicating role before the next stage begins. The verdict is not waited for (QA, as above), but an asset whose review was never requested has not finished its stage.
  3. Every L3 asset names the L2 asset it implements, and every L2 asset the L1 node it rests on, in wasDerivedFrom with the edge’s adjudication state. An L3 asset with no L2 upstream is a finding, not a shortcut: a green build and passing tests do not make up for it.
  4. A request that skips stages is still this process. “Adapt X to using these documents" is stages 0–6. If the request names no L1/L2 work, the agent does it anyway and says so; it does not read the absence as permission to go straight to L3.

Why the rule is written down. On 2026-10-15 an agent asked to adapt the WHO immunization guidelines to Uganda (https://github.com/litlfred/smart-immunizations-uganda/issues/1) read the poster and the UNEPI deck by eye and wrote CQL, a PlanDefinition and prose pages directly (#3): no library entry, no L1 extraction, no L2 decision table, no review requested. CI was green throughout. The causes were that the new repository had no pointer to this skill and no platform mount (smart-guideline-create §6 now requires both), and that nothing checked the order (rule 3 above).

l2-dak-authoring.bpmn follows the same rule (owner, 2026-10-14). Its Clinically accurate? decision now runs beside assembly, not before it: a parallel fork after the authoring join starts clinical validation and assembly together. changes needed still sends the work round again, which re-assembles the DAK. validated ends in its own event.

Stages 0 and 7 belong to the requester: the agent asks, and never invents the use case or the application.

Between stages 5 and 6 sits Gateway_L3Ready, the order rule as a decision. It is not a stage, but the check it decides on has its own skill, l3-readiness (owner, 2026-10-16), run as Task_L3Ready just before it: In l1Kg, l2Assets, the reviews requested and the L3 artefacts about to be written; Out ready and the findings. No goes back to stage 4.

Publication of the IG (the end of dak-l3-ig.bpmn) runs as normal and is not on the path to stage 8: an application can be built against an IG that has not been published yet.

Every adjudication in the process is a call to cat-harness’s generic review, Process_Review (processes/content/review-task.bpmn): it works out what kind of change it has, runs the review that fits, and accepts or sends back. When reviewers disagree, that process hands over to Process_Adjudication. Neither is copied here.

Staging: every review looks at a staged preview

Each stage commits to the guideline’s feature branch, and that branch is staged by feature-staging (Process_FeatureStaging) on the site its section Which site names: a guideline in a repository of its own is previewed on that repository’s own Pages, and smart-base itself, which folio-assistant mounts, by a staging re-pin on the platform’s site. An IG repository’s site needs its AST cache seeded first (fhir-ig-create, new-repo step 5). Neither rule is WHO’s, so neither is restated here.

The IG Publisher’s branches/ preview (ghbuild.yml, /deploy) is the IG’s, not this content’s, and is never the preview for it. A review item never links to source alone. It links to the staged page, through staging-review, which returns before (main) and after (staging) URL pairs. A new guideline that has no repository yet is staged inside the current one first, as smart-guideline-create already defaults to (in-repo, a staged sub-KG).

Per-asset review

Every asset a stage creates or changes gets its own review item. An asset that was reused unchanged gets none: its upstream’s adjudication covers it. The review item shows the asset the way its reviewer reads it, not as source, on the staged preview. At L2 it is a run of l2-component-edit-review.bpmn, whose skill gives each row’s checker, renderer and reviewer:

Forms are designed as wireframes at L2

A data-entry form is designed once, at L2, and the L3 Questionnaire is derived from that design. It is not designed at L3 and then drawn back as a picture for review.

  1. Stage 4: design. For each business-process activity where a persona records data, the agent runs wireframe-design-review in its design use. The intent comes from the L2 assets: the persona (who), the activity and its user scenario (what they do), and the core data elements the activity captures (what it shows). That produces two or more candidates, each with a web and a mobile layout, using real content: the data elements’ labels, value sets and the DMN rules that show or hide a field. Each field carries the id of the core data element it captures (a data-element attribute). Under the QA rule the agent goes on with its recommended candidate. The review and the choice between candidates (Process_Adjudication, Process_OptionsAnalysis) are that form’s stage-4 adjudication.
  2. Stage 6: derive. The Questionnaire follows the chosen wireframe: one item per field, in its order and grouping, each item’s definition pointing at the logical-model element of the same core data element, and enableWhen taken from the same DMN rules.

  3. Stage 6 review: fidelity. It is fhir-harness’s skill fhir-questionnaire-wireframe (process Process_QuestionnaireWireframeReview), run on each built Questionnaire with the chosen wireframe as its L2 wireframe. Its fidelity step is fhir-harness check-wireframe-questionnaire, which pairs the wireframe’s data-element attributes with the Questionnaire items’ definitions. A field with no item, an item with no field, or a different order is a finding. The check compares two lists and renders nothing:

    bun run fhir-harness/scripts/check-wireframe-questionnaire.ts <wireframe.html> <Questionnaire.json>

    A wireframe that draws web and mobile as separate subtrees marks each with data-layout, and each layout is checked on its own. A Questionnaire item names its data element by definition (the URL, or the element path after #) or by code[].code. Exit 0 faithful, 1 a finding, 2 unreadable input.

If the chosen wireframe changes later (a review asks for it), the Questionnaire derived from it is flagged rejected-upstream like any other derived asset. A change request on either side — through ✍ suggest or the questionnaire-change issue form — says which side was edited, and the other is brought back in line (fhir-questionnaire-wireframe, step 7).

An adaptation is reviewed as a diff. When the asset came from a stage-3 or stage-5 dependency with decision: adapt, the review item shows before (the upstream asset at its pinned version) and after side by side, with the change highlighted, and the L1 node that justifies the change. At L3 the diff is fhir-harness’s ig-ast-delta (element-level, per resource). At L2, and for anything rendered, it is before-after-preview, drawn with one of the DiffRenderers in schemas/diff-renderers.ts. A changed asset with no L1 justification is a finding in its own right: an adaptation is local evidence or local policy, and the KG has to say which.

The record of a review item is a cat-harness QaReview (qa-review/v1, schemas/qa-review.ts): subject is the asset, and each verdict is a Decision whose role is the adjudicator’s role id. Its outcomes are the ones to use:

outcomemeaning here
approvethe asset stands
request-changesreopen the stage for this asset. If the reviewer wrote the fix themselves, it goes in an AuditNote and the agent applies it as given
rejectthe asset is wrong at the root (wrong source, wrong dependency). Reopen the stage that chose it

At L1, recommendation-extraction keeps its existing review: {by, at} fields on the mapping. The QaReview is the record of the stage’s review, not a replacement for those fields.

New guideline or adaptation: one process

An adaptation is not a separate process. It is this process with stages 3 and 5 returning adapt decisions, which makes stages 4 and 6 show diffs. A new guideline is the case where those stages return only reuse, extend or nothing. Do not maintain two copies of the stages.

What this does not change

  • The WHO DAK component set and L1–L4 layering: smart-stack-layering.
  • How a new repository or IG is set up: smart-guideline-create. Run it before stage 4 if the guideline has no home yet.
  • The persona-swimlane lifecycle (planning, QC, translation, publication) on the IG’s Authoring Process page. Those phases still run. This process says what goes into phases 2a and 2b, and what comes before and after them.

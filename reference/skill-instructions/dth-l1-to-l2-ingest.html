dth-l1-to-l2-ingest

Skill id: dth-l1-to-l2-ingest · Package: authoring-who-smart-guidelines · Stages 0-2 of dth-authoring for a handbook that WHO has already published. Worked examples (2026-10-31): litlfred/dth-phc#1, dth-sc#2, dth-pc#2, dth-sfp#1; pilot litlfred/dth-hrh#47.

An L2 DTH is a handbook whose narrative validates against the glossaries and links to the ArchiMate model. The owner’s definition (2026-10-31): the handbook can “naturally utilize and validate against the glossaries”, and its “narrative content has a rendering/linkage/representation in ArchiMate”.

Where things go

whatwhere
shared glossary, every ArchiMate element and view, roles every DTH has (business analyst, health informatician, …)smart-ra
the handbook’s narrative, its own terms (linked to smart-ra’s), its DAK-kind blocks, links from text to ArchiMate elementsthe handbook’s repo
the L2 DTH kind, its checks, the DAK kinds and their fieldssmart-base
the source PDF and its L1 entrywho-iris library/<isbn>-eng

The workplan comes first

Write one workplan per handbook and show it to the owner before any content work. It lives as an issue on the handbook’s own repo. Open it with the issue form dth-workplan.yml: copy it to .github/ISSUE_TEMPLATE/ in the fork, so the BPMN, roles and DMN sections cannot be skipped (owner, 2026-10-31, option A: skill plus issue form). Every workplan has these sections; the last three are required (owner, 2026-10-31):

  1. Source: IRIS item, ISBN, edition, who-iris entry, and anything missing from it (a missing PDF, a missed glossary).
  2. Repo vs smart-ra split, per the table above.
  3. Dependencies: other DTHs it mounts (dth-pc and dth-sfp mount dth-sc).
  4. Glossary: the source’s own glossary terms (see Terms below) and every conflict with smart-ra.
  5. ArchiMate: elements and views it needs, existing or new.
  6. Business processes as BPMN: one diagram per business process the handbook describes, each lane naming a role from section 7. Draw a process only as deep as the handbook goes. A worked example taken from a WHO DAK links to the DAK’s version and is not redrawn.
  7. Roles as structured entries: every role as a persona or actor-definition block, linked to its BPMN lanes, a smart-ra ArchiMate role and a glossary term. Systems are system actors.
  8. Decision tables as DMN: only tables the handbook itself states. Each cites its source passage. Thresholds come only from the source text, never invented. A model the handbook does not recommend is not a decision table.
  9. Schema gaps: content with a fixed shape that no kind holds yet. These are proposals for review by the architect group and the handbook owners, not approved work.

Ids are per handbook and per kind: <HB>-BP-nn (business process), <HB>-R-nn (role), <HB>-DT-nn (decision table), for example PC-BP-01.

Housekeeping

  • Forks only. Every commit, PR and issue goes to litlfred/dth-*. Never push to, or open a PR or issue on, a WorldHealthOrganization/dth-* repo without the owner’s explicit permission.
  • Issues on the fork. GitHub turns Issues off on a fork. Ask the owner to tick Settings > Features > Issues, then put the workplan issue there, not on smart-ra.
  • When in doubt, file an issue; do not guess (owner, 2026-10-31). An agent that hits a problem or is unsure during ingestion files it where the handbook tracks work: a GitHub issue on the fork, or a row in its review sheet, whichever is available. It records what it found, the page, and the options it sees, then carries on with work that does not depend on it.
  • Conflicts are issues, not choices. When the handbook defines a term differently from smart-ra, open an issue on litlfred/smart-ra that keeps both definitions, each quoted with its page. Do not pick one.
  • Third-party material stays out. A figure or table the handbook uses by someone else’s permission is outside the handbook’s licence: do not copy it; leave a note pointing to its page.
  • Mechanical before agentic. Content with a fixed shape (a step box of inputs, tasks, outputs, resources and risks; an annex template; a table) is read from the PDF by a script (for example pdfplumber) and checked by a person. An agent writes only what has no fixed shape.
  • Verbatim, with the page. Definitions, tables and quoted passages are copied word for word, each with its page.
  • Fetching what the sandbox cannot reach (a missing PDF, a private repo): file a bean and give the owner a ready-to-paste prompt for the local agent.
  • Read the workplan issue’s comments first. The owner’s local agent may already have done some steps.
  • The first merge into a bare fork needs the owner’s OK. After it, turn on Pages for the fork.
  • Check verbatim quotes by script. Text shown as a verbatim quote must be found in the normalised L1 text by a check, not by eye (dth-phc#3: seven chapter 2 role quotes were not in the L1).
  • Agents never sign off. An agent never writes the owner’s name into signedOffBy in l1-exclusions.json. An exclusion an agent writes stays a proposal until the owner signs it.
  • A table in the PDF is a table in the L1. When ingestion flattens a table or a figure’s cells into lines, fix the L1 entry in who-iris so the cells sit in a table, word for word. Flattened cells that cite another guideline’s figure (“Fig. 8.4 …”) read as figures this handbook declares, and figure:coverage reports them missing (who-iris#157, PHC Fig. 13).
  • Regenerate coverage after every L1 repin. Sentence keys move when the L1 entry changes, so committed l1-coverage* outputs go stale. Rerun the coverage writer in the same PR as the who-iris repin (dth-phc#5).
  • Texts name things by title or number. A handbook text cites a block, figure or table by its title or number, never by a raw id.
  • Validators live in the platform. Glossary validators and L1 coverage checks belong in folio-assistant-core, not in the handbook repo (core#377).

Blocks, figures, ArchiMate and DMN

  • Blocks link to ArchiMate through the glossary. A block’s Markdown shows a **Concepts:** line built from meta.glossaryTerms. Only figure blocks link straight to an ArchiMate view (core#407).
  • Figures are rebuilt by type. An architecture figure becomes ArchiMate, a process becomes BPMN, a data model becomes a class diagram, and a chart becomes SVG from its data. Third-party and country figures stay cited images. The original PNG is kept as evidence.
  • Never edit a shipped ArchiMate draft (for example 0.3.0-draft.1). Write the next draft.
  • DMN house rules. A table is complete. It has an explicit “unknown” outcome, and catch-all rules name their inputs. No rule is narrower than the source. Names are noun phrases. Each table has one source.

Terms

The handbook’s own glossary is the first source of terms: extract it as SKOS candidate terms, verbatim, from the latest edition, by folio-assistant-core’s glossary-terms skill (“Source glossary first”). Use the handbook’s words, not ours, in blocks and in ArchiMate names.

Then

Once the owner approves the workplan: scaffold the repo from the dth-hrh layout (stage 0), seed the folio from the L1 by the handbook’s own chapter outline (stage 2), and continue with dth-authoring stage 3.

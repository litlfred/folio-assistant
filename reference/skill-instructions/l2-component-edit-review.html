l2-component-edit-review

Skill id: l2-component-edit-review · Package: authoring-who-smart-guidelines · Process: l2-component-edit-review.bpmn (Process_L2ComponentEditReview), called by every authoring track of l2-dak-authoring.bpmn

Owner, 2026-10-14: “make sure all L2 agent edit-human review process for DMN and BPMN, glossary/data dictionary, user stories and personas for the DAK are documented as part of subprocess and tools/skills where necessary.”

This skill adds one table and no mechanism. Every step of the subprocess runs a skill that already exists. Review is cat-harness’s Process_Review. The verdict is a qa-review/v1 QaReview. The links follow staging-review’s deep-link rule, and the preview follows before-after-preview. What differs between components is only which renderer, checker, diff and reviewer a pass uses, and the table below records that.

The shape: edit, check, render, then fork 

edit ─► check ─► render + stage ─┬─► hand on (adjudication: pending)   the track continues
                                 └─► ask for review ─► Process_Review ─► verdict
                                       approve          ─► done
                                       request-changes  ─► edit again
                                       reject           ─► reopen upstream, flag derived assets

Adjudication is QA, not a gate (owner, 2026-10-14). The track that called the subprocess carries on as soon as the component is staged, and nothing waits for the verdict. But not waiting is not skipping: the call ends only when both branches have ended, and the DAK is not adjudicated until every component’s verdict is recorded. These are rules 1 to 4 of smart-guideline-end-to-end, applied to one component.

An adaptation is a diff against its pinned upstream, not against an empty file. At L2 that diff is the renderer’s own. At L3 it is fhir-harness’s ig-ast-delta. A changed component with no L1 justification is a finding in its own right.

Asking for review

Task_RequestReview follows staging-review’s deep-link rule:

  • the request carries one deep link per changed page, to the anchor (…/STAGING/<slug>/<path>#<anchor>), beside the same page on main as before;
  • the pages come from the change (rendered-impact), not from judgement;
  • if there is no preview yet, the request says so.

smart-base content reaches staging by a folio-assistant staging re-pin (bun run cat mount:remote --staging). It never goes through /deploy.

Where the request goes is a judgement, and more than one place may be right. Ask where the person will look: this conversation, the issue the work came from, the pull request. Each place carries the same links. The question follows interaction-modality. A tagged PR comment becomes a todo (review-comments). Feedback on published content goes through content-feedback.

Recording the verdict

Process_Review records a QaReview whose subject is the component and whose Decision.role is the reviewing role:

  • approve: the derived edges’ adjudication: pending becomes the outcome;
  • request-changes: the agent edits again (a fix written in an AuditNote is applied as given), re-stages, and asks again;
  • reject: Task_ReopenUpstream files a bean against the stage that chose the source or dependency, and flags every derived asset rejected-upstream.

The agent never records a verdict.

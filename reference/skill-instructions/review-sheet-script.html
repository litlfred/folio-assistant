The review sheet’s Apps Script

The sheet itself, its tabs and who writes each column are the public-comment skill’s (§”The live review sheet”). This skill is the script that keeps that sheet’s links current, and the Tool review-sheet-sync that builds it.

Links inside a cell’s text (a section, a page, a “No. n” in a joined column) cannot come from a formula: a formula makes at most one link per cell. They are rich text, and rich text goes stale the moment the sheet changes. So the sheet keeps them itself, with a Google Apps Script bound to it (owner, 2026-10-30: “Apps Script in the sheet”). Never paste them by hand from an agent: it costs about 30 kB of tool output per 30 rows, and the next edit undoes it.

A question to people goes in the sheet, not only in chat (owner, 2026-10-31: “how would the editor / feedback committee / review committee know if there was a card … should be there and in the agent column”). When the agent needs a person to decide something about a change set, it writes the question into that row’s agent column, under its proposal, as

Decision needed: <the question>
  A. <option> (recommended)
  B. <option>
Answer in your Blue column, or ask an Editor to set Ready for agent.

and sets the row’s Agentic status to Needs human on the Agent tab. The script shows the whole “Decision needed” block, up to the next blank line, in bold, black, in the agent’s feedback cell (owner, 2026-10-31: “decision needed should be bold highlighted … so clear”; red was tried and was too glaring). The sheet never shows those words (owner, 2026-10-31: “unclear: needs human to do what?”): Agentic status opens with Needs you: answer the agent’s question, saying where the question is and what to do, and Agentic status (filter) reads Needs you: answer the agent's question, so the “Needs you” filter view finds it. A card in the agent’s chat may carry the same question for the owner, but the sheet is the record people see. When the question is answered, the agent removes the block from the feedback and adds the decision, with who made it, to Disposition (agent) (below).

Disposition (agent): the change set’s decisions and dispositions (owner, 2026-10-31: “agent should NOT remove historical decisions”, “decision history in own column Disposition (agent), not in Change Set Feedback (agent)”, “new col left of agentic status”). The agent keeps one record per change set in the Agent tab’s Disposition (change set), and the script shows it, read-only, in the Green Disposition (agent) column, just right of Ready for merge (owner, 2026-10-31, moved from left of Agentic status), on Review Change Sets or Contributor Feedback. An empty one still reads, in bold, ⚠ No disposition yet for Nos. 127 to 131 and 134 when the change set has comments (“make sure … mechanical ‘this PC has no disposition’ is shown”). It holds:

  1. The decision history, oldest first, one line per decision, never removed or rewritten: Decided (Q1, 2026-10-31): A, by the Editor; <what it means>. When a Decision needed question in the agent’s feedback is answered, the decision moves here, and the question leaves the feedback cell. Change Set Feedback (agent) holds only the current proposal and any open question.

  2. One disposition per comment (owner, 2026-10-31: “enforce more structured Disposition (change set), so each PC is given a disposition”), after an optional overall statement (“can also be an overall disposition statement without reference to a PC”):

    Overall: <a statement for the whole change set>
No. 136: Accepted. DPI-F defined at first use, with a glossary entry.
Nos. 127 to 135, 138 and 139: Not accepted. Already addressed.
No. 326: Partially accepted. <what was done, and what was not>

    A disposition is one of Accepted, Partially accepted, Not accepted, Noted, Deferred, Duplicate, Out of scope or Withdrawn, first after the colon. Every comment of the change set gets exactly one. The script checks this (dispositionProblems) and puts any problem, in bold, at the top of Disposition (agent): ⚠ No disposition yet for No. 140, 141, ⚠ No. 9 is not in this change set, ⚠ No. 136 has two dispositions, or a line whose word is not a disposition. It never edits the Agent tab.

    Drawn from the people’s dispositions (owner, 2026-10-31: “QC check is that each PC # in the CS has a disposition. agent should draw from human blue dispositions when drafting”). Before writing a comment’s line, the agent reads that comment’s Blue Disposition on Review Public Comments (drafting: the row’s Blue Disposition). Where a person has set one, the line uses the same word, and the text says what was done; where it is empty or Pending, the agent proposes one. The QC check is that every comment number in the change set has a disposition; a word that differs from the people’s is flagged (⚠ No. 136: Accepted here, Noted in the people's Disposition) for the committee to settle, and never corrected by the agent or the script. Written before the staging preview is made, and kept current with each push.

Once an Editor sets Ready for merge to Yes, the record as it stands is the summary: the agent puts it in the merge commit and posts it as the closing comment on the change set’s issue.

Change Set Feedback (agent) (Review Change Sets, green, right of Ready for merge; owner, 2026-10-31). The agent writes its proposed direction for resolving the change set here, so the Feedback Review Committee and the Editor react to a proposal rather than drafting from nothing. Any question for people is written here too (§”Inputs and outputs”). The script only marks it stale. It is a proposal, never a person’s feedback: a tool that collects the people’s Committee Feedback (…) columns by header must leave it out, or show it apart, and it decides nothing.

Names (owner, 2026-10-31). The people’s columns were Architect Feedback … and are Committee Feedback …, for the process role. The agent’s columns are Change Set Feedback (agent) (public comment; it was Architect Feedback (agent)) and Feedback (agent) (drafting; it was Contributor Feedback (agent)). Their names live in Config COLS (rcs.agentFeedback, draft.agentFeedback). The script finds each column under any of its names (aliasOf, SAME_COLUMN), and a feedback basis written under the old names still matches, so renaming marks no proposal stale.

Every No. n in Review Change Sets links to #gid=<Review Public Comments>&range=A<row>. Do not link to a named range by #rangeid=: Sheets shows “Invalid range” for a named range whose id was set through the API.

One script, one Config tab per sheet (owner, 2026-10-31, option C). Code.gs is the same file for every document: review-sheet.gs, stamped with its commit and made plain ASCII. Nothing about a document is in it. What differs per document lives in the sheet’s Config tab: visible, locked to the sheet’s owner, columns Key and Value, rows CFG, COLS and DATA, each JSON with a leading | (so Sheets never reads it as a number or formula), a long value continued on the next rows under the same key. DATA explains itself in its ABOUT entry. In public-comment mode it holds SECTIONS (each section the comments can name: key → [name shown, PDF page]), ABBREVIATIONS (short names such as HWR → a section key), PAGE_LINES ([PDF page, first line, last line]), PAGE_OFFSET (PDF page = printed page + this) and LAST_PAGE. In drafting mode it holds TOC (the dropdown: [name shown, anchor]). A Config written before 2026-10-31 used the short names K, ABBR, LP, OFFSET and MAX; the script still reads them.

# the script, once per platform version
bun run folio-assistant-core/tools/review-sheet-sync/build-review-sheet-script.ts --script Code.gs
# one document's Config rows, from the folio's repository root
bun run folio-assistant-core/tools/review-sheet-sync/build-review-sheet-script.ts \
  --repo . --config review/public-comment/sheet-sync.json --out config-rows.json
# a drafting sheet also gets its TOC tab (the Selected Sections dropdown)
bun run folio-assistant-core/tools/review-sheet-sync/build-review-sheet-script.ts \
  --repo . --config review/drafting/sheet-sync.json --out config-rows.json --toc-out toc-rows.json

The agent writes config-rows.json into the Config tab (A1 down, columns A and B, clearing rows below) with the Sheets connector, which runs as the owner, and keeps the tab protected so only the owner can edit it. CFG and COLS, which a person might edit by hand (a URL, a tab or column renamed), are indented JSON, cut into cells between lines, and column B wraps; DATA, generated from the folio and never edited by hand, stays compact (owner, 2026-10-31). The script joins a key’s cells and parses them, and JSON ignores the line breaks. Neither file is committed: both are rebuilt.

Install it, once per sheet. A person does this, from the sheet owner’s account, because Google asks the owner to authorise the script:

  1. Open the sheet, then Extensions → Apps Script.
  2. Replace everything in Code.gs with the built file, and save. Code.gs is the only file to paste: leave the project’s manifest as it is.
  3. In the function list beside Run and Debug, pick installTriggers (not onOpen, which only adds the menu), and press Run. Allow access when asked.
  4. Reload the sheet. A Review links menu appears.

installTriggers runs a full refresh, then installs two triggers: every edit of the three tabs marks the sheet dirty, and every minute a dirty sheet is rebuilt. On a public-comment sheet too slow to rebuild per edit, an edit of Review Change Sets still flags a stale proposal at once (staleNow, reading only that tab and the agent’s change-set tab; owner, 2026-10-31: “made feedback change in RefArch Log but no warning on stale”). A public-comment sheet is also rebuilt on the timer when its Agent tab changed since the last rebuild, because the agent writes Agent through the API, which fires no edit (found 2026-10-31: CS-001 read Not started on Review Change Sets after its PR was open on Agent). A drafting sheet rebuilds incrementally (owner, 2026-10-31): an edit rebuilds only the rows it touched, at once, so a pick shows its link and a new row its Change-set within seconds, however large the sheet. The timer rebuilds only the rows whose change set’s Agent row changed (the agent writes through the API, which fires no edit; the script keeps a short hash per change set to notice). A new table of contents in Config, an edit of the header row, or Refresh now rebuilds everything. A public-comment sheet rebuilds whole, since a comment feeds its change sets: at once while a rebuild takes under 5 s, otherwise gathered for the timer. Review links → Refresh now rebuilds at once.

Stale staging previews (owner, 2026-10-31, option C: sheet and page). The agent records when it built a change set’s preview in the Agent tab’s Staging built (UTC, change set), beside Agent completed (UTC, change set). When a PR of the change set was completed after the build, the script writes the Staging review cell as review ⚠ stale: built <time>, PR changed since, in both modes (Review Change Sets takes the link from the Agent tab’s Staging review page (change set) where it names one). Without a build time it claims nothing. The preview page shows its own live banner too (the site’s staging build, cat-harness-tools).

On every push, in the same pass (owner, 2026-10-31: “preview review should say stale if started but not done”): write the new PR head, set Staging deploy to building, set each comment’s status, and stamp Agent completed with the clock (date -u '+%Y-%m-%d %H:%MZ'), never an estimate. A push recorded only in prose leaves the sheet saying the old preview is current and the row is “Not started”. Then, as the restage moves (owner, 2026-10-31: “update stages of gh-pages deployment (merge to gh-pages, waiting for deploy, deployed)”): on the gh-pages push, write Staging built from and Staging built and set pushed; when the Pages run starts, deploying; when it succeeds, deployed. The sheet shows each stage in Staging review and the ⏳ line. With each stage before deployed the agent adds when it expects the preview live, from the clock and recent runs of the same site (gh run list --workflow pages-build-deployment and the build’s own duration): building, expected 2026-10-31 15:20Z. The sheet shows “expected live " after the stage (owner, 2026-10-31: "also expected time of gh-page deployment").

Writing the Agent tab with the tool (owner, 2026-10-31, option C)

The agent does not type numbers or times into the Agent tab. On 2026-10-31 two typed slips reached a sheet: Nos. 127 to 135 took in two comments of another change set, and an Agent completed time was left behind after the agent acted. The owner chose “A, and agent self-check”: a tool makes the cells, and the agent runs the sheet’s own check before writing.

  • Dispositions. Read Agent - Comments (No., Change-sets) and Review Public Comments (No., Disposition) with their header rows, and the change set’s current Disposition (change set) cell. Put them in an input file with the items (which numbers, which word, why; rest for “every other comment of the change set”), and run bun run folio-assistant-core/tools/review-sheet-sync/agent-record.ts dispositions <input.json>. The tool takes the change set’s numbers from the sheet, groups them (Nos. 127 to 131, 134, 135, 138 and 139), uses the people’s Blue word where an item names none, keeps every earlier Decided line, and runs dispositionProblems from the same review-sheet.gs the sheet runs. If anything would show a ⚠, it prints the problems, exits 1 and writes nothing: fix the input and run it again. Write its output, unchanged, to Disposition (change set).
  • On every push. agent-record.ts push --head <full sha> --expect <minutes> prints PR head, Staging deploy (building, expected <time>) and Agent completed, the times from the clock. Write all three in one update.

  • After acting on Ready for agent with no new commit (the PR already held the change), run agent-record.ts done and write the Agent completed it prints, so it is later than the Ready time and the ⏳ line moves on. Not push: nothing is restaged, so Staging deploy stays as it is.

  • The PR’s review brief. agent-record.ts brief <input.json> --look "<where to look>" prints the same Overall and per-comment lines as Markdown between <!-- review-brief --> and <!-- /review-brief -->. Put it in the PR body: the staging review page’s “What to expect in this review” pane shows only that section (cat-harness-tools#1153). Add --pcs <public-comment dashboard url> (on smart-ra, https://litlfred.github.io/smart-ra/en/folio-assistant-core/public-comments/folio/dpi-h-ra/) and every comment number links to its row there, so the reviewer can open the comment itself. The link target is the comment’s own id from the Agent - Comments “Comment ref” column (pass those rows as comments): the sheet’s No. is not the id (on DPI-H, No. 136 is PC-0137). A run such as “127 to 131” is spelled out, so no comment hides behind a range.

Drafting sheets have no comment numbers: pass "nos": [] and items without numbers are not needed; the tool then only keeps the history.

The script compares only; it stays @OnlyCurrentDoc with no internet access. Short and full shas both work: it compares the common prefix, at least 7 characters. It reads the active PR as the last one listed (one branch, one active PR per row) and writes, in this order of precedence: ⚠ deploy failed; ⚠ stale: built from <sha>, PR now at <sha> (with ; restaging: <stage> while one runs); ⚠ restaging: building the preview | on gh-pages, waiting for Pages to deploy | Pages is deploying it. A change set with a recorded PR head but no preview link shows ⚠ no preview yet: not ready for merge. A change set is never ready for merge without a preview to review (owner, 2026-10-31: “how can it be ready for merge when there is no preview?”): the agent stages a preview for every PR it opens, and the “Merge decision due” filter view leaves out rows whose Staging review starts with ⚠. Without these columns it falls back to the time check above. A sheet made before 2026-10-31 gains the three columns at the right of the Agent (change sets) tab; the script finds them by header.

Ready for agent after the preview (owner, 2026-10-31: “i just set Ready for agent to Y … i expected Staging review to get a stale warning”). The PR has not changed yet when an Editor sends a row back, so the commit check above passes. The script records, as a document property ready:<CS>, the time it first sees a row’s Ready for agent at Yes (cleared on No). A Yes it first sees on a row the agent has already completed counts from that completion instead, since the script cannot know when it was set: a freshly pasted script would otherwise flag work the agent had already done (2026-10-31, CS-001). When that time is later than Staging built, after the deploy checks, it writes ⚠ missing feedback from <time>: the preview still shows the PR, but not the feedback an Editor has just sent to the agent (owner, 2026-10-31: “requested from whom? what are we waiting on?”). The review page cannot know the sheet, so only the sheet says so. The same time makes Agentic status open with **Waiting on the agent since (Ready for agent set)**, until the agent records a later completion or sets the status to Working.

Stale agent proposals. Feedback (agent) (drafting) and Change Set Feedback (agent) (Review Change Sets) carry the agent’s proposal. The agent records what it wrote against in the Agent tab’s Feedback basis (change set): feedbackBasis() in tools/review-sheet-sync/feedback-issue.ts, a hash of the row’s blue cells (drafting: Title, Selected Sections, people’s Contributor Feedback; public comment: Title, TWG (CS), people’s Committee Feedback). The script computes the same hash; while they differ it puts “⚠ Stale: the row changed since this proposal; the agent will propose again.” on the proposal’s first line, and takes it off if the row changes back. The agent’s next sync replaces the proposal and the basis.

Where the change set is (owner, 2026-10-31: “agent feedback should also try to say where it is in producing PR / staging”). Below any stale mark, the script keeps one line starting with ⏳ at the top of the agent’s proposal (progressLine, withProgress), and replaces it on every refresh: “Ready for merge set: the agent will merge dth-hrh#7.”; “Ready for agent set <time>: the agent will act on this and rewrite it.”; “The agent is working on dth-hrh#7.”; or “dth-hrh#7 open; no preview yet | preview current (built <time>) | preview missing feedback from <time>.” No pull request, a merged one, or an empty proposal gets no line. The agent never writes this line and drops it when it rewrites the proposal; the next refresh (within a minute) puts it back. The line is bold, and an open PR’s line carries the agent’s last completion time (“smart-ra#185 open, updated 2026-10-31 14:41Z; preview stale: built from 420acd3, PR now at e7b4094.”). The agent writes no status line of its own (“Status (agent, …)”): it records the facts in the Agent tab (PR head, Staging deploy, Agent completed from date -u) and the sheet says them (owner, 2026-10-31: “lost time, not bold”). An Editor’s Orange change (a Ready column) is not part of the basis, so it never marks the proposal stale: it shows here as a note, and Ready stays as the Editor set it (owner’s card, option A). The note appears at once: an edit of a Ready for agent cell records its time (noteReady_) and, on a slow public-comment sheet, staleNow writes that row’s line without waiting for the timer (owner, 2026-10-31: “i expected to see change to Change Set Feedback (agent) b/c i said ready for agent”).

How to tell it works. The first run of installTriggers takes about 20 seconds for 800 rows and its execution log ends “Execution completed” (a one-second run means onOpen was picked). Then No. is a blue link, and hovering a No. n on Review Change Sets shows a row such as A327. Failed runs are listed with their error under Executions (the clock icon) in the Apps Script editor. An agent checks from outside by reading a No. cell’s formula (=HYPERLINK(…)) and a joined cell’s text-format runs.

Protected columns. The script runs as the account that installed it, so it writes the grey and green columns even when they are protected, as long as that account is an editor of the protected ranges. Install it from the owner’s account.

Test it without a sheet. bun test folio-assistant-core/tools/review-sheet-sync/review-sheet.test.ts builds the script for a small fake folio and runs it against a fake of the Apps Script services over the three tabs. Rewrite the Config tab when the review anchors change, the draft link moves, or a tab or a header the script reads is renamed. Re-paste Code.gs only when the script itself changes. Renaming a header the script reads, without rewriting Config, leaves that column unlinked; it fails nothing.

Ready for agent: Yes, No, Completed (owner, 2026-10-31)

“preview is now live, so nothing more for agent to do. so no longer ready for agent … like Yes, No, Completed”. The script sets Ready for agent from Yes to Completed once the agent’s last push is later than the time Yes was set and the preview of it is live and current (no ⚠ in Staging review). An Editor sets Yes again to send the row back to the agent. A row that turns stale goes back to No from Yes or Completed, as before. The agent never writes the Orange columns.

Every pass ends with a finish stamp after the Ready time (owner, 2026-10-31: “make sure process works … so it doesnt fail again”). On DTH-HRH CS-001 the agent pushed at 12:49Z, Ready for agent was set (again) at 12:57Z, and no agent ran after that: the row read “the agent will act on this” for seven hours and never reached Completed. So:

  • The agent ends EVERY pass with a stamp from the tool: push --head <sha> when it committed, else done, which writes Agent completed and the step idle together. A proposal that waits for the Editor ends with step proposed. The script counts a later idle or proposed step as the end of the pass, the same as Agent completed.
  • Before stopping, the agent re-reads Ready for agent: if it was set after the pass began, the pass is not over; act on it (or done if there is nothing new).
  • A Ready for agent with no step recorded after it for 20 minutes shows “⚠ no agent has picked this up for N min: ask in the project chat” on the ⏳ line and in Agentic status, so a row with no agent never looks like quiet work.
  • Every log needs a watcher: the setup is not complete until an agent thread is watching the sheet. The QA gate, before Ready for merge (owner, 2026-10-31)

“agent should make sure all dispositions are consistent with human and feature branch changes. add review (agent-independent) before ready for merge”, then “QA gate. also sheets should link to QA reports for the staging”.

Who. A reviewer that did not write the change: another agent session, or a person. The authoring agent never gates its own pull request; one party doing both halves is not this check.

What it checks, against the PR’s head commit:

  1. every comment (drafting: every feedback item) of the change set has one disposition (the script’s dispositionProblems already flags gaps);
  2. each disposition agrees with the people’s Blue Disposition, where one is set;
  3. each Accepted or Partially accepted item has its change in the PR’s diff, and the change does what the line says;
  4. a Not accepted, Noted, Deferred, Duplicate or Out of scope item has no change in the diff that contradicts it;
  5. the diff changes nothing that no disposition accounts for;
  6. the staging QA report for that commit has no failing gate.

What it writes, on the Agent tab’s change-set row and nowhere else:

  • QA gate (change set): first line Passed <head sha>: <one line> or Failed <head sha>: <the first problem>, then one line per problem;
  • QA report (change set): the link to the QA report for the staged commit: the tree pr/<n>/<sha> on the folio’s QA reports branch (in smart-ra, cat/cat-harness/qa-reports; check the branch name, it varies).

What the sheet shows. Staging review reads review · QA report (both links), then the gate: ✓ QA gate passed (b20534f), or in bold ⚠ QA gate: no independent review yet: not ready for merge, ⚠ QA gate failed: <why>, or ⚠ QA gate stale: reviewed 1234567, PR now at b20534f: not ready for merge once the PR moves on (qaGate). If Ready for merge is set before the gate passes, the agent’s ⏳ line says it will not merge until it does, and the agent does not merge. A failed gate sends the change set back to the author, who updates the PR and its dispositions; the gate then runs again on the new head.

Linking a sheet to a repository

A copied sheet knows nothing about its document until the agent links it (owner, 2026-10-31: DTH-PC’s copy opened with an empty Config and an empty dropdown, and nothing said why). Linking is repository work first and sheet work second, in this order:

  1. The folio has a section list. A drafting sheet’s dropdown is the document’s chapters and sections, read from folio/<doc>/review-anchors.json. The folio’s package.json declares review:anchors and check:review-anchors, both running folio-assistant-core/scripts/review-anchors-from-folio.ts --document <doc>. A document seeded from a library file adds `–library --source --source-label `; one authored from scratch (dth-pc, dth-sc) leaves all three out. Run `review:anchors` and commit the file. A new document folio declares both scripts from its first commit, so no sheet ever waits on them.
  2. The folio names the sheet. review/<mode>/sheet-sync.json: {"mode":"drafting","anchors":"folio/<doc>/review-anchors.json","sectionUrl":"en/<doc>/#","sheet":"<spreadsheet id>"}.
  3. The agent writes the sheet. From the folio’s root: bun run folio-assistant-core/tools/review-sheet-sync/build-review-sheet-script.ts --config review/<mode>/sheet-sync.json --out config-rows.json --toc-out toc-rows.json, then, with the Sheets connector, the CFG, COLS and DATA rows into Config below EDITORS (keep the sheet’s EDITORS value), and for drafting the TOC rows into the TOC tab from A1. The connector writes values, not colours, so the agent also colours Config: the Key row a Grey header (#b7b7b7, bold), EDITORS Orange (#f4b26b), and CFG, COLS, DATA and their continuation rows Grey (#efefef), and fits the Instructions rows’ heights to their text (a Sheets API autoResizeDimensions; an inserted row otherwise inherits its neighbour’s height). Every refresh re-applies these (styleConfig), so a sheet the script runs in heals on its own. The TOC rows are exactly what the script’s refresh writes, so the dropdown works before anyone pastes the script.
  4. The agent says what is left for a person: paste Code.gs and run installTriggers (step 5 above), and tick Allow multiple selections (step 6).

When the branch carrying the folio is not merged yet, the agent may run steps 1 and 3 from that branch without pushing to it, and write the sheet; the branch’s owner commits the anchors and sheet-sync.json. Re-run step 3 after any structural change to the document (a section added, moved or renamed).

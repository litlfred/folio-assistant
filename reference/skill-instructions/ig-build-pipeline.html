ig-build-pipeline

Skill id: ig-build-pipeline · Package: fhir-ig-base · Instance: fhir-harness

The base: run the FHIR IG Publisher over an IG, with no pre-processing and no post-processing, and publish the result. This is how WHO SMART Guidelines were built before DAK pre/post processing was added, so it is a shape that demonstrably worked rather than a design being invented here.

It serves any FHIR IG. That is the whole point of the layer, and it is a constraint rather than an aspiration — see §”What this layer refuses to know”.

The pipeline 

input/fsh/          →  SUSHI      →  fsh-generated/resources/
input/pagecontent/  ┐
sushi-config.yaml   ┘  →  IG Publisher (JVM, Docker)  →  output/
                                                        →  publish to a pages branch

Four stages, and the only one that is not a straight invocation is the last: a pages branch is a deployment target, and which one is the instance’s to declare.

SUSHI and the Publisher both need packages.fhir.org. Where it is refused, see fhir-validation §”When a package host refuses you” before concluding either cannot run.

Version numbering: SEMVER for a FHIR IG

Owner, 2026-10-30 (litlfred/folio-assistant#222, bean l1nl): define the SEMVER rule for IG versions — what bumps major, minor and patch.

An IG’s version is declared in sushi-config.yaml version (and mirrored in publication-request.json version when cutting a release). It is always an exact MAJOR.MINOR.PATCH semantic version triple (versionIncrement: "major" | "minor" | "patch" in ig-publication; directory-conventions §”Pinning a reference”), never a range or floating tag. Which segment bumps is determined by the delta on the IG’s published conformance and canonical surface since the previous release — measured over the AST with `ig-ast.ts diff

Do not restate the list here — two copies of an emission list is two copies free to drift, and the emission list is exactly the thing a new Publisher release changes. ## What the site build emits: thin pages, by default Since 2026-10-12 (owner: *"make thin default"*) the Jekyll phase emits THIN pages: each artefact page and the IG's `artifacts.html` and `toc.html` are a few KB that load their content from JSON-LD nodes (`artifact/-.jsonld` and `artifact/index.jsonld`). Each artefact's tab views (definitions, mappings, JSON and examples) are thin pages beside it, drawn from the resource's JSON (owner, 2026-10-14: *"3. Render them too"*). The IG's narrative pages keep their prose with every piece of chrome linked rather than inlined. The old full pages stay reachable with `--full-pages` on both `gen-ig-pages.ts` and `stage-ig-sites.ts`. An IG that pins this layer by SHA changes nothing until it re-pins, and gets the thin pages when it does. What each page holds, and the QA over the nodes, is [`ig-render-jekyll`](../../reference/skill-instructions/ig-render-jekyll.html) §"Thin pages, the default". ## The AST cache lifecycle: an IG site is built from the AST Owner, 2026-10-14: *"i want AST to be used. it should be in cache branch. update processes/skills"*, and *"that should be in fhir-harness then smart-* all use that"*. The process is [`ig-ast-cache.bpmn`](../../en/cat-harness/processes/ig-ast-cache.html). Terms: - **AST**: the per-resource dump the IG Publisher AST exporter writes (`output-ast/`; formats in [`ig-ast-delta`](../../reference/skill-instructions/ig-ast-delta.html)). - **Cache branch**: `cat/fhir-harness/fhir-ast/` on the IG's own repository, one orphan commit holding the AST, the Publisher's `expansions.json` and its `txcache/`. `` is `sushi-config.yaml`'s `id`. - **Valid**: `ig-ast.ts validity` says the AST was built from the inputs the commit being published has (Publisher version, `sushi-config.yaml`, `ig.ini`, `input/`). **The rule.** 1. **An IG repository's site is built from the AST on its cache branch.** The site is never built from the Publisher's HTML, and the publish runs no Publisher. Its first step restores the cache and judges it: `ig-site:ast` (`ig-repo-site.ts ast`), which runs `ig-cache.sh restore --ig-root .` and then `validity`, as `ig-cache.sh verify` does. See §"The IG repository's site route" for the steps that follow it. 2. **The publish refuses an AST that is not valid**: `stale-inputs`, `cannot-tell`, or no cache at all. It does not fall back to a Publisher build or to the Publisher's HTML. `ig-site:ast` accepts a stale AST with `SITE_ACCEPT_STALE_AST=1` for a preview only; on the root it still refuses. 3. **A commit that changes no input does not make the AST stale.** If the recorded commit is an ancestor of HEAD and the input digest is unchanged, the AST is still valid (`sameSourceAs` in `ig-ast.ts`), so a README or workflow merge needs no rebuild. A checkout that cannot see the recorded commit (a shallow clone) reads as stale. It never reads as valid. 4. **Only a Publisher run refreshes the cache, and it runs on a GitHub runner.** It needs Java, a 10 GB heap and `tx.fhir.org`, which an agent's container lacks. Whenever the IG's source changes, someone has to run it. **Who writes the cache: one workflow, here.** [`.github/workflows/ig-ast-refresh.yml`](https://github.com/litlfred/folio-assistant/blob/main/fhir-harness/.github/workflows/ig-ast-refresh.yml) (`workflow_call`) is the only writer. The IG repository's `site-publish.yml` (the [template](https://github.com/litlfred/folio-assistant/blob/main/fhir-harness/templates/ig-repo-site/site-publish.yml)) calls it as its first job, `ast`, so a publish refreshes the cache before it builds: a no-op when the cache is valid for the commit. No IG repository carries a workflow of its own for it (owner, 2026-10-14, paraphrased: all of this should be part of fhir-harness, reached through the IG overlay above it). A repository whose owner wants the cache refreshed on every push to its IG sources may add the optional caller [`templates/ig-repo-site/ig-ast-refresh.yml`](https://github.com/litlfred/folio-assistant/blob/main/fhir-harness/templates/ig-repo-site/ig-ast-refresh.yml). One run: 1. mounts the layers the IG repository's `index.lock.json` pins; 2. restores and judges the cache for `ref` (default `main`); 3. if the cache is not valid, or `force` is set, runs the caller's `pre-export` command when it gives one, then builds the IG with `AstExportCli` (Tool `ig-ast-export`, pinned `ast-export-ref`); 4. puts back what `pre-export` changed in the inputs, and checks that the new AST is valid for its own commit; 5. seeds the cache with `ig-cache.sh seed --push`, only when the commit is on the default branch with the tip's inputs. Otherwise the AST is uploaded as a run artefact, `output-ast`. **A stale cache is rebuilt incrementally; a release is cut from a full build** (phase P4, bean `h3tx`; owner, 2026-10-24, option C). Step 3 does not always run a full Publisher build: - When the cache is **stale**, the run is not `force`, and the caller gives no `pre-export`, it runs `IncrementalBuildCli` over the restored cache. That rebuilds only the cone of what changed and merges it over the cache (skill [`ig-publisher-fork`](../../reference/skill-instructions/ig-publisher-fork.html)). Its own plan falls back to a full build when it cannot tell, and a failure, or a merged AST that is not valid, falls back to `AstExportCli`. - A cache that is **missing** or **cannot-tell**, a **`force`** run, and a caller with a **`pre-export`** always build in full. A `pre-export` changes the work tree, which the incremental build refuses. - The run's `kind` output, and `ig-ast.ts build-kind output-ast`, say which kind of build it was: `full`, or `incremental` (the manifest is `mixed`, with an `incremental` lineage). - **A release is cut from a full build only.** Any step that cuts a release runs `ig-ast.ts build-kind output-ast --require-full`, which exits 1 on an incremental AST. To get a full AST, run the refresh with `force`. - **The site says which kind of build it came from.** `folio-build.json` carries `ast.kind` beside `ast.verdict` (`ig-repo-site.ts`, the `publisher-pages` step). **A preview is built from its own branch's AST.** The template's `ast` job passes `ref: github.ref_name`, and when that run rebuilt without seeding, the `publish` job downloads the run's `output-ast` before `ig-site:ast` runs, which keeps an AST already in the checkout when it is valid for the commit. So a branch that changes the IG's inputs gets a preview of its own content, and the shared cache stays the default branch's. Pinned to the default branch, as the template was until 2026-10-24, every such branch was refused as stale: a review committee could never see a content change on STAGING (the folio-assistant#215 walk on smart-immunizations-uganda#12). Overriding with `SITE_ACCEPT_STALE_AST=1` is no substitute: it mixes the branch's narrative with the default branch's artefacts. That is why `folio-build.json` names the AST it used (`ast.commit`, `ast.verdict`) beside `source`. Seeding is refused below 90% of the incumbent's resources or edges (the no-shrink gate in `compiled-artefact-cache`). The run builds no site, writes no gh-pages and dispatches nothing. The Tool node is `ig-ast-refresh`. **An overlay's preparation: `pre-export`.** Some IGs prepare their inputs before the Publisher runs: an overlay registers pages in `sushi-config.yaml` or generates resources from other sources. The plain exporter does not do this, so the caller passes the command as the optional `pre-export` input, written in its own workflow file. This layer runs it with `bash` at the IG root and knows nothing about what it does: the overlay names its own steps, and this skill does not list them. The exporter records the digest of the tree it is given, and a prepared tree is one no clean checkout has. So the run takes the source's digest (`ig-ast.ts digest`) before the command runs. After the export it puts the inputs back, checks the digest again, and writes the source's digest into the manifest's `inputs` with `ig-ast.ts source-inputs`. The prepared tree's digest and the command are kept under `preExport`. The cache then verifies on any clean checkout, the way an AST built without `pre-export` does. A failing `pre-export` fails the run, so nothing is seeded. **When it runs.** The run is dispatched by a person, or by an agent the owner named for that run. An agent never dispatches it on its own (`feature-staging` §"Agent-run repositories"). Adding a `push` trigger on the default branch, filtered to `sushi-config.yaml`, `ig.ini` and `input/**`, is the owner's decision for each repository. **Measured 2026-10-14**, cache branch against `main`. Restoring, judging, building and seeding are here. ## What this layer reads: `contentTypes.ig.include` Owner, 2026-10-30: *"a harness can point to a repo, but doesnt want to automatically slurpo up all content in a repo. harness desclares what it it pays attention to in the repo."* So an IG repository says which of its paths this layer reads, in its root `index.config.json`, and nothing else is read: ```json "contentTypes": { "ig": { "include": ["sushi-config.yaml", "ig.ini", "input/fsh/", "input/pagecontent/"] } } ``` The section is the `ig` content type (`schemas/ig-content-type.ts`). An entry ending in `/` is a directory and covers everything under it; any other entry is one file. Paths are repository-relative and POSIX: absolute paths, `..`, `.`, backslashes and empty segments are refused. `sushi-config.yaml` is still SUSHI's file and is no longer the marker: a repository is an IG source because it declares the section. **Every IG reader here honours it.** Each one asks `scripts/ig-read-scope.ts` (`igReadScope(root)`) before it touches a path: `build-ig-indexes`, `ig-repo-site`, `build-ig-site`, `fsh-cone`, `ingest-ig-menu`, `ingest-ig-chrome`, `ig-api-hub`, `ig-site-data`, `ig-review-data` and `measure-logic-layer-edges`. An undeclared optional directory (`input/images/`, say) reads as absent; an undeclared file a reader cannot work without (`sushi-config.yaml`) is refused with the path named. `ig-repo-site compose` and `stageIgSite` stage from a copy of the declared paths only. Two things are not gated: `index.config.json` itself, and the input digest in `ig-ast.ts`, which must equal the Java exporter's and names what SUSHI and the Publisher read. The list bounds the harness, not those tools. **A repository that declares no section** is a legacy IG. It is read as before, every path, and each run prints one warning per repository: ```text warning: declares no contentTypes.ig in its index.config.json, so fhir-harness reads it as a legacy IG (every path). Declare "contentTypes": { "ig": { "include": [...] } } there, listing the paths the harness reads (see fhir-harness schemas/ig-content-type.ts). ``` When you see it, declare the section; do not silence the warning. A section that is there but has no `include`, an empty one, or a bad entry is refused outright: a section that declares nothing is never read as "everything". **Adding a path.** When a page, a diagram or a data file is missing from the site and the IG declares the section, check `include` before the reader. Add the path to `contentTypes.ig.include` in the IG's own `index.config.json` (a directory with a trailing `/`), in the same pull request as the content that needs it, and say in the description which reader needed it. Add the narrowest path that covers it, never `""` or the repository root. The WHO SMART Base IG's list is a worked example: it added `input/diagrams/`, `input/archimate/`, `input/dmn/` and `input/ignoreWarnings.txt` when its site stopped showing them. ## The IG repository's site route: the layers supply the steps Owner, 2026-10-14, on an IG repository that lost its OpenAPI pages, its DAK API sidecars and its artefact index when it dropped its own declaration (paraphrased): those steps should already be supplied by the layers, the DAK API by the IG overlay above this one and the OpenAPI pages by the harness. That was not the expected answer — the phase sits inside a workflow whose other two phases are gated on `do_dak`, so the obvious reading is that it is WHO's too. It is not, and this is the strongest single piece of evidence for `nsbb`'s claim that **the base is the real pipeline and DAK is an overlay on it**: the overlay does not reach the deployment end at all. **One step places outside the stack, and that is not a failure.** Commenting on a pull request is forge plumbing, which `cat-harness` already owns — it is not an IG concern in any layer. The falsification test asks whether a step can be placed, not whether it lands in one of the five; a step with a home elsewhere in the harness is placed. ## Who starts a build: two owner questions before a repository publishes on its own Owner, 2026-10-06: *"make this part of the process/skill. if gh-pages is being populated, ask use if disable. ask use if they want justthedocs rendering (default is yes)"*. Bean `p3yl`. **This section owns the rule.** Every other skill that adopts, onboards or converts an IG repository points here rather than restating it. **When it applies:** whenever an agent adopts an IG repository ([`fhir-ig-create`](../../reference/skill-instructions/fhir-ig-create.html) `existing-ig` or `new-repo`, or [`repo-conversion`](../../reference/skill-instructions/repo-conversion.html) over a repository with a `sushi-config.yaml` or `ig.ini`), **and** whenever it notices automatic builds in an IG repository it is already working in. A repository forked from an upstream IG usually arrives with the upstream's build workflows, and those publish on every push and every pull request whether or not the fork's owner wants that. Why ask rather than leave them: the measured case (2026-10-06, three IG forks) had IG Publisher workflows writing a `branches//` preview to `gh-pages` on every push and every PR, which the owner did not want, and one fork's PR preview was deploying to **another organisation's** Pages site. Nothing in the repository said so; it was found by reading the triggers. ### 1. Detect, read-only List every workflow under `.github/workflows/` whose `on:` includes `push`, `pull_request`, `pull_request_target` or `schedule` **and** that builds or deploys a site: it runs the IG Publisher, pushes to `gh-pages` (or another pages branch), or uses a Pages deploy action. For each, record: | field | what | |---|---| | file | the workflow path | | automatic triggers | which of the four, with their branch filters | | what it publishes | full build, branch preview (`branches//`), PR preview | | where it publishes | the repository's own Pages site, or a target **outside** it (another repository's pages branch, another organisation's `github.io`) | | called by others | whether it declares `workflow_call`, and whether another repository calls it | **A deploy target outside the repository's own Pages site is a finding in its own right**, reported even if the owner keeps every trigger: the repository is writing to a site it does not own. If nothing matches, say so in one line and skip to step 3. ### 2. Ask whether to disable the automatic triggers Put it per [`interaction-modality`](../../reference/skill-instructions/interaction-modality.html): the detection table first, so the owner can answer without opening anything, then this question: > This repository publishes to gh-pages automatically: *(the table from step 1)*. > Should those builds keep running on their own? > > 1. **Manual only** *(recommended)*. I change each listed trigger to > `workflow_dispatch`, so a build runs only when someone starts it from > the Actions tab. I keep `workflow_call` wherever another repository calls > the workflow, and I leave what is already on gh-pages untouched. > 2. **Manual only, and remove the workflows nobody calls.** As 1, but a > workflow with no caller and no remaining use is deleted from > `.github/workflows/` rather than kept as a manual one. > 3. **Keep them as they are.** Nothing changes; I record the finding > (and any out-of-repository target) in the work plan. > 4. **Tell me more.** > > **Default if you do not answer: 1.** The default is 1, manual only, by the owner's ruling of 2026-10-06: *"i dont want github tools implemented, only defined."* A build workflow is kept **defined**, so it can be started from the Actions tab, but it does not run on its own. Disabling a trigger is reversible, and an IG fork's owner has, so far, never wanted every push published. Option 3 stays available to an owner who says so; it is no longer what silence means. Rules that hold whichever option is chosen: - **Turning a repository's automatic BUILDS off never turns its harness CHECKS off.** The question is about the IG Publisher and gh-pages workflows. The harness checks are a separate workflow: a caller of cat-harness-tools' `layer-pr-checks.yml` on `pull_request`, described in the cat-harness skill [`index-config`](../../reference/skill-instructions/index-config.html) ("A harnessed repository runs its checks on its own pull requests"). It stays on whatever the answer is. On 2026-10-06 the answer "manual only" was applied to every workflow in the WHO SMART Base IG, the WHO SMART Trust IG and the WHO SMART Immunizations IG, so their harness gates went off together with their builds, and nothing judged those repositories until an index re-pinned them (owner, 2026-10-14: "There should be CI running"). - **Never delete gh-pages content as part of this.** The previews already published stay. Removing them is a separate question, asked separately, with what would go and how big it is, per [`deletion-requires-confirmation`](../../reference/skill-instructions/deletion-requires-confirmation.html). Option 2 deletes a workflow file, which `git revert` restores; it does not delete anything the workflow published. - **Keep `workflow_call`.** A workflow another repository calls is an API; dropping the trigger breaks the caller, and the caller's owner is not in this conversation. - **An out-of-repository deploy target is never "kept" silently.** If the owner chooses 3, the finding still goes in the work plan. ### 3. Ask whether to render the IG with the just-the-docs site > Do you want this IG rendered as a just-the-docs site, with the harness's > navigation, search and language bar, on this repository's own Pages site? > > 1. **Yes** *(recommended)*. I install the folio site workflow, manual > trigger only, and tell you how to run it. > 2. **No.** The IG Publisher output stays the only rendering. > 3. **Tell me more.** > > **Default if you do not answer: 1.** The default is yes because this is the rendering the owner wants ([`ig-render-jekyll`](../../reference/skill-instructions/ig-render-jekyll.html) says why: the Publisher's finished HTML is opaque to every harness surface), and installing a manual-only workflow publishes nothing until somebody runs it. On yes: 1. **The repository needs no harness of its own.** No `.json` declaration and no `folio-assistant/` submodule. Its `index.config.json` names the layer it builds on as a remote instance, with consent: this layer for a bare IG, or the overlay above it (the WHO SMART Base IG, for an IG that wants the DAK surface). `remote-mount.ts --seed` writes the entry and `remote-mount.ts` the `index.lock.json`; the layer's closure comes with it. The owner's ruling, 2026-10-14 (paraphrased): the IG repository can just define `index.config.json` and reference the overlay layer as a dependency, and that is the preferred and expected behaviour. `index.config.json` also says which mounted layer's chrome the site wears: `"site": {"landing": ""}` (the WHO SMART Base IG for a WHO SMART IG). Without it the route refuses rather than guess among the mounted layers. It also declares `contentTypes.ig` with its `include` list (§"What this layer reads"); without it every reader warns and reads the whole repository. 2. Keep one workflow that calls the overlay's IG build (`ghbuild.yml` or `fhirbuild.yml` of the layer the IG builds on): it is the recipe the publish mirrors, and it stays `workflow_dispatch` only. 3. Add `.github/workflows/site-publish.yml` from [`templates/ig-repo-site/site-publish.yml`](https://github.com/litlfred/folio-assistant/blob/main/fhir-harness/templates/ig-repo-site/site-publish.yml), `workflow_dispatch` only. It mounts the locked layers and runs `bun run cat-harness-tools/scripts/stage-local.ts --repo .`, the same command every agent-run repository publishes with: it builds the site from the IG's cached AST, with the steps the mounted layers provide (§"The IG repository's site route"), and publishes `main` at the root (keeping `STAGING/`, `_render-log/` and `branches/`) and any other branch as a preview under `STAGING//`. `--plan` prints what it would do and `--dry-run` builds without publishing. `--bare-ig`, which publishes the Publisher's own output, is not how an IG site is built under the 2026-10-14 rule, and neither is a Publisher run by the route: it runs none. The route's steps come from the mounted layers (§"The IG repository's site route"); an IG that needs steps of its own beyond them declares `site.build` inline in its `index.config.json` entry, never in a `.config.json` (bean `ymvt`, owner 2026-10-14: *"i thought ONLY index.config.json"*). The menu is read from `sushi-config.yaml` at build time: nothing is committed for it. The old per-repository `folio-site.yml` needed the `folio-assistant/` submodule, which the layer split (bean `n3h9`) removed; the template above replaces it. The site is built from the IG's AST on its cache branch, never from the Publisher's HTML: the route's first step is `ig-site:ast`, the restore and its judgement (§"The AST cache lifecycle"). 3a. Nothing more for the AST: the template's first job, `ast`, calls this layer's reusable `ig-ast-refresh.yml`, which runs the Publisher on a runner and seeds the cache branch when it is missing or stale for the commit. 4. Tell the owner how to run it: **Actions tab → "Site publish (by hand)" → Run workflow**, on the branch to publish, with `plan` ticked first. The site lands at the repository's own Pages URL, since the template reads the base path from the repository name rather than assuming it. 5. If the IG has sibling sites (other IGs on the same platform) or depends on another IG with its own site, set the two repository **variables** the template reads, so no copy is edited per repository: `FOLIO_SITE_SIBLINGS` (site URLs) and `FOLIO_SITE_DEPENDENCIES` (`owner/repo@ref`). The run then reports each sibling built with a different platform, and re-runs the dependencies' `Site publish (by hand)` after a publish. The re-run needs a `FOLIO_SITE_DISPATCH_TOKEN` secret. Without it the run summary says what was not rebuilt, and nothing fails. Why: built by hand, the sites drift. Each one shows the harness chrome of the platform it was last built with, and in bean `48a6` the owner found that by looking. Every build writes `folio-build.json` at its site root (`scripts/site-build-stamp.ts`), so a deployed site can be compared without rebuilding it. A sibling whose stamp cannot be read is reported as **not checked**, never as matching. The report is a message, not a gate, and the dependency rebuild is the owner's interim step (2026-10-09: *"1, but rebuild dependency for now"*). ### 4. Say what the pull request will fire A pull request that changes a workflow **still runs the base branch's `pull_request_target` workflows**, because `pull_request_target` runs the workflow file from the base, not the one in the PR. So the PR that disables an automatic preview fires that preview one last time, and on the measured fork that meant a deploy to another organisation's site. Say so before opening the PR, and offer the two ways round it: cancel those runs as soon as they start (`gh run cancel `), or, with the owner's agreement, push the workflow change straight to the working branch rather than through a PR. Once the change is on the base branch, later PRs are quiet. ### Process diagram No BPMN activity covers IG repository adoption yet, so these steps are not in a diagram.

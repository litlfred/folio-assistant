Description

folio-reference/v1: one bibliographic reference, as a KG node (bean folio-assistant-63q4).

Why a node

Every \cite{key} already becomes cito:cites → references/<key> (cat-harness resolveReferenceKey), and until now nothing was ever written at that IRI: every citation in the KG dangled. A reference node is what is there. It is also what a bibliography viewer lists and exports, path by path, the way the glossary lists terms.

The body is CSL-JSON, and the node reads as Dublin Core

Owner, 2026-10-14, on aligning qou's bibliography: "1 + 2". Keep CSL-JSON as the source (qou's 915 entries, and the LaTeX/BibTeX pipeline built on them), one entry per node. CSL-JSON is the citation format: it carries the volume, issue, page and series that mathematics needs and that Dublin Core has no fields for. Dublin Core is how the node READS: referenceToJsonLd maps the CSL fields to dcterms: and bibo: predicates, so every reference, from whatever source, is also a DC description.

Where a reference comes from

One node type for every source, said by ReferenceProvenance: - authored: a folio's own bibliography entry (qou's references.ts, then its per-entry files); - catalogue: projected from a catalogue's Dublin Core record (dublinCoreToReference), e.g. an item of the IRIS catalogue layer; - library: a library asset's own manifest; - extracted: one entry of a paper's reference list, split out of its references section.

Core's, by core's rule: a reference describes what a folio HOLDS or CITES and where it CAME FROM. Not the harness's.

Exports: toCslJson, toBibtex, toRis, toJsonLdGraph.

Its fields are CSL-JSON's (no external-schema record names CSL-JSON yet). The tag reader takes ONE spec id per line, so each is its own tag: the comma-separated form declared none of them.

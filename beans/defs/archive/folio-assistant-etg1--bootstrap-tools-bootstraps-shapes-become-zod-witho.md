## Measured, from the #603 viewer

The schema projection is 113 modules across FOUR instances. `bootstrap`
contributes ZERO:

    cat-harness            101
    folio-assistant-core     9
    large-datasets           2
    detangle                 1
    bootstrap            0

Two independent causes. `bootstrap/harness.json` declares `skills/`,
`workflows/`, `render/` and no `schemas` graph, so the reader never looks. And
the two schemas it holds — `discussion.input.schema.json`,
`discussion.output.schema.json` — are hand-written JSON Schema draft-07, which
`schema-management` documents as the edge-erasing form.

## Why the obvious fix is WRONG, and this is the whole point

Converting them in place puts a file in bootstrap that must be RUN to yield a
shape. Bootstrap's own README forbids it:

| An Initiator has **no** harness, no server, no tools and no work plan. If a
| step seems to need one, you are reading instructions meant for later.
| It is a file you read, not something you run.

Measured: `bootstrap` holds 8 .md, 6 .json, 3 .bpmn and ZERO .ts. That is
the design, not an omission.

## The shape, owner 2026-09-20

| note, though. that the zod schema should by one special exemption not be
| bootstrap, but bootstrap-tools

and, sharpening it:

| bootstrap should not know zod at all (it is just generated by it in main and
| ghpages rendering pipeline)

So: NO import, NO dependency, NO package.json entry, NO build step of its own.
Generation is a PIPELINE concern running in main and gh-pages rendering, from
`bootstrap-tools/schemas/*.ts`. Bootstrap is where the output LANDS. Read from
inside `bootstrap/`, the two .json files are just files, as today.

## Done when

- `bootstrap-tools/` exists as a SIBLING top-level instance (never nested under
  bootstrap — that would put .ts inside the tree an Initiator is told has
  no tools), declaring a `schemas` graph.
- The two schemas are Zod .ts there, and appear in the schema viewer.
- The .json in bootstrap is generated by the pipeline, with the `$id`s
  UNCHANGED — they are a published contract, and the filenames are referenced
  from discussion.bpmn, cat-harness/tools/index.ts, the generated skill docs,
  and .pot catalogues in FIVE languages.
- A `--check` twin ships in the gate set. Non-negotiable per
  `schema-management`: three schema generators rotted here before, because
  nothing asked whether their output still matched their input.
- `hfkl`'s exemption reasoning is restated, since this changes it.

## Summary of Changes

`bootstrap-tools/` exists as a sibling top-level instance, declaring a
`schemas` graph, with `schemas/discussion.ts` as the authoritative Zod.
`cat-harness/scripts/gen-bootstrap-schemas.ts` generates
`bootstrap/skills/discussion.*.schema.json` from it, `$id`s unchanged, and
`bootstrap-tools:schemas:check` is in the gate set.

**Bootstrap is untouched apart from the two generated files.** It carries no
import, no dependency and no build step; read from inside `bootstrap/`
those files are exactly what they were.

### The finding that shaped it

`zodToJsonSchema` drops `.refine()` entirely — measured: no `allOf`, no
`if`/`then`, no message. The output document's two conditionals
(`assumed` requires `assumption`, `unsettled` requires `stillOpen`) would have
vanished, so the published schema would have started ACCEPTING what it
currently REJECTS, at an `$id` consumers follow. The generator re-applies them
from `JSON_SCHEMA_CONDITIONALS`, and `discussion.test.ts` proves it with a
corpus of documents that MUST fail — falsified by deleting `allOf`, which
turns 5 tests red.

A second, quieter change was caught and reverted: `z.object()` is strict, so
the exporter added `additionalProperties: false` everywhere, TIGHTENING the
contract. Stripped, and the question of whether to adopt it deliberately is
bean `z634`.

### Measured result

    before: 113 modules, bootstrap contributing 0
    after:  115 modules, bootstrap-tools contributing 11 declarations
            and a relationship diagram at
            /cat-harness/schemas/bootstrap-tools/

The shape was written as a literal `z.object({...})` rather than a shared
shape constant on purpose: a bare object literal is `undetermined` to a
syntactic reader (as `themePaletteShape` and `kgNodeLabelShape` are), and
hiding the biggest shape behind a variable would have defeated the reason this
instance exists.

Also required a repository-scoped duplicate in `cat-harness/harness.json`,
the same one `detangle`, `kg-navigation` and `large-datasets` carry: a
directory declared only in an instance that is not a DEPENDENCY is invisible
from this root.

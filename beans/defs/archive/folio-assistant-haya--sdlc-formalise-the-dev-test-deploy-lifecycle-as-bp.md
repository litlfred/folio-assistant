From [#363](https://github.com/litlfred/folio-assistant/issues/363): "need better
documentation on deve, testing and deployment lifecycle to fit in with the
software development lifecycle (SDLC - it needs to be formal formal, subprocess
includes developing MVP etc, align/cleanup exisrting documentation)."

## What exists, measured 2026-09-19

`processes/` holds 31 BPMN files. Of those, the ones that touch this
lifecycle are `content-lifecycle.bpmn`, `draft-to-publication.bpmn`,
`editing-hci-validation.bpmn` (the three content-agnostic, STRICT ones) and the
seven `crdm-*.bpmn` that run the requirements process. **There is no BPMN for
the software development lifecycle itself** — for how a change to the *platform*
goes from a need to a released capability. `beans list -S SDLC` returns empty.

So the gap is not that the documentation is scattered. It is that the SDLC is
the one process in this repository that is described in prose (`AGENTS.md`
§"Commit early, commit often, always PR", `skills/folio-core/prepare-merge.md`,
`docs/contributing.md`) and never drawn — while AGENTS.md's own rule is that
anything with actors, activities and a control flow is authored as BPMN.

## What "formal formal" has to mean here

Not more prose. A process in this repository is formal when it is executable:
lanes bound to declared roles, every activity carrying `<folio:skill ref>`,
bean operations declared with `<folio:bean op>`, and `bun run kg:audit` green on
its joins. That is the bar `crdm-requirements.bpmn` already meets.

MVP is named in #363 as a subprocess. It probably is one — `crdm-deliver.bpmn`
already contains "share MVP" and loops back into implementation — so the work
may be to *reference* that subprocess rather than draw a second one. Check
before drawing.

## Route

1. Audit which of the existing 31 diagrams already cover a phase of the SDLC,
   and where the seams are. Do not draw over them.
2. Draw only what is genuinely missing, as a process that calls the existing
   subprocesses rather than restating them.
3. Bind every lane to a role in `scenarios/roles.json`; add roles only where
   a real participant has none.
4. Align the prose: the rules in `AGENTS.md` that describe this lifecycle move
   into the governing skill, per the "🛑 Do not edit this file" banner. Rules
   that live only in `AGENTS.md` are migration debt.

## Done when

- [ ] the audit above is written down, naming which existing diagram owns which
      phase — including the phases nothing owns
- [ ] `bun run render:bpmn:check` and `bun run kg:audit:check` are green
- [ ] no SDLC rule is left stated only in `AGENTS.md`

## Not doing

Changing how any existing process behaves. This is drawing what already happens,
plus the deployment phase the topology axes add. If the audit finds a real
defect in an existing diagram, that is its own bean.

## Depends on

The topology axes (parent epic). A deployment phase cannot be drawn before the
set of deployment targets is agreed — the lane's activities differ per topology.

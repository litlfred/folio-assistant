`main` has been red on **End-to-end + accessibility (hard)** since at least
`de4a49ecfbe` (2026-09-30). The failing step is `render:bpmn:check`, and it
cannot go green on its own.

## What is actually true

There are **two** `render-bpmn.ts`, and they overlap on three files while
disagreeing about their contents.

| renderer | files its `--check` reports | writes the generated-by note |
|---|---|---|
| `cat-harness/scripts/render-bpmn.ts` | **78** | no — 0 references to `generated-by` |
| `bootstrap-tools/scripts/render-bpmn.ts` | **3** (`bootstrap/processes/`) | yes — imports `generatedNote` |

`package.json` names the **cat-harness** one for both `render:bpmn` and
`render:bpmn:check`.

The three files under `bootstrap/processes/` are written by bootstrap-tools'
renderer and carry its note:

```
<!-- Generated by bootstrap-tools (scripts/render-bpmn.ts) from discussion.bpmn
     — do not edit; change discussion.bpmn. -->
```

cat-harness' renderer produces the same SVG **without** that line, compares,
and reports stale. It will report stale on every run forever, because the file
it is comparing against is not the file it would write.

## How it got here

- `3019b61729d` — *"bootstrap-tools: the Process renderer moves down (Phase 2,
  3 of 3)"*. Touched both files.
- `9771531e489` — *"Every file bootstrap-tools writes into bootstrap names it
  as the writer (owner, 2026-09-30)"*. Taught the **moved** renderer the note
  and rewrote the three SVGs.

The move landed; `package.json` did not follow it. Neither commit is wrong on
its own.

## The two obvious fixes are both wrong, and that is the point

**"Just run `bun run render:bpmn`"** — which is *what the failure message
itself advises* — regenerates through cat-harness' renderer and **deletes the
note the owner added yesterday**. Measured: `3 files changed, 3 deletions(-)`,
one line each, and the line removed is the attribution. The gate goes green by
reverting owner-directed work, and the commit that does it looks like routine
housekeeping.

**"Point `package.json` at the bootstrap-tools renderer"** — the gate goes
green by checking **3 files instead of 78**. That is `tqv4` exactly: a
measurement that improves by losing its subject. It was my first proposal and
the count is what killed it.

## What the fix has to decide

Which renderer OWNS `bootstrap/processes/`, and then:

- if bootstrap-tools owns it, cat-harness' renderer must **stop rendering those
  three** (and the gate must run both renderers, or 3 files lose their check)
- if cat-harness owns it, its renderer must **learn the note**, and
  bootstrap-tools' should stop writing them

Both are defensible. Neither is derivable from the corpus — `9771531e489` says
bootstrap-tools writes *into bootstrap*, which argues for the first, but does
not say cat-harness' renderer should narrow, and narrowing it silently is how
75 files stop being checked.

**Owner decision. Recorded unanswered rather than guessed at.**

## Done when

- [ ] ownership of `bootstrap/processes/*.svg` is settled between the two
      renderers, in one place
- [ ] `render:bpmn:check` is green on `main` **and** still reports 78 files, or

- [ ] the failure message no longer advises a command that reverts the note —

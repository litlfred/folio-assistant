**A regression from `oqdr`'s fix**, which is `completed` and covered exactly
these three files from the opposite direction: *"rendered by nothing since the
split"*. They are now rendered by **two** generators that disagree.

## Measured

`End-to-end + accessibility (hard)` failed on PR #1664, at `render:bpmn:check`:

```
✗ bootstrap/processes/discussion.svg is stale
✗ bootstrap/processes/initialize-harness.svg is stale
✗ bootstrap/processes/log-message.svg is stale
```

**NOT MINE, and established rather than asserted:** zero `.bpmn`/`processes/`
files in that PR's diff, and a pristine `origin/main` worktree reports the
SAME three. Main is red on this.

## Regenerating "fixes" the check by DELETING the provenance banner

`bun run render:bpmn` produces a diff of **3 deletions, 0 insertions**:

```
-<!-- Generated by bootstrap-tools (scripts/render-bpmn.ts) from log-message.bpmn — do not edit; change log-message.bpmn. -->
```

That is the `sec-119` shape from #1637 one corpus over: a regeneration that
silently drops content is not a regeneration. Not committed.

## The actual defect: two generators, one artefact

| generator | writes the banner? | wired to |
|---|---|---|
| `bootstrap-tools/scripts/render-bpmn.ts:200` | **yes**, via `generatedNote(...)` | not the npm script |
| `cat-harness/scripts/render-bpmn.ts` | **no** | `render:bpmn`, `render:bpmn:check`, CI |

And the omission is DELIBERATE — `bootstrap-tools`' own comment says so:

> The note goes on THIS copy only — the one written into the content graph. A
> harness drawing its own site copy with `drawing()` is not bootstrap-tools
> writing into bootstrap, and must not say it is.

So `cat-harness`'s generator is correct to omit the banner **for its own site
copy**, and is judging a file it does not own. `oqdr` closed the "nobody renders
these" gap by widening the cat-harness scan to reach `bootstrap/`, which made
the owner ambiguous.

## Why this is NOT a one-line fix, and why I did not guess

Three readings, and they are not equivalent:

1. **bootstrap-tools owns `bootstrap/processes/*.svg`** → the cat-harness scan
   must EXCLUDE them, and something must run the bootstrap-tools renderer in CI.
   `oqdr`'s gap returns unless that second half lands.
2. **cat-harness owns them** → the banner is dropped from the committed files
   on purpose, and `generatedNote` at `render-bpmn.ts:200` is dead code for
   this path. A generated file then no longer says it is generated.
3. **Both write, to different destinations** → the content-graph copy keeps the
   banner and the site copy does not, which is what the comment describes, and
   the two must not share a path.

Getting it wrong either strips provenance from a generated artefact or leaves
two writers fighting over one file. That is an ownership ruling, not a repair,
and it belongs to whoever owns the split (`vke6`).

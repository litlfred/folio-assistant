**A regression from `oqdr`'s fix**, which is `completed` and covered exactly
these three files from the opposite direction: *"rendered by nothing since the
split"*. They are now rendered by **two** generators that disagree.

## Measured

`End-to-end + accessibility (hard)` failed on PR #1664, at `render:bpmn:check`:

```
✗ bootstrap/processes/discussion.svg is stale
✗ bootstrap/processes/initialize-harness.svg is stale
✗ bootstrap/processes/log-message.svg is stale
```

**NOT MINE, and established rather than asserted:** zero `.bpmn`/`processes/`
files in that PR's diff, and a pristine `origin/main` worktree reports the
SAME three. Main is red on this.

## Regenerating "fixes" the check by DELETING the provenance banner

`bun run render:bpmn` produces a diff of **3 deletions, 0 insertions**:

```
-<!-- Generated by bootstrap-tools (scripts/render-bpmn.ts) from log-message.bpmn — do not edit; change log-message.bpmn. -->
```

That is the `sec-119` shape from #1637 one corpus over: a regeneration that
silently drops content is not a regeneration. Not committed.

## The actual defect: two generators, one artefact

| generator | writes the banner? | wired to |
|---|---|---|
| `bootstrap-tools/scripts/render-bpmn.ts:200` | **yes**, via `generatedNote(...)` | not the npm script |
| `cat-harness/scripts/render-bpmn.ts` | **no** | `render:bpmn`, `render:bpmn:check`, CI |

And the omission is DELIBERATE — `bootstrap-tools`' own comment says so:

> The note goes on THIS copy only — the one written into the content graph. A
> harness drawing its own site copy with `drawing()` is not bootstrap-tools
> writing into bootstrap, and must not say it is.

So `cat-harness`'s generator is correct to omit the banner **for its own site
copy**, and is judging a file it does not own. `oqdr` closed the "nobody renders
these" gap by widening the cat-harness scan to reach `bootstrap/`, which made
the owner ambiguous.

## Why this is NOT a one-line fix, and why I did not guess

Three readings, and they are not equivalent:

1. **bootstrap-tools owns `bootstrap/processes/*.svg`** → the cat-harness scan
   must EXCLUDE them, and something must run the bootstrap-tools renderer in CI.
   `oqdr`'s gap returns unless that second half lands.
2. **cat-harness owns them** → the banner is dropped from the committed files
   on purpose, and `generatedNote` at `render-bpmn.ts:200` is dead code for
   this path. A generated file then no longer says it is generated.
3. **Both write, to different destinations** → the content-graph copy keeps the
   banner and the site copy does not, which is what the comment describes, and
   the two must not share a path.

Getting it wrong either strips provenance from a generated artefact or leaves
two writers fighting over one file. That is an ownership ruling, not a repair,
and it belongs to whoever owns the split (`vke6`).

## Done when

- [ ] Which generator owns `bootstrap/processes/*.svg` is DECIDED and written
      down where both scripts' scan sets are computed.
- [ ] `render:bpmn:check` passes on `main` without any SVG losing its banner.
- [ ] `oqdr`'s gap stays closed — whatever renders them is RUN in CI, not
      merely able to be run.
- [ ] A test pins whichever way it goes, so the next widening of a scan set
      cannot silently re-create the overlap.

## NOT in this bean

Whether `generatedNote` should be used by more generators. This is about one
overlap, not about provenance banners in general.


## CORRECTION 2026-09-30 — the gate FLAPPED, and the title's "main is red" overclaims

The title and the account above present this as a deterministic failure. It is
not, and I do not have the mechanism. What is measured:

| head | `End-to-end` | note |
|---|---|---|
| `b937d71cb40` 18:52 | **red** at `render:bpmn:check`, naming exactly the three `bootstrap/processes/*.svg` | read from the CI log, not inferred |
| `7d28eb637da` 19:0x | **green**, whole job | same three files untouched between the two heads |

The only difference between those commits is a bean file and the
`beans/README.md` regenerated from it. Neither touches an `.svg`, a `.bpmn`, or
either generator. **So the gate flapped, and #1664 merged with every one of its
twelve checks green.**

Locally it fails CONSISTENTLY, and there the diff is banner-only — 3 deletions,
0 insertions, removing `<!-- Generated by bootstrap-tools ... do not edit -->`.
That part stands, and so does the two-generator overlap: `bootstrap-tools`
emits the banner at `render-bpmn.ts:200`, `cat-harness` deliberately does not,
and `cat-harness` is the one CI runs.

### What I checked and what I did NOT establish

Ruled out by reading the 18:52 log in full: that the CI failure named different
files than the local one. It named the same three.

**NOT established, and not to be read as established:**

- why it passed on the later head. A plausible story is available — that run
  installed fonts and downloaded a fresh Chromium seconds before the check, and
  bpmn-js lays out SVG text from font metrics — but the local diff is
  banner-only, which font metrics do not explain. Two incompatible stories, so
  neither is recorded as the cause.
- whether `main` is red on this NOW. The worktree reproduction was run in this
  container, which also fails consistently; that is evidence about this
  container, not about CI.

### This is the `1xhc` family, not only an ownership question

A gate whose verdict changes without its inputs changing is worse than one that
is simply wrong: it teaches readers to re-run rather than to look, and it made
me write a confident ownership story into a bean off one observation. The
ownership overlap is real and still worth settling — but **the flap has to be
characterised first**, or a fix will be judged by a gate that cannot tell
whether it worked.

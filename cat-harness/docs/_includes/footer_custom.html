The build stamp lives HERE rather than in `footer_content` for a reason that is easy to get wrong: the theme emits that setting as `{{ site.footer_content }}`, a plain variable output. Liquid does not re-parse a variable's value, so `{{ site.data.build.short_sha }}` written into _config.yml would render on the page as those literal characters. An include is parsed, so it works here and only here. WHY A STAMP AT ALL. Without one there is no way to tell from the page whether a change is live: a stale browser cache and a deploy that has not run look identical, and the reader is left inferring deployment state from rendered behaviour. That is not a hypothetical — it is how this site's last few rounds of changes were assessed. `docs/_data/build.yml` is written by the "Stamp the build sha" step in .github/workflows/docs-site.yml and is NOT committed: a sha checked into the repo would name the commit BEFORE the one that deployed it, which is worse than no stamp at all. A local `jekyll serve` has no data file and shows "dev". {%- endcomment -%} {%- comment -%} THE LINEAR FLOOR, and it is page content rather than a script's output. `generated/todo-listing.html` is written by `gen-docs-pages.ts` from the same `items` array that produces `assets/todos/index.json`.

Description

Where a note sits on a board — a layer ON TOP of the notes, never inside them.

Notes sit below the folio

A note gains no x, no y, no board, no order. This layer names notes BY ID and the relation points one way:

    So:

    1. A note is complete with no board. readTodoFiles, the todo index, the sticky board and the QA sidecars are untouched, and a folio that never opens a board has nothing extra in its work plan. The layer is ADDITIVE and REMOVABLE: delete this file and every note is what it was. 2. One note may sit on several boards, at different places, without the note arbitrating between them. 3. The layers stay clean. This is state, written by a running process; a coordinate on a content note would make it carry state, which content-context-and-state-graphs refuses. 4. An orphan is swept from the LAYER: one file, one pass, and nothing edited out of a note a person owns.

    ONE committed file, with the board as a key

    The board is a key inside this document, so a new board adds lines rather than a file.

    Mergeability

    Two sessions moving two notes is the ordinary case, and git merges by line, so a minified one-line file conflicts on every concurrent change. So: indented, one position per line, sorted by board then note id. Two sessions moving DIFFERENT notes merge untouched. Two notes that sort ADJACENT can still conflict: this removes the guaranteed conflict, not every conflict.

    The ordering must be deterministic, or a writer would reshuffle on every save; sortPositions guarantees it, and it is tested.

    ONE position per note per board, in the TYPE

    Positions are keyed by note id: boards[board][note] is one position or none, so no file — hand-written, merged, or from a writer that bypassed place() — can hold a note twice on one board. Each note still occupies its own lines under an indented write, so a move edits one line-block in situ.
